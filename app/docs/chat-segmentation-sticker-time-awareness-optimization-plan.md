# Echo 聊天分段、官方表情包与时间感知优化方案

> 状态：已确认，进入实现阶段
>
> 日期：2026-08-07
>
> 适用范围：Android APP 文字聊天、Echo 分段回复、Echo 官方表情包、连续消息窗口、对话时间感知
>
> 不适用范围：语音通话。通话继续使用 ASR -> Agent -> TTS 链路，不注册和交付表情包工具。
>
> 关联文档：`async-chat-experience-optimization-plan.md`、`unified-agent-runtime-refactor-plan.md`、`sticker-sending-plan.md`

## 1. 先回答当前观察

### 1.1 为什么 Echo 分段回复很少出现

目前的分段能力不是把每条回复机械拆开，而是受到三层约束：

1. Agent 最终文字本身通常是一段完整文本，模型没有明确规划分段时，交付层不会强行拆分。
2. 短回复、事实回答、工具结果、错误提示、敏感话题默认保持单段，避免产生不自然的“机器人逐句发送”。
3. 分段数量和节奏受到最多三段、最小长度、句子边界和发送冷却控制。

因此当前表现确实偏保守。优化方向不是无条件增加消息数量，而是让 Agent 返回可验证的分段意图，并增加一个确定性的分段兜底器，让适合的中长回复稳定触发两段或三段。

### 1.2 为什么 Echo 主动发图也不容易触发

主动表情包同时需要满足模型意图和运行时门禁：

- 模型必须在当前语境中提出 `search_stickers`，而不是只在文字里说“哈哈”。
- 搜索必须返回当前 Echo 可见的候选表情包。
- 本回合还必须成功执行一次 `send_sticker`。
- 第一阶段默认有主动发送冷却，且严肃、冲突、医疗、安全、明显悲伤等话题禁止主动发图。
- 每个 Echo 回合最多成功发送一张。

这套规则能防止刷屏和“文本说发了但实际没有附件”，但默认值偏保守，会让主动发送体感较少。本文建议降低主动冷却，并增加可观测日志，先用数据校准，不恢复关键词强制触发。

## 2. 目标

1. 用户连续输入时，Echo 能把同一批消息作为持续对话理解，同时保留每条用户消息的独立气泡。
2. Echo 的中长回复能自然拆成 2 至 3 条独立文字消息，并按字数产生打字节奏。
3. Echo 官方表情包与用户个人表情包分离存储、分离权限、分离检索范围。
4. 用户明确索要表情包时稳定触发；Echo 自然聊天时可以适度主动发送，但不刷屏。
5. 混合批次中，文字消息拥有更高语义权重；用户表情包只以标签参与理解，不让描述词干扰文字上下文。
6. Echo 能感知用户是否在连续聊天或长时间离开，但不会每条消息都提到时间。
7. 所有策略均可配置、可观测、可测试，后续能扩展更多附件和工具。

## 3. 总体数据流

```text
APP 发送文字/表情包
  -> Chat Intake 记录 message_id、client_sent_at、server_received_at
  -> 2500ms 静默窗口收集消息
  -> 最长 10000ms 后封口
  -> Input Batch 生成
  -> Context Builder 计算表情包语义和消息时间状态
  -> Unified Agent Runtime
       -> 普通回复，或调用 sticker/time/search 等工具
       -> 生成 reply_segments + attachments
  -> Segment Planner 校验分段数量和边界
  -> Delivery Timing Policy 计算每段延迟
  -> Chat Delivery 持久化并通过 SSE 推送
  -> APP 显示独立文字气泡和独立图片消息
```

分段、表情包和时间感知都属于同一个 Agent Turn 的结果处理，不重新引入独立 Planner，也不在 Agent 之外用关键词改写模型结论。

## 4. 连续消息窗口

### 4.1 确认后的窗口参数

```text
静默窗口：2500 ms
最长等待：10000 ms
```

定义：

- 第一条消息进入收集状态时记录 `batch_started_at`。
- 每收到一条新消息，将 `collect_until` 更新为“最后一条消息的 `server_received_at` + 2500ms”。
- `collect_until` 不能超过 `batch_started_at + 10000ms`。
- 达到静默窗口，或达到最长等待，批次封口并只启动一次 Agent Turn。
- 封口后新来的消息进入下一批，不追加到已开始推理的批次。

示例：

```text
12:00:00.000  用户：今天好累
12:00:01.200  用户：工作好多
12:00:02.900  用户：再发一个表情包
12:00:05.400  静默 2500ms，批次封口
```

以上三条消息作为一个 Input Batch，但仍然是三条独立用户消息。

### 4.2 混合文字和表情包的上下文投影

当同一批次同时包含文字和表情包时：

- 文字原文完整进入 Agent 上下文。
- 表情包只注入经过服务端校验的语义标签。
- 不注入表情包描述、文件名、URL、上传备注或图片二进制。
- 多张表情包的标签去重后合并，保留原消息顺序。

示例：

```text
用户文字：今天工作好多
用户表情包标签：疲惫、无奈
```

模型看到的是“用户表达了今天工作很多，并附带了疲惫、无奈语义的表情包”，而不是把描述词作为第二段长文本参与竞争。

当批次只有表情包没有文字时，可注入标签和一条很短的描述，帮助 Echo 理解图片；仍然不暴露 URL 和二进制内容。

### 4.3 窗口相关的重试和幂等

- `client_message_id` 保证用户重试不会产生重复消息。
- 同一 `conversation_id` 同时最多一个 collecting/processing Agent Turn。
- Worker 重启后根据 `collect_until` 和 `lease_expires_at` 继续处理，不重新创建批次。
- 2500ms/10000ms 只决定收集边界，不改变历史消息的真实发送时间。

## 5. Echo 分段回复

### 5.1 采用结构化分段，而不是字符串硬拆

Agent 最终结果增加可选的结构化字段：

```json
{
  "reply_segments": [
    {"text": "先抱抱你。", "kind": "empathy"},
    {"text": "今天是不是事情特别多？", "kind": "follow_up"}
  ]
}
```

`reply_segments` 为空时仍兼容单段 `reply_text`。Runtime 只接受模型输出的候选分段，不允许模型指定任意等待时间、消息时间戳或附件状态。

### 5.2 分段触发规则

推荐默认规则：

| 条件 | 处理 |
| --- | --- |
| 少于 24 个中文字符，或只有一句完整回答 | 单段 |
| 24 至 80 个字符，且有两个独立语义句 | 允许两段 |
| 超过 80 个字符，且存在三个自然语义单元 | 最多三段 |
| 含代码、URL、表格、数字清单、工具原始结果 | 默认单段，除非模型显式给出安全边界 |
| 错误、超时、安全、医疗、冲突和严肃说明 | 默认单段 |
| 只有一个句子但很长 | 按标点安全拆分，不在短语中间切断 |

分段优先使用模型提供的语义边界；模型没有给出分段但文本满足长度和标点条件时，由 `Segment Planner` 在句号、问号、感叹号、分号和自然连接词处做一次确定性兜底。禁止按固定字数切割，也禁止拆散 URL、数字、代码和专有名词。

### 5.3 交付节奏

文字已经生成完成后，Delivery Timing Policy 决定视觉上的“打字感”：

- 第一段：短暂准备延迟，建议 400 至 900ms。
- 段间延迟：根据上一段字数线性增加，建议 450ms 起步，单段不超过 2500ms。
- 长回复最多三段，不把模型 API 等待时间重复叠加。
- APP 收到消息后立即显示已交付的段，不等待整个 Reply Group 全部完成。
- 服务器不使用长时间阻塞数据库事务的 `sleep`；延迟应由可恢复的 delivery job 或事件计划实现。

### 5.4 为什么要增加兜底分段

如果只依赖模型主动返回多个段，模型会出于 token 和稳定性考虑经常返回一段。增加确定性兜底后：

- 语义完整的短回复仍保持单段。
- 适合聊天的中长回复能稳定产生两段。
- 任何工具、错误和敏感结果不会被强行切碎。
- 日志能区分“模型没有分段”和“策略主动保持单段”。

## 6. Echo 官方表情包批量导入

### 6.1 资源范围

官方表情包不是用户上传资源，建议新增独立资源范围：

```text
owner_type = echo
owner_id = Echo persona id
visibility = system
```

用户个人表情包继续使用：

```text
owner_type = user
owner_id = user id
visibility = private
```

`search_stickers` 默认检索“当前 Echo 官方表情包 + 当前用户个人可见表情包”，但工具返回的候选必须带来源和权限，不能跨用户读取私人资源。

### 6.2 批量导入文件格式

建议采用“图片目录 + manifest.jsonl”而不是只依赖文件名：

```json
{
  "file": "happy_001.webp",
  "description": "开心地眯眼笑",
  "tags": ["开心", "满足", "轻松"],
  "emotion": "joy",
  "situations": ["收到好消息", "轻松闲聊"],
  "priority": 50,
  "enabled": true
}
```

必填字段：`file`、`description`、至少一个语义标签。建议字段：情绪、适用场景、优先级、是否启用、来源和版权备注。

### 6.3 导入流程

1. 管理员准备图片目录和 manifest。
2. `dry-run` 扫描文件，校验格式、大小、尺寸、字段和重复项。
3. 计算 SHA-256 做完全重复检测，计算感知哈希做近似图片检测。
4. 生成缩略图和统一的展示尺寸；保留原图用于 COS 存储。
5. 通过内容安全和人工审核后，写入 `echo` 资源范围。
6. 图片上传 COS，元数据和对象 key 在同一批次中登记。
7. 批次提交后才进入 Agent 可见候选集合；失败批次整体保持不可见。
8. 导入报告列出成功、跳过、重复、字段错误和审核失败的文件。

### 6.4 存储建议

```text
COS:
  stickers/echo/{persona_id}/original/{sticker_id}.webp
  stickers/echo/{persona_id}/thumb/{sticker_id}.webp
  stickers/user/{user_id}/{sticker_id}/...
```

数据库至少保留：`sticker_id`、所有者、描述、标签、情绪、场景、COS key、SHA-256、感知哈希、状态、排序和导入批次 ID。

第一阶段建议只支持静态 PNG/JPEG/WebP。GIF/动画表情包先在导入时转为首帧或统一静态版本，待 APP、COS 和缓存链路都支持后再开放动画。

## 7. Echo 发送表情包的约束

### 7.1 用户明确索要

用户明确说“发一个开心的表情包”时：

1. Agent 调用 `search_stickers`，先按精确语义和标签检索。
2. 精确搜索无结果时，只允许进行一次宽泛分类回退，例如“开心”回退到“正向/轻松”；禁止连续猜关键词。
3. 有候选时调用 `send_sticker`，候选必须来自本回合搜索结果。
4. 成功发送后，文字和图片由同一个 Agent Turn 交付。
5. 明确请求不受主动表情包冷却影响，但仍然每回合最多成功一张。
6. 搜索和回退均无结果时，不伪造附件；Echo 应自然说明暂时没有合适的表情包。

### 7.2 Echo 主动发送

主动发送必须同时满足：

- 当前 Agent 判断图片能增加表达，而不是为了填充回复。
- 话题属于轻松、庆祝、安慰、撒娇、打趣、问候等允许场景。
- 不属于医疗、安全、争执、投诉、悲伤确认或严肃事实说明。
- 距离上一次 Echo 主动发送已通过冷却。
- 本回合尚未成功发送表情包。
- `search_stickers` 返回候选且候选通过可见性和状态校验。

建议把当前“4 个 assistant 回合冷却”调为“2 个 assistant 回合冷却 + 最短 30 秒间隔”，以降低体感上的触发难度；明确请求仍不受该冷却限制。该值先做成配置，不直接写死在提示词中。

### 7.3 不允许的行为

- 只根据关键词扫描强行触发工具。
- 模型在文字中说“我发了”但没有成功的 `send_sticker` 结果。
- 直接让模型编造 sticker ID、COS URL 或附件状态。
- 同一回合重试造成两张成功图片。
- 用户表情包描述覆盖混合批次中的文字语义。
- 通话模式暴露或调用表情包工具。

### 7.4 必须补充的可观测字段

每次 Agent Turn 记录脱敏事件：

```text
sticker_intent: explicit | proactive | none
search_query_source: model | fallback
search_result_count
send_attempted
send_succeeded
blocked_reason: cooldown | sensitive_topic | no_candidate | quota | tool_error | none
```

这样可以区分“模型没有想发”“模型想发但被冷却拦截”“搜索无结果”和“工具执行失败”，不再凭聊天文本猜测触发原因。

## 8. 对话时间感知

### 8.1 时间字段

用户消息建议同时保留：

- `client_sent_at`：APP 生成消息时的本地时间，仅用于诊断和离线延迟分析。
- `server_received_at`：服务器收到并持久化消息的时间，作为对话时间线权威。
- `created_at`：数据库记录创建时间；如果当前字段已经承担服务端接收时间，则直接复用，不新增重复字段。

不能让客户端时间直接决定是否触发“你去哪了”，避免设备时钟错误或恶意伪造影响人格行为。

### 8.2 时间状态分类

Context Builder 不把每次时间差都写成自然语言，而是计算结构化状态：

```json
{
  "conversation_timing": {
    "gap_seconds": 18,
    "state": "active",
    "should_acknowledge_gap": false,
    "gap_acknowledged_for_return": true
  }
}
```

推荐初始阈值：

| 最近一条用户消息间隔 | 状态 | 默认行为 |
| --- | --- | --- |
| 0 至 120 秒 | `active` | 当作持续对话，不提时间 |
| 120 秒至 30 分钟 | `recent` | 正常回答，不主动提时间 |
| 30 分钟至 6 小时 | `returned` | 仅在闲聊或问候语境中允许轻描淡写地问候 |
| 超过 6 小时或跨自然日 | `long_absence` | 可在合适语境中问候一次，不强制插入 |

这些阈值只作为初始配置，后续用真实对话数据调整。

### 8.3 “你干什么去啦”的触发策略

长时间离开不等于每次都要追问。建议使用三层门禁：

1. **时间门禁**：至少达到 `returned`，优先 `long_absence`。
2. **语境门禁**：用户当前消息是闲聊、问候、分享近况或情绪表达时才允许；用户直接问事实、发送任务指令或报告错误时不插入。
3. **频率门禁**：同一次返回窗口最多询问一次；同一自然日最多主动提及一次。用户已经主动解释去向后，本次返回窗口不再追问。

最终文案仍由 Agent 自然生成，系统只提供一个低优先级提示：

```text
用户离开了一段较长时间。若当前是轻松闲聊，可自然问候一次；不要机械报时，不要每次都询问去向。
```

可接受的表达包括“刚刚去忙什么啦？”、“回来啦？”；不要求固定模板，也不在系统消息中暴露精确时间给用户。

### 8.4 与连续消息窗口的关系

- 同一个 2500ms/10000ms Input Batch 内的消息一定视为持续对话，不触发离开问候。
- 批次之间间隔很短但超过 2500ms，只影响收集边界，不自动触发时间话术。
- 时间感知使用用户消息的服务端接收时间，不使用 Echo 回复分段之间的交付延迟。
- APP 重连、历史补齐和重复投递不能重复触发“回来啦”，状态必须由服务端持久化或可重建。

## 9. 配置建议

```text
CHAT_COLLECT_SILENCE_MS=2500
CHAT_COLLECT_MAX_WAIT_MS=10000

CHAT_REPLY_MAX_SEGMENTS=3
CHAT_REPLY_SEGMENT_MIN_CHARS=24
CHAT_REPLY_SEGMENT_MAX_DELAY_MS=2500

ECHO_PROACTIVE_STICKER_COOLDOWN_TURNS=2
ECHO_PROACTIVE_STICKER_MIN_INTERVAL_SECONDS=30
ECHO_STICKER_MAX_SUCCESS_PER_TURN=1

ECHO_TIME_ACTIVE_MAX_SECONDS=120
ECHO_TIME_RETURNED_MIN_SECONDS=1800
ECHO_TIME_LONG_ABSENCE_SECONDS=21600

```

配置必须由后端统一下发或读取，APP 不自行决定 Agent 门禁。语音通话使用独立能力集合，不继承表情包配置。

## 10. 实施阶段

### Phase 1：批次和时间基础

- 确认并实现 2500ms 静默、10000ms 最大等待。
- 保存或复用 `server_received_at`，补充 `client_sent_at` 诊断字段。
- 增加混合批次的“标签-only”上下文投影。
- 增加 `conversation_timing` 结构化上下文。

### Phase 2：分段交付

- 扩展 AgentTurnResult 的 `reply_segments` 协议。
- 增加 Segment Planner 和句子边界兜底。
- 增加按字数计算的 Delivery Timing Policy。
- 保持最多三段，工具、错误和敏感场景默认单段。

### Phase 3：官方表情包资源

- 增加 `echo` 资源范围和批次导入命令。
- 实现 manifest 校验、哈希去重、缩略图和 COS 前缀。
- 管理员审核后才进入 Agent 检索集合。
- 搜索工具默认合并 Echo 官方资源与当前用户个人资源。

### Phase 4：表情包触发校准

- 先增加触发原因和拦截原因日志。
- 将主动冷却从 4 回合调整为可配置的 2 回合 + 30 秒间隔，观察刷图率。
- 明确请求继续免冷却，精确搜索无结果只允许一次分类回退。
- 回归测试工具成功、无结果、失败、超时和重复请求。

### Phase 5：时间感知灰度

- 先只记录时间状态，不生成任何时间话术。
- 通过日志观察 `active/recent/returned/long_absence` 分布。
- 开启低优先级问候提示，验证每日和返回窗口限额。
- 评估用户反馈后再调整阈值和文案风格。

## 11. 验收标准

### 分段

- 24 字以内短回复仍为单段。
- 具有两个自然语义单元的中长回复稳定出现两段。
- 超长回复最多三段，URL、代码和敏感说明不被错误切开。
- APP 文字气泡独立显示，段间有可观察但不夸张的延迟。

### 官方表情包

- 官方表情包不出现在用户私人资源管理列表中。
- 批量导入可预览错误、重复和成功数量。
- 导入未提交前，Agent 搜索不到该批次。
- 用户明确请求成功率可通过日志区分模型未调用、无候选和工具失败。

### 时间感知

- 同一批次和两分钟内的连续消息不触发离开问候。
- 超过 30 分钟返回的闲聊最多自然问候一次。
- 直接任务、事实问题和错误反馈不插入“你去哪了”。
- 同一返回窗口和自然日不会重复追问。
- 服务重启、SSE 重连和历史补齐不会重复触发时间话术。

## 12. 待确认事项

以下是建议默认值，不在你确认前修改代码：

1. 主动表情包冷却是否从现行 4 个 Echo 回合调整为 2 个回合，并增加 30 秒最短间隔。
2. “很久没回来”的初始阈值是否采用 30 分钟，超过 6 小时或跨自然日提高问候概率。
3. 官方表情包第一阶段是否只导入静态 PNG/JPEG/WebP，不处理 GIF 动画。
4. 官方表情包是否由你提供图片目录和 manifest，还是先由我按现有资源目录生成一份待补标签清单。
5. `server_received_at` 是否作为唯一对话时间线，`client_sent_at` 仅保留用于延迟诊断。
