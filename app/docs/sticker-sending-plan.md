# Echo 表情包发送功能开发方案

> 状态：已实现
>
> 日期：2026-08-05
>
> 本文用于记录交互、协议和分阶段实现范围。Agent 编排细节见 `agent-tool-orchestration-plan.md`。

## 1. 背景与现状

### 1.1 已有能力

- APP 已有表情包库页面，可以从相册上传、保存、刷新和删除用户表情包。
- 表情包数据包含 `sticker_id`、`owner_type`、`source`、`url`、描述和语义标签。
- 后端聊天响应已经支持 `content_parts`，其中可以包含 `type=sticker`。
- APP 聊天消息已经支持显示一个表情包，当前通过 `ChatReply.firstSticker` 取第一张。
- 后端 Agent 已有 `search_stickers` 能力，可以从 Echo 公共库和当前用户的私人库中检索表情包。

### 1.2 当前限制

- APP 聊天输入区没有表情包入口。
- 聊天请求目前只发送普通文本，没有用户表情包消息结构。
- Echo 当前主要在用户消息明确提到“表情包”时检索和返回一张表情包，不会在每轮普通聊天中主动发送。
- 用户上传的表情包如果没有描述或语义标签，可能无法被 Echo 的文本检索命中。
- APP 目前只渲染回复中的第一张表情包，不保证多个 `content_parts` 的完整顺序。

## 2. 本次目标

实现类似微信的表情包发送体验：

1. 聊天输入框旁增加表情包按钮。
2. 点击按钮后，从底部弹出当前可用的表情包面板。
3. 点击某张表情包后立即发送，不放入文字输入框。
4. 表情包作为一条独立的用户消息显示在聊天记录中。
5. Echo 可以继续返回文字，也可以在同一轮回复中附带表情包。
6. 发送失败时保留明确错误状态，不能出现“界面已显示但后端未收到”的假成功。

## 3. 交互方案

### 3.1 聊天页入口

在现有文字输入框左侧增加图标按钮：

- 图标使用 `Icons.emoji_emotions_outlined` 或项目已有图标规范中的等价图标。
- 按钮 tooltip 为“表情包”。
- 当前聊天正在发送、清理上下文或退出页面时禁用。
- 不改变现有文字输入和发送按钮行为。

### 3.2 底部表情包面板

使用 `showModalBottomSheet` 展示表情包：

- 顶部显示“表情包”标题和关闭按钮。
- 使用网格布局显示缩略图，建议 4 列，图片保持等比裁切。
- 同时显示 Echo 公共表情包和用户私人表情包。
- 用户私人表情包可以继续删除，但面板中不显示删除操作，避免误触。
- 表情包加载中显示轻量 loading；加载失败提供重试。
- 没有表情包时提供“去添加表情包”的入口，跳转现有表情包库页面。

### 3.3 发送时机

推荐“点击即发送”：

- 用户点击某张表情包后立即关闭面板并发送。
- 不需要再次点击聊天发送按钮。
- 发送前先在本地消息列表中加入用户表情包消息，表现为乐观更新。
- 请求期间沿用现有聊天忙碌状态，防止连续重复发送。
- 如果请求失败，将该消息标记为错误，并提供重试入口；不能静默丢失。

不采用以下方式：

- 选择表情包后只填入输入框，等待用户再次点击发送。
- 打开表情包库或离开表情包库时自动发送。
- 根据用户每句话自动猜测并发送用户表情包。

## 4. 消息模型设计

### 4.1 用户表情包消息

现有 `ChatMessage` 已有 `sticker` 字段，可以继续复用。用户消息建议表示为：

- `sender=user`
- `content=''`
- `sticker=ChatSticker(stickerId, url)`
- `isTyping=false`

聊天气泡根据消息是否包含文字和图片决定布局，图片消息不显示空白文字区域。

### 4.2 Echo 回复消息

保留现有响应兼容字段：

- `reply` 继续承载文字回复。
- `content_parts` 承载文字、表情包等有序内容。
- 第一阶段 APP 可以继续显示第一张表情包。
- 后续再改为完整按 `content_parts` 顺序渲染，支持多张表情包和文字交错。

## 5. 后端协议方案

### 5.1 推荐方案：扩展现有 `/chat/send`

不新增独立聊天 endpoint，统一走现有会话、记忆和回信流程。

普通文字请求保持不变：

```json
{
  "message": "你好",
  "mode": "chat"
}
```

表情包请求新增内容片段：

```json
{
  "message": "",
  "mode": "chat",
  "content_parts": [
    {
      "type": "sticker",
      "sticker_id": "stk_xxx"
    }
  ]
}
```

服务端只信任 `sticker_id`：

- 根据当前用户身份校验表情包是否可用。
- 允许 Echo 公共表情包和当前用户自己的私人表情包。
- 不接受客户端直接指定任意图片 URL。
- 将该表情包消息写入会话上下文，再交给 Echo 生成回复。

### 5.2 请求响应行为

表情包请求成功后，后端返回普通 `ChatResponse`：

- `reply` 可以为空，也可以包含文字。
- `content_parts` 可以为空，也可以包含 Echo 选择的表情包。
- APP 将用户表情包和 Echo 回复分别显示为两条消息。

### 5.3 兼容策略

- 现有纯文本客户端不受影响。
- 后端缺少 `content_parts` 时，APP 继续只显示 `reply`。
- 后端拒绝无权限的 `sticker_id` 时返回明确的 4xx 错误。
- 不把图片二进制放入聊天请求，避免请求体膨胀。

## 6. Echo 回表情包规则

### 6.1 第一阶段规则

先保持克制，只在以下情况发送：

- 用户明确请求表情包。
- 用户发送的内容明显适合用表情包回应，并且检索到高匹配度结果。

以下情况默认不主动发送：

- 严肃、安全、医疗、冲突或明显悲伤的话题。
- 连续多轮重复发送。
- 没有高匹配度表情包时强行发送。

### 6.2 用户表情包可检索性

上传表情包时建议增加描述和标签，例如：

- 描述：`开心挥手`
- 标签：`开心,挥手,打招呼`

如果继续允许无描述上传，后端需要增加“无查询时按最近使用或随机候选”的策略，否则 Echo 很难主动找到这类图片。

### 6.3 Agent 发送能力

Echo 的表情包发送属于 Agent 能力，不由 LLM 自己伪造图片链接：

- `search_stickers` 负责按描述、标签和语境查找候选。
- `send_sticker` 负责再次校验当前用户可见范围，并生成结构化附件。
- 发送动作写入 Agent 工具调用记录，最终通过 `content_parts` 返回给 APP。
- 用户明确请求表情包但语义检索没有精确命中时，可以从当前用户可见库中选择最近候选；不得让 Echo 回复“无法发送”后结束。
- `send_sticker` 的结构化执行结果是发送状态的唯一事实来源，成功文案和附件由 Agent Response Policy 一次性组装。
- 当前 LLM Provider 通过结构化 JSON Planner 生成工具计划；工具成功后不再调用自由文本 LLM 描述发送状态，也不再使用关键词或正则纠错。

## 7. APP 实现拆分

### 7.1 Domain / Data

- 扩展聊天请求 DTO，使其能够表达文本消息或表情包消息。
- 扩展 `ChatRepository`，增加发送表情包的方法，或统一为发送 `ChatSendPayload`。
- 保留 `StickerItem` 和 `ChatSticker` 两套领域模型，避免表情包库和聊天消息互相耦合。

### 7.2 Controller

- 增加 `sendSticker(StickerItem sticker)`。
- 复用文本消息的取消、忙碌、错误和回复处理逻辑。
- 在请求开始时加入用户表情包消息。
- 成功后追加 Echo 回复；失败后保留失败消息并支持重试。

### 7.3 Presentation

- 新增聊天表情包按钮。
- 新增底部表情包选择面板。
- 复用 `stickersControllerProvider` 加载表情包列表。
- 调整消息气泡，使用户和 Echo 的图片消息都能正确显示。
- 文字回复继续使用气泡；表情包作为独立图片消息渲染，不嵌套在文字气泡内。

## 8. 分阶段实施

### Phase 1：用户发送闭环

- 聊天页表情包按钮和底部面板。
- 用户点击即发送。
- 后端接受 `content_parts` 表情包请求。
- 用户表情包消息显示。
- Echo 返回的文字和一张表情包继续显示。

### Phase 2：回信质量优化

- 上传时补充描述和语义标签。
- 优化 Echo 表情包检索和触发条件。
- 支持最近使用、收藏和基础去重。
- 支持回复中的多个 `content_parts` 按顺序渲染。

### Phase 3：体验增强

- 长按预览。
- 表情包发送失败的单条重试。
- 最近使用列表和分页加载。
- 统计用户发送、Echo 发送和删除行为，用于调整主动发送频率。

## 9. 验收标准

- 聊天页可以打开表情包面板。
- 面板同时显示 Echo 表情包和当前用户已保存的表情包。
- 点击表情包后立即出现一条用户图片消息。
- 后端能收到正确的 `sticker_id`，且不能越权发送其他用户的表情包。
- Echo 能正常返回文字；命中条件时能附带表情包。
- 网络失败、后端 4xx、重复点击均有可见且可恢复的状态。
- 原有文字聊天、语音通话、表情包保存和删除功能不回归。
- `flutter analyze` 为 0，`flutter test` 全部通过。

## 10. 已确认决策

1. 用户发送表情包后，Echo 必须回复一次。该回复可包含文字，也可在命中合适表情包时附带一张表情包。
2. 上传表情包时必须填写描述和语义标签。描述用于用户识别，标签用于 Echo 检索和理解该图片表达的语义。
3. 第一阶段 Echo 回复最多展示一张表情包；多张表情包和文字交错渲染放入后续阶段。
4. 其余实现细节以本文第 3 至第 9 节为准：聊天页入口、点击即发送、统一 `/chat/send` 会话协议、`sticker_id` 权限校验和失败可恢复状态均为本次范围。
