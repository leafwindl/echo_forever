一、整体架构

四端一脑：手机/鸿蒙 App、安卓 Phone Agent、Windows 电脑节点、Hyper-V 虚拟机，加一个 FastAPI 后端和 DeepSeek 模型。

客户端 Flutter / Harmony

Flutter App（13 个 feature：聊天、语音、设备、表情、来信、记忆、在场、推送、专注、更新…）和 HarmonyOS 原生版（Index / Devices / Notifications / Update）。

  • 聊天走 POST /chat/messages + SSE 事件
  • 设备走 BLE 配网 + WebSocket 语音

Phone Agent Android

无障碍服务 + 截图桥 + 通知监听 + 微信 OCR 监控，通过 WebSocket 接入后端，按技能执行手机任务。

  • 技能：抖音/小红书/B站/音乐/微信/通知
  • 输入走 PC ADB 桥（8765）

Desktop Node Windows

用户自己的电脑节点：屏幕截图、应用、媒体控制、DSH 任务，带审批和 token 配对。

  • /desktop/nodes/ws 长连接
  • 审批弹窗，auto_approve 可配

EchoComputer Hyper-V VM

Echo 自己的 Windows 电脑：agent.ps1（点击/输入/截图/exec）+ wechat_bridge.py（微信 UI 自动化、图片目录、B站扫描）。

  • exec 是异步 job：Start-Job + job_result 轮询
  • 微信只服务唯一联系人「叶子」

后端 FastAPI

21 个 feature、18 个路由模块、8 个后台循环。分层：Interface → Application → Domain ← Infrastructure。

  • WebSocket 节点通道 + HTTP API + SSE
  • 异步聊天队列 chat_turn_jobs

模型与外部服务 Providers

DeepSeek 文本 + 多模态；另有 ASR、TTS、视觉、网页搜索、图片生成、Embedding、COS 存储、Getui 推送。

  • 图片消息直接进 DeepSeek，不再单独视觉模型
  • 上下文预算按 token 估算
已完成 线上验证过 有风险 可用但脆弱 阻塞 当前卡点

二、功能模块（后端 21 个 feature）

每个模块只写职责和最关键的入口，细节链路在「执行链路」一节。

chat 会话 核心

消息、异步队列、历史、摘要、交付、清除上下文。

  • POST /chat/messages（202 入队）
  • GET /chat/messages、GET /chat/events(SSE)
  • 摘要：24 条触发，保留最近 12 条

agent 模型回路 核心

受限模型循环、工具选择、执行门禁、轨迹与去重。

  • 42 个工具、按模式注入
  • 记录 agent_runs / agent_tool_calls

conversation_events 事件流 新

统一历史表：消息、工具调用、B站分享、主动发送都写同一时间线，供后续压缩。

  • 字段：type / source / actor / payload / source_created_at
  • 聊天消息已 1:1 覆盖，孤儿与重复为 0

desktop 电脑节点 核心

节点配对、在线状态、审批后的电脑操作、微信桥事件、审计。

  • /desktop/nodes/ws、/desktop/wechat/events
  • 统一异步 exec：run_remote_command

presence 在场 有风险

心跳、内心念头、主动触达预算，以及每小时 B站刷视频分享。

  • POST /presence/bili/share 手动触发
  • bili 分享走 scan → 多模态判图 → 微信图+文

proactive_chat 主动 核心

主动策略、提醒任务、到期处理，先发微信再记录 App。

  • 预算、静默、去重门禁
  • 已接入统一事件流

memory 记忆 核心

长期记忆抽取、索引、召回、后台任务恢复。

  • Job 状态持久化 background_jobs
  • 召回最多 8 条进上下文

voice 语音 核心

ASR、TTS、语音文件、过期音频清理。

  • /voice 路由 + 设备流式识别
  • 清理循环可配间隔

devices 设备 核心

配对、连接、设备语音、声纹录入与校准。

  • 声纹只用于称呼，不是授权

mobile_agent 手机 Agent 有风险

手机配对、命令下发、技能执行、微信通道回调。

  • /mobile-agent
  • 依赖 Android 无障碍服务

stickers 表情 核心

表情资产、向量检索、按意图生成、发送。

  • 生成任务 + embedding 回填

letters 每日来信 核心

来信证据、生成、配图、发布、阅读状态。

  • 每日生成 + 到点发布循环

relationship 关系 核心

相处方式、熟悉阶段、关系信号、亲昵边界。

  • 用户显式选择朋友 / AI 恋人

persona 用户偏好 核心

用户的称呼、偏好、引导数据，不是助手人格。

assistant_persona 助手人格 核心

Echo 固定人格与版本（echo-persona-v4）。

auth 认证 核心

手机验证码、JWT access/refresh、令牌族吊销。

  • 刷新令牌 hash 存储

push 推送 核心

推送目标、通知 Outbox、发送与重试（Getui）。

releases 版本发布 核心

手机应用版本、发布、下载地址。

firmware_releases 固件 低频

设备固件版本数据与查询。

study_focus 专注 模块

专注记录、完成反馈、专注证据。

system 系统 核心

健康检查、版本信息、一键重置陪伴数据。

四、核心执行链路

按真实代码路径整理，括号里是落库位置。

1. App 聊天（异步队列）

POST /chat/messages写 chat_messages + chat_turn_jobs→ chat workerprocess_turns 轮询→ build_chat_context记忆/摘要/关系/历史→ DeepSeek多模态 + 工具选择→ complete_turn拆分 deliveries→ SSE chat.delivery.createdApp 渲染

回复按段拆成多条 assistant 消息，写 conversation_events（message / app_chat）。

2. 微信收消息

微信窗口叶子会话→ bridge watcher1s UIA 读列表 + 左右判断归属→ 攒批 flush文本合并 / 图片下载原图→ POST /desktop/wechat/events带 created_at→ generate_chat_reply同步一轮→ /send_many逐条发回微信

写 chat_messages（channel=wechat）+ conversation_events（source=wechat，source_created_at=原始时间）。

3. Echo 主动发微信 / 分享

决策工具调用 / 主动策略 / B站分享→ exec 提交agent 返回 job_id→ job_result 轮询done / failed / missing→ bridge /send_imagepath + text，常驻实例→ 微信图 + 文

图片只传 VM 本地路径（C:/EchoComputer/images），base64 不进命令行。

4. B站每小时分享

bili worker每小时 / 手动触发→ /bili_scanPlaywright 刷 10 个视频 + 截帧→ 多模态判图DeepSeek 看图给 score + note→ ≥6 分才分享最多 2 条→ /send_image帧路径 + 话术

瓶颈 扫描输出 4–5MB 走 job output，慢且脆。

5. 主动消息（proactive）

presence tick念头 + 预算→ proactive job门禁：静默/预算/去重→ 生成正文安全事实注入→ persist_delivery写 App 历史→ 微信发送/send

已补写 conversation_events（source=proactive）。

6. 工具调用（Agent loop）

模型返回 tool_call名称 + 参数→ 门禁 + 执行ToolExecutionContext→ 结果回填AgentToolResult→ record_tool_callagent_tool_calls→ 写事件conversation_events / tool_call

工具事件已接入代码，但还没有真实调用数据。

六、当前卡点 / 风险

按优先级排；P0 是现在真正卡住体验的，P1 是可用的但脆弱，P2 是优化项。

P0 微信 UI 自动化稳定性

bridge 依赖微信窗口的 UIA 控件树。微信白屏/最小化/掉线时读不到消息列表，文本消息会延迟甚至漏读；恢复后补读可能一次涌进多条。本次两次归属错配都是这个根因。

VM: wechat_bridge.py · ChatTextItemView 读取 / ensure_window

P0 微信发送依赖常驻实例

白屏时 /send_image 会卡到 Invoke-RestMethod 超时（120s），后端只能看到「操作超时」。重启 EchoWechatBridge 任务能恢复，但没有自愈。

VM: _send_image / _get_wx · 后端: bili_share_worker / wechat_events

P1 B站扫描 payload 太大

一次扫描回传 4–5MB（10 张帧 base64 全走 job output）。虽然能过，但慢、占内存，且对 WS/agent 缓冲敏感。

wechat_bridge.py: _bili_scan · bili_share_worker: _scan_videos

P1 微信文本没有精确原始时间

UIA 文本行没有 local_id，只能记 bridge 发现时间（误差 1–2 秒）。图片已经用微信 create_time，文本还差这一层。

wechat_bridge.py: _check_once / _maybe_flush

P1 事件流还有三个口子

tool_call 还没有真实数据；deliver_external_assistant_message 未接事件；图片/表情的 content_parts 未进 payload。

conversation_events · chat/public.py

P1 压缩机制未实现

事件表已经统一，但裁剪/摘要/预算策略还没写。目前只有「24 条触发摘要、保留 12 条」这一层。

chat/infrastructure/conversation_summary.py

P2 固定窗口，没有 token 预算

历史固定 20 条，不按 token 预算动态裁剪；长文本、图片消息多时上下文会偏大。

chat/infrastructure/context_builder.py · MAX_HISTORY_MESSAGES=20

P2 文本归属靠 UIA 左右位置

图片已按字节数 + 发送后标记 seen 严格过滤；文本仍靠 x 坐标判断左右，极窄窗口/特殊布局可能误判。

wechat_bridge.py: _check_once / self_side

P2 8899 bootstrap 服务不自动拉起

VM 更新用的 8899 文件服务在电脑重启后会掉，redeploy 报「无法连接到远程服务器」；需要重跑 launch-echo.ps1 或手动启动。

launch-echo.ps1 · vm/redeploy-bridge.ps1

七、本次会话完成

统一异步 exec 轮询 三个调用方合并成 run_remote_command；修掉「等 completed 永远等不到 done」的 8 分钟超时；补 exit_code 与非 json 判断。
B站分享改成图 + 文 bridge 返回帧路径，后端走 /send_image（path + text），base64 不进命令行；不再污染聊天历史。
图片归属过滤 发送后按原图字节数把消息标记 seen 并持久化；TTL 时间窗改为最近 200 张永久匹配，解决 UIA 掉线半小时后的补读误判。
多模态判图 帧直接以 image_url 交给 DeepSeek，一次调用输出 score + 分享话术，去掉独立视觉模型和二次文本生成。
启动竞态 bili 循环启动时等待 echo 节点上线，最多 180 秒，不再必然首轮失败。
统一事件流 新增 conversation_events，接入聊天、工具、分享、主动消息；回填历史并修正 source 与原始时间。
