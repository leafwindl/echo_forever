# Echo 自然陪伴设计讨论：关于她、分段、主动聊天与表情

日期：2026-10-27  
状态：讨论稿，供用户审阅；没有修改业务代码、运行提示资产、配置、数据库或客户端。  
依据：当前用户要求、[后端架构与代码规范](../doc/Echo%20后端架构与代码规范.md)与本次静态阅读的实际实现。

本次修订：展示项直接使用“关系”；关系进入下一阶段由 Echo 在自然对话中主动提出；自然主动聊天每经过半小时允许联系的时间提高一档概率；增加首页与安装包版本一致的发布验收。聊天分段与表情包方案保持上一稿内容不变。

## 1. 建议采用的整体方向

Echo 保持轻快好奇、傲娇甜软的 AI 陪伴人格。用户打开应用就能相处，不必先调出一套“适合自己的机器人参数”。

前台精简为“关于她”的关系与相处记录。后台使用少量内部策略维持自然变化：

| 能力 | 概率适合决定什么 | 必须先满足的条件 |
| --- | --- | --- |
| 主动聊天 | 在合适的时间里，这次是否值得主动开口 | 没有打扰边界、没有连续未回复、当前有自然的交流理由 |
| 聊天分段 | 已经写好的内容，在哪些自然边界分成气泡 | 句子与语义完整，不拆坏引用、列表、代码和颜文字 |
| 表情包 | 这一轮是否更值得考虑用图片表达 | 情绪和语境合适，实际图库有匹配图片，模型愿意这样表达 |

三者分别判断，不共用一个“活跃概率”。一次没抽中不需要补偿；长时间没使用某项能力，可以逐渐增加合适机会中的倾向，但不能越过语境与用户边界。

**建议落点：主动聊天用渐增的触发机会；分段用语义优先、按句兜底、边界随机；表情包用渐增的软提示机会，保留主模型的最终选择。**

以下数值都是说明机制的候选参数，不是已经配置或验证过的默认值，不展示给用户。

## 2. “关于她”：让用户看见关系，不用管理人格

### 页面保留什么

复用现有头像、名称与关系卡片，页面主体可以收敛为：

```text
关于她

Echo · AI 陪伴伙伴

关系        朋友
互动        128 次
活跃        12 天

                         重置关系
```

上面数字与关系文案仅用于示意，不是读取到的用户数据。真实页面只展示真实记录；不添加好感排行榜、升级倒计时或“再聊几次解锁恋人”的提示。

移除本页的称呼输入、聊天方式、亲昵强度、关系节奏、个性化开关、恢复默认设置和朋友／AI 恋人选择器。取消独立的主动聊天频率设置页。

账号、设备、应用更新和用户明确建立的提醒仍有各自用途。应按实际入口保留必要功能，不能因为删去两个设置页而顺带删掉这些能力。定时任务管理需要从原主动聊天页迁到可达的现有入口，或者通过聊天查看、取消，不能留下不可管理的任务。

### 关系怎样自然发展

熟悉与好感主要来自持续交流、共同经历、表达被理解和彼此形成的默契。消息数与活跃天数只是证据的一部分，不能刷几百条重复消息就得到一段深厚关系。

- 关系发展由相处积累推动，页面只展示结果，不提供切换按钮。
- 朋友也可以非常亲近，AI 恋人不应成为所有用户必须到达的最高等级。
- 好感与熟悉度影响靠近的节奏；恋爱方向还要看实际对话中是否持续出现并被接受的亲密意愿，不能仅由分数自动宣布。
- 关系转折可以在聊天里自然发生，不设计额外的关系选择弹窗或购买解锁。
- 主动消息没人回复，也不作为关系降级依据。

### 下一阶段由 Echo 自然主动提出

相处积累足够、近期互动也支持更进一步时，系统只提供一个内部的“可以考虑推进关系”的机会。Echo 找到自然的话题位置主动表达，页面不能在后台分数越线时直接跳到下一阶段，也不让用户去设置里切换。

建议流程为：

```text
共同经历与相处积累支持下一阶段
  → 确认当前没有拒绝亲密、只做朋友或暂停相关话题的边界
  → 在适合的对话里，由 Echo 用自己的语气主动提出
  → 用户自然回应，结合上下文理解是否接受
  → 接受后保存关系变化，“关于她”直接展示新的关系
```

“主动提出”指她主动把心意说出来，不要求另发一条后台消息。优先接在轻松、亲近的真实交流中，不在用户处理报错、认真办事或难过时突然切入。若通过后台自然联系开口，仍遵守主动聊天的时间、概率与未回复规则，不额外插队。

措辞示意如下，仅用于评审感觉，不作为固定台词或常驻 Few-shot：

| 情境 | Echo 可以怎样主动提出 |
| --- | --- |
| 已经从办事往来积累出日常熟悉 | “我有点想当你的朋友了。以后没正事，也来找我聊聊呗？” |
| 双方已有持续、被接受的亲密互动，她想更进一步 | “这次我先开口好了……要不要试着和我谈个恋爱？” |
| 用户回应“先做朋友吧” | “好，就做朋友。咱们还按舒服的方式聊。” |

不使用“好感度达标”“检测到关系升级条件”“是否确认进入下一阶段”等系统口吻。不汇报她为什么被算法触发，不要求用户点击同意按钮。

用户明确接受后再更新展示；玩笑、引用、含糊回答和沉默不直接算接受。她可以继续自然交流，不把一次提议变成连续追问。用户拒绝或暂缓后，不因下一次半小时概率增长再次提同一个关系请求；需要有新的实际相处依据，且用户边界已允许，才重新考虑。

“下一阶段”是有意义的关系转折，不是每次后台熟悉度小幅增加都办一次升级。朋友、暧昧、恋人、家人等称谓也不组成每个人必须走完的固定流水线。

称呼和表达偏好仍可以在正常聊天中形成，例如“以后叫我小叶”。删除表单不意味着删除已经表达过的偏好；真正影响后续行为的明确边界，应由业务状态可靠保存，不能只期待一次记忆检索碰巧命中。

### 三项展示的含义

| 展示项 | 建议口径 |
| --- | --- |
| 关系 | 朋友、暧昧、恋人、家人等可理解状态，不显示精密好感分数 |
| 互动 | 一次用户输入批次与一次 Echo 回应算一次交流；回应拆成四个气泡仍算一次 |
| 活跃 | 用户确实参与交流的本地自然日数；Echo 单方面主动发消息不增加活跃天数 |

这能避免分段越多，好感与互动数字涨得越快。活跃日期应统一按用户时区计算，不以服务器 UTC 日期代替用户当天。

页面不再单列“熟悉程度”。熟悉度与好感仍可作为内部发展依据，关系一项显示当前实际成立的相处关系；Echo 还没有提出或用户尚未接受时，不提前显示下一阶段。

### 底部重置关系

保留现有二次确认。建议语义为：熟悉进度与由相处形成的亲密阶段回到初识，清空所有历史，明确的拒绝与称呼边界继续尊重。

若当前显示 AI 恋人，重置后也应回到重新相识的关系展示，不能同时出现“初识”和已经确定的恋人状态。这个建议不同于当前“重置进度但保留手选关系类型”的实现，实施前需要统一确认文案、关系状态与记忆使用方式，避免旧关系叙述立即把状态拉回去。

保留的记忆可以描述曾经的相处，但不能自动成为重置后的现任关系或当前亲昵许可。

## 3. 主动聊天：等待增加机会，未回复降低打扰

### 用户看到什么

取消保守／均衡／积极等频率档位，不告诉用户“每隔几小时找你一次”。她在适当的时候偶尔发起交流：可能续上有意义的近况，也可能只是一个轻松的开场。

首次使用时可用一句产品说明交代：Echo 偶尔会主动找你，你可以直接告诉她暂时别打扰。无需新增频率配置流程。

用户可以在聊天里说：

- “这两天别主动找我。”——按这段时间暂停自然主动联系。
- “以后别主动发消息了。”——持续停止自然主动联系。
- “你可以主动找我聊。”——恢复自然主动联系。
- “工作日上午别打扰。”——保存明确的时间边界。

必须真的改变后台行为，不能只回复“好”。取消频率页面后，这些指令的可靠执行比增加更多概率参数更重要。操作系统的通知权限仍单独控制通知展示，不能拿“关了推送”代替停止生成主动消息。

### 三种联系不能混成随机提醒

| 类型 | 建议 |
| --- | --- |
| 用户明确要求“明早九点提醒我” | 按约定执行，不抽签决定发不发；尊重用户对时间与提醒的明确要求 |
| 有真实背景的重要事件回访 | 时间与话题仍相关时优先考虑，允许用户不聊；未确认发生的事件不当作已完成 |
| 没有明确约定的自然闲聊 | 使用渐增概率，抽中后仍可以因为没有合适话题而跳过 |

“不要主动找我”默认停止 Echo 自发联系；用户另行明确建立的提醒按其请求处理。用户说“把提醒也停了”时再处理相应任务，不擅自扩大指令范围。

### 一次主动联系的判断顺序

```text
是否允许联系
  → 是否处于安静时段、明确忙碌、正在对话或已有待交付消息
  → 是否连续主动发出后没有得到回应
  → 是否到达一个尚未评估的半小时档位，使用该档位的概率进行一次判断
  → 进入已有主动聊天规划／生成链，判断这次能说什么
  → 有自然内容才交付；没有则略过这次机会
```

时间只是增加开口机会，不自动提供一个值得开口的话题。不能因间隔久就反复发“在吗”，也不能为了有话说虚构她一直在后台惦记、阅读或等待。

### 概率如何随时间变化

明确采用**每半小时提高一次概率**。以最近一次真实交流结束或成功自然联系之后的周期为起点，累计允许联系的时间；每满 30 分钟进入下一档。不是在手机时钟的每个整点或半点固定发消息。

一份便于评审的数值示意如下。半小时的增长单位已经按本次要求确定；起始概率、每档增量与上限仍是候选参数，需要后续体验校准，不显示在 APP 中。

| 本周期已累计的允许联系时间 | 本档触发机会示意 |
| --- | --- |
| 刚结束交流 | 不立即另起后台问候 |
| 30 分钟 | 10% |
| 60 分钟 | 15% |
| 90 分钟 | 20% |
| 120 分钟 | 30% |
| 150 分钟 | 40% |
| 180 分钟 | 50% |
| 之后每满半小时 | 继续提高5%，示意上限为 90% |

每个半小时档位最多判断一次，抽中后进入已有主动规划／生成链，最终仍可因话题不合适而略过。没有抽中或没有发送，下一个合适的半小时再按新档位判断，不在同一档反复重抽。

上述示意中，前六档都适合联系且不受其他因素降低时，三小时内至少抽中一次候选机会的概率约为 35.56%。这是进入规划的机会，不保证一定生成消息，也不承诺三小时必发。

安静、禁止打扰、正在处理对话等不适合联系的时间不推动档位。用户回来真实交流或一次自然联系实际发送成功时结束旧周期；成功发送但未回复后，下一周期使用更保守的机会，不把“又过半小时”当成继续催问的理由。

后台可以每分钟检查任务，但同一半小时档位仍只判断一次。服务重启保留周期与已评估档位，错过的档位不补抽，避免重启、轮询加快或早晨恢复时突然提高发送频率。具体状态与去重要求见附录。

### 等待与未回复必须方向相反

| 观察到的情况 | 后续倾向 |
| --- | --- |
| 正常交流后过了一段允许联系的时间 | 自然联系机会逐渐提高 |
| 刚结束聊天，用户正在持续输入，或正在处理一条回复 | 不另起一个后台问候 |
| 自然主动发过一次，尚未得到回应 | 降低机会，不继续沿用“越久越积极”的增长 |
| 连续两次自然主动联系没有回应 | 建议沿用当前暂停保护，等用户回来再恢复 |
| 用户明确说晚安或暂停打扰 | 相应时段不主动联系，不靠随机绕过 |
| 用户重新参与聊天 | 结束之前的未回复周期，从新的真实交流状态重新判断 |

“未回复”只描述产品收到的消息事实，不推断用户已读、厌烦、在线或有空。不确定用户是否在忙时，不编造这些状态；使用温和默认节奏。

关系更亲近主要影响措辞与共同话题，不自动等于应该更频繁地打扰。

安静时段可以先沿用目前 22:30—08:00 的产品默认与已有明确偏好。夜间不把“联系冲动”累积到早晨一次释放，恢复时也不准点补发所有过期问候。自然闲聊过时就作废，有约定的提醒单独按任务语义处理。

后台重启、任务重试和网络重连不能重新抽签直到抽中，也不能把同一次联系发成多条。概率周期、实际交付结果和任务幂等需要一致。

## 4. 聊天分段：完整句子可以有不同的组合

### 分段要增加节奏，不增加内容

不要求每次都是一两个气泡，也不要求偶尔必须刷出四五条。一次简短回应可能一条；包含接梗、补充和柔软收尾的回应，可以自然形成三四条。前提是本来就有这些内容。

普通闲聊先控制信息量，只讲当前值得说的内容。用户要求详细说明时，必要内容应完整提供。不能将一篇不必要的小作文拆开，就算解决了聊天过满的问题。

### 推荐的分段流程

1. 优先保留模型主动给出的自然段落。
2. 对仍然挤在一段里的普通聊天，找完整句末、语气转折和独立回应点；短文本也可以有候选边界，不必等到 180 字。
3. 合并语义依赖明显的部分，保护引用、代码、列表、表格、数字、链接、括号和颜文字。
4. 在剩下的自然边界中，允许概率决定“这一处合在一起，还是下一气泡再说”。
5. 如果模型总不给明确段落，可以先用按完整句子拆分的兜底，不额外调用一个分段模型；再合并不适合独立成条的片段。

“嗯”“啊？”等短反应如果本身有独立语气，可以单独发。不能用最低字数一律合并，也不能把每个逗号都切成一条。

### 概率应用在哪里

| 候选位置 | 倾向 |
| --- | --- |
| 独立观点结束、转到另一个完整回应点 | 较容易断开 |
| 先轻轻打趣，再软一点补充 | 可以保留一个小停顿 |
| 一个因果、解释或条件句的中间 | 更倾向合在一起 |
| 引用、代码、列表、链接、颜文字内部 | 不随机拆开 |
| 最近合适的多句闲聊总被合成一条 | 小幅提高已有自然边界的断开倾向 |
| 已经形成多条短气泡 | 减少继续碎切的倾向 |

不要为每个标点独立地高概率抽签，否则很容易变成消息轰炸。一次回复可以先选择偏连贯或偏轻快的组句倾向，再据此组合已有句子。选择的倾向不会改变她的稳定人格，也不是一套新的情绪模拟系统。

最近总是单气泡，可以让下一次**有多个完整意思**的回复更容易分开；如果这次只有“好呀”，仍然只发这一句。

### 示例：同样的内容，不同的消息组合

前提：用户之前确实说过“想把项目删了”，现在告诉 Echo 终于修好了。

原本值得说的内容：

> 行，今天这声天才我喊。刚才还说要删项目呢，现在又开始得意了。不过这一下，确实该开心。

较连贯时，可以分成两条：

> 气泡 1：行，今天这声天才我喊。  
> 气泡 2：刚才还说要删项目呢，现在又开始得意了。不过这一下，确实该开心。

偏轻快时，可以分成三条或四条，在“现在又开始得意了”与柔软收尾之间留一点节奏。两种组合都不新增内容，不能为了达到四条再补一句追问。

这些只是设计示意，不是准备重新常驻注入的闲聊 Few-shot。

### 发送间隔

先有内容，再做展示：首条已经准备好的内容及时显示，之后依内容长度设置短间隔，允许小幅随机变化，并限制整组额外等待。

复用当前“额外等待总计不超过三秒”的方向。不能为了像真人而多等十几秒，也不能以打字间隔掩盖模型生成延迟。分段数量只统计文字气泡，图片不算额外文字句子。

## 5. 表情包与颜文字：久未使用时增加合适机会，不形成欠账

### 图片与颜文字是表达选择

轻快、得意、害羞、庆祝或轻微委屈时，图片或颜文字可以增加语气。严肃、明显悲伤、用户设定边界时，优先回应本身，不因许久没发图就插一张可爱图片。

画像不能简单复制用户情绪。用户说“烦死了”，Echo 可能是在陪对方吐槽、表达无奈，也可能要认真安慰；检索意图应来自她此刻想表达的态度与对象。

### 推荐使用轻量的“考虑机会”

在现有“主模型自主调用表情工具”的基础上，概率只决定：这一轮要不要给主模型一个很短的、可忽略的考虑提示，例如“若贴合当前表达，可以用图”。

| 情况 | 考虑机会如何变化 |
| --- | --- |
| 轻松闲聊、有明显适合图片的表达点 | 比普通事实问答更容易考虑 |
| 最近已经有许多适合的轻松回合，却没有使用图片 | 小幅提高下一次合适机会的倾向，设一个温和上限 |
| 最近刚用过图片 | 回到基础倾向；仍可因语境需要继续使用，不禁用工具 |
| 连续几天都是严肃话题 | 不累积“必须补发表情”的压力 |
| 没有合适图片，或主模型认为文字更好 | 不发图，不当作失败，不立即重抽 |
| 用户明确说“发个开心的表情” | 正常执行明确请求，不经过这层随机机会 |

这里的“很久没用”优先按**有机会但未用的轻松互动**理解，不按单纯的墙上时间计算。没有聊天的两天不会让用户下一句话必带表情。

抽中的是考虑机会，不是发送命令；没抽中时工具仍然存在，主模型仍可因上下文自主使用。实际发图率因此不等于这个概率，需要用真实日志和体验观察校准。

不额外增加逐轮情绪分类模型，不重新引入工具隐藏、发图冷却、近期图片降权或固定“每几轮必须一张”。这些都不属于本方案的概率机制。

### 怎样避免文字、颜文字和图片一起用力过猛

同一个情绪优先选择一种主要表达。已经有一张贴切的害羞图，文字可以简单一点；用一个颜文字足以表达得意时，也不需要再配一张同义图片。

这不是“最多只能有一个”的新硬限制。强烈的庆祝或自然斗图可以更丰富，但要来自具体互动，不成为每轮默认组合。图库无匹配就回到文字，不能从无关图片里随机找一张交差。

### 图片的位置与真实交付

第一版继续使用当前图片前置／后置能力。对连续几个气泡，图片放在真正完成对应态度表达的位置；如果现有协议只能放在开头或结尾，就在这个能力范围内选择，不假称已经支持任意气泡间插图。

只有真实工具执行成功，才计为使用并保存图片附件。抽中考虑机会、搜索过图片、生成过发送意图，都不等于图片已经发给用户。文字和内部情绪标签继续分开，颜文字作为正常文字保留。

## 6. 三种机制一起使用时

### 情境 A：用户来闲聊

用户：“终于忙完了，来找你说两句。”

Echo 按人格正常接话。若有独立的轻快反应与柔软补充，可以分成两三条；适合时选一个颜文字或图片。用户此刻已经参与交流，后台自然主动联系应让出位置。

### 情境 B：用户离开较久

在安静时段以外，随着允许联系的时间推移，开口机会增加。若已有真实的共同话题，可以自然回访；如果没有可说的内容，本次仍可略过。

主动消息发出后没回复，后续联系倾向降低。分成三个气泡的一次主动消息仍只算一次联系，不能拿分段绕过未回复保护。

### 情境 C：很久没发图，用户今天很难过

这次优先认真回应。图片机会不补发，熟悉度也不强迫她撒娇。等以后出现合适的轻松互动再考虑图片。

### 情境 D：回复本来只有一句

用户：“好，那就这样。”

Echo 可以只回一句。即使最近一直是单气泡，也不补几句话，不自动加表情，不制造新的聊天任务。

## 7. 与当前项目的差异及后续落点

本次读取的是 2026-10-27 的工作区。此前文档里描述的 v2 Few-shot、表情冷却和单轮一张限制，后续已经调整；不能把 10 月 20 日的实现快照当成当前状态。

| 当前实际入口／行为 | 若采用本文，后续要改变什么 |
| --- | --- |
| Flutter `persona_page.dart` 与 Harmony `Index.ets` 有关系选择器和偏好表单 | 精简为“关于她”；保留只读关系、三项统计与重置入口，连同首次引导中重复的偏好填写一起审查 |

| 主动聊天页包含频率、时段与多个开关，任务管理依附此页 | 移除频率控制，保证提醒管理仍可达；将“暂停／恢复联系”接入正常聊天的可靠业务执行 |

| 当前表情工具由主模型自主选择，无发图冷却与近期图片降权 | 只加入可选的机会倾向，保持工具可用，不增加辅助情绪模型与强制发送 |
| 共享提示实际位于 `shared/prompting`，已有规则资产由真实链加载 | 若增加条件提示，在实际选择与渲染链同一变更接入，按规则／上下文／输出格式归属；不另建未加载的资产库 |

这里只记录实际修改落点，不预建新 feature、表、API 或空注册。概率参数是产品内部少量参数，不把被移除的用户设置换成另一套复杂配置系统。

### 旧数据如何处理

- 已经明确关闭自然主动聊天的用户继续保持关闭，不能因设置页消失而重新开启。
- 如果无法区分“历史默认关闭”和“用户主动关闭”，先保持原行为，不批量猜测用户意愿。
- 原来手动选择过的朋友／AI 恋人关系不直接清零；迁移时作为已知的相处背景保留，后续按新的发展机制更新。
- 移除编辑入口不清空称呼、明确边界、聊天记录和长期记忆。旧配置字段是否退出，应先检查客户端、首次引导、任务和其他消费者。
- 不再使用的频率档位不能在后台偷偷继续控制节奏；正式迁移时应一起整理读取、写入和说明，而不是只删界面。

当前规范第 4.1 节仍规定手动选择关系。本文是用户提出的新设计方向；若确认实施，需要同步更新规范、运行合同和消费者。本轮没有改动规范或既有行为。

## 8. 按奥卡姆原则，第一版做到哪里

建议顺序：

1. 精简“关于她”和频率入口，直接展示关系、互动与活跃；明确 Echo 主动提出关系转折以及用户自然回应后的状态更新，保留旧偏好及重置语义的审查。
2. 先改善短多句回复的分段：自然换行优先，按句兜底，少量边界变化；不增加模型调用。
3. 将自然主动聊天改为每半小时递增一档的触发机会，每档只判断一次，未回复时收敛；把暂停／恢复指令接入真实状态。
4. 最后加入表情的软机会倾向，验证它是否改善了使用感。如果主模型已经自然使用，或者短提示没有收益，就不保留这层额外机制。

先不做长期情绪模拟、自主内心活动、完整关系游戏、全新提示资产选择引擎或自学习多臂老虎机。当前只需要把三个已有能力协同好。

## 9. APP 更新：主页显示与实际安装版本一致

每次更新 APP 都同时核对首页版本显示、构建配置、安装包内版本与设备实际安装结果。首页不能使用一份容易漏改的独立固定字符串；应优先读取当前已安装包的真实版本，相关构建和请求元数据也应来自一致的版本来源。

本次静态检查发现一个实际落点：鸿蒙 `Index.ets` 的首页工具栏仍写着 `v1.1.7`，`AppScope/app.json5` 与 `AppConfig.ets` 已为 `1.1.8`。这里只记录为后续修复项，本轮没有修改这些代码。Flutter 首页当前使用已安装版本 Provider，更新时仍要核对真实安装结果。

后续发布检查包括：

1. 确定本次版本名，以及各平台各自递增的构建号；Android 与鸿蒙的构建号不要求数值相同。
2. 核对鸿蒙包配置与实际使用的版本配置、Android 构建版本及必要构建注入，避免只改一处展示文本。
3. 构建后检查 APK／HAP 包内版本信息，与目标发布版本一致。
4. 默认通过 USB 同签名覆盖安装：鸿蒙走现有 `harmony_app/scripts/install-usb.ps1`，Android 走对应 adb 覆盖流程；不自动卸载、清数据或改签名。
5. 覆盖安装后打开首页，核对显示版本与系统实际安装版本一致；若此次会更新服务端发布记录，其元数据也必须对应同一个安装包。

## 附录：半小时档位的计算与去重

第一版采用离散半小时档位，替代上一稿可选的连续累计机会方法，不同时维护两套触发算法。

```text
档位 k = 本周期累计的允许联系分钟数整除 30。
当 k >= 1 且该档位尚未评估时，按本档概率只判断一次。
示意基础概率 p(k) = min(2% × k, 20%)。
实际判断可结合时段、话题依据和未回复状态降低机会；禁止联系时不判断。
抽中只获得进入主动规划／生成链的机会，真实发送仍取决于当前内容与交付结果。
```

这里 2% 的增量和 20% 的上限只用于说明半小时递增机制，不是已经确定的上线参数。若使用语境权重，它只是内部产品权重，不伪装成模型校准过的置信概率。

可靠保存当前周期与已评估档位，原子地认领一次判断。多个 Worker、服务重启、任务重试或网络重连都不能使同一档位再次抽签。即使增长已到上限，每个新的半小时仍有自己的档位，只评估一次。

错过多个档位时，不为每个历史档位补抽；恢复后最多按当前有效档位判断一次。安静时段及明确禁止打扰的时间不推动档位；恢复允许联系后继续按有效时间累积，不能把整晚直接换成高概率。

模型判断无合适内容、图片或消息交付失败，都不能被当成成功联系；也不能因此在该半小时反复重新生成。技术失败按原任务身份和幂等语义处理，发送前仍检查最新用户状态，不创建新随机机会绕过限制。

用户真实交流或成功自然联系后结束旧周期；如果发出后尚未得到回应，新的周期降低机会，达到连续未回复暂停条件就停止。用户界面不展示概率、档位或倒计时。
