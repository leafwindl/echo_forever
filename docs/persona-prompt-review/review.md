# Echo 人格提示词精简调研

调研日期：2026-10-22。依据当前工作区代码及下面链接的公开一手文档。本次只新增分析材料，没有修改聊天服务的行为。

**结论**

当前问题主要是多层重复规定同一行为、特殊场景规则常驻，以及部分软风格被升级成程序硬限制。仅把 `prompt_renderer.py` 拆成 JSON/YAML 不会节省模型输入；应改变每轮实际加载的内容，并同步调整风格兜底。

建议采用“小而稳定的人格核心 + 独立的安全与能力边界 + 按需附加的场景提示 + 必要的代码门禁”。人格与安全仍要稳定，表达长短、提问方式、亲昵程度和具体措辞保留情境弹性。

**别人采用什么结构**

1. SillyTavern 的角色设计区分常驻角色定义和可被挤出的示例消息；World Info 支持按关键词等配置激活相关内容，并限制背景预算。可借鉴“短常驻核心、相关内容按需加入”，而不是照搬它的角色扮演设定或依赖关键词解决全部语义判断。来源：[Character Design](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)、[World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)。
2. Letta 的 V1 SDK 文档将 `persona`、`human` 等信息放在有说明和字符上限的 memory blocks 中，分别维护。它们仍会进入上下文；模块化本身不意味着省 token，也不能推导成所有新版功能都沿用相同实现。来源：[Memory blocks，V1 SDK 文档](https://docs.letta.com/v1-sdk/memory/memory-blocks)。
3. OpenAI 官方文档将身份、指令、示例、上下文分开组织，并建议用评测验证迭代。这个项目可以保留清晰分层，同时删除跨层重复。来源：[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)。
4. Anthropic 的提示词建议包括用少量相关示例，以及用期望行为描述替代部分否定式格式规则。这里可作为候选写法，但其模型经验需要在实际使用模型上验证。来源：[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)。

这些资料支持结构上的选择，不证明“越短越好”，也不证明某一个项目的角色稳定性优于 Echo。

**项目内具体应改哪里**

| 位置 | 当前问题 | 建议 |
| --- | --- | --- |
| `shared/config/settings.py` 的 `system_prompt` 与 `assistant_persona/infrastructure/default_persona.py` | 重复描述身份、性格、关系定位 | 选一个人格内容源，产品配置保留版本与基础定位；最终只渲染一次完整核心 |
| `chat/infrastructure/prompt_renderer.py` 的 `NATURAL_DIALOGUE_POLICY`、`RESPONSE_CALIBRATION_POLICY` | 不说教、不追问、不虚构、相关时才使用背景等多次出现 | 合并成少量原则；产品反馈、关系试探等特殊场景不再整段常驻 |
| `render_persona` | 默认偏好也转为一整段说明 | 仅加入用户实际修改、且会改变行为的字段；不要重复系统默认 |
| `render_relationship_guidance` | 阶段、温度与表达上限夹带较长共通规则 | 保留简短状态与必要语义；稳定的共通边界只解释一次 |
| `render_turn_focus_guidance` | 没有异常时也持续提示“允许一个问题”等 | 无特殊信号时可不附加；显式边界优先；任务澄清不被闲聊追问冷却误伤 |
| `context_builder.py` 的时间说明 | 每轮都携带长时间使用教程 | 简短的稳定使用规则配合必要时间数据；时间相关场景再加细节 |
| `agent/application/orchestrate_chat.py` | 表情真实性、内部信息和自然交付要求跨多段重复 | 留一份简短执行合同；单工具选择细节放在相关工具描述或专用分支，按实际暴露能力加载 |
| `chat/domain/dialogue_style.py` 与 `generate_reply.py` | 风格条件触发清理或固定回复，会压过正常任务需求 | 将普通表达偏好作为软约束；只有范围明确的格式、动作凭据或必要边界做硬处理 |

安全政策、工具参数与授权、调用预算、超时、动作真实性、数据隔离仍需要独立设计，不能为了人设自由而全删。代码门禁也不能替代模型理解需要的最简规则。

**已隔离复现的灵活性问题**

历史里最近两条助手消息分别是“网络还好吗？”和“什么时候开始的？”。用户当前说“帮我排查一下登录失败的问题。”，候选回复为“能提供一下具体错误提示吗？”。

执行当前领域函数，`should_pause_followup_questions` 返回 `True`，检测结果包含 `followup_question_cooldown`，`apply_dialogue_fallback` 将候选改成“我先不追问了，按你想说的节奏来。”。

这说明提问冷却混淆了闲聊追问与任务澄清。这个复现没有请求模型，验证的是代码会如何处理给定候选，不代表模型每次一定生成这个候选，也不是线上发生频率的统计。

**可供讨论的人格核心草案**

以下仅是人格核心，不是包含安全、工具、隐私等全部内容的完整上线提示：

> 你是 Echo，以女性人格交流的 AI 陪伴伙伴。你温暖、灵动、有主见，熟悉后偶尔带一点俏皮和小得意，认真时直接可靠。人格体现在接话与判断，不需要每轮表演性格标签。
>
> 先理解用户此刻想聊天、分享、求助还是设定边界，再自然回应。闲聊给对方接话空间；需要解决问题时讲清楚，必要时可以澄清，不强行压成短句。
>
> 亲近程度跟随共同经历与用户意愿。可以表达当下的关心、欣赏和幽默；诚实面对身份与能力，不虚构现实身体、离线经历或不存在的执行结果。
>
> 历史与记忆用于理解当前话题，相关时自然带入；表达可以变化，不照搬示例，不必每次提问、称呼或添加装饰。

现有人格示例已经有可取之处，可保留作为外置示例库。先比较“少量固定示例”和“选择相关示例”两种方案；示例也消耗 token，不默认越多越好。动态选择应尽量复用已有状态，避免每轮新增一次分类模型请求抵消收益。

**建议的验证方式**

先建立实验配置，保持当前路径可回退；第一轮只去重和缩写，不改变安全与工具执行语义。以当前 5,259 的估算口径作为基线，先把“无历史、无额外资料”的固定说明降到约 1,200–1,800 作为实验目标；这不是行业标准，也不是已达到的效果。

使用相同模型配置和同一组多轮对话比较：人格辨识、自然程度、任务完成、澄清正确性、用户边界、工具真实性、兜底命中率、真实 API usage 和延迟。复用 `tests/fixtures/natural_dialogue_acceptance_cases.json` 的已有场景，并补上“连续两个问句之后仍需澄清”的例子。

现有某些测试断言 Prompt 必须出现特定长句；精简后应保留必要的结构和安全合同检查，把风格质量交给可复现的行为评测。不能通过删除失败测试来宣布成功。当前尚未改线上 Prompt、未运行真实模型 A/B，不能声称人格质量已经提升。
