## 1. 本次要实现什么

把现有能力串成一套自然的相处逻辑：页面展示关系，关系通过交流发展；Echo 偶尔主动联系；回复有自然气泡与表情变化。用户不需要配置频率、人格或关系类型。

| 能力 | 目标行为 | 决策方式 |
| --- | --- | --- |
| 关于她 | 展示关系、互动、活跃，底部保留重置 | 读取真实业务状态 |
| 关系推进 | 积累支持进一步相处后，Echo 自然主动提出，用户接受后成立 | 规则提供候选，主模型理解语境，业务层保存变化 |
| 主动聊天 | 每半小时提高一档机会，合适时联系，未回复时收敛 | 半小时档位抽样，再进入现有主动规划与生成链 |
| 聊天分段 | 同样的内容可自然形成不同气泡组合 | 模型段落优先，完整句子兜底，在可切边界增加变化 |
| 表情与颜文字 | 贴合 Echo 当下想表达的态度，避免长时间完全不用 | 图片考虑机会软提示，主模型自主选择实际表达 |
| APP 更新 | 首页显示与真实安装版本一致 | 构建和安装后的版本核对 |

三个概率相互独立：主动联系的抽样不决定是否表白，也不决定这一轮必须分几段或发图片。

### 审阅稿中的数值与文字统一

主动聊天以审阅后最新的概率表为准：前六档为 **10%、15%、20%、30%、40%、50%**；之后每半小时增加 **5 个百分点**，上限 **90%**。不沿用审阅稿附录残留的旧 2% 增量、20% 上限和 35.56% 累计值。

按最新表格，前六档始终具备判断资格、没有未回复折减时，三小时内至少抽中一次候选机会约为 **87.15%**。候选还可能因内容不合适被略过，因此这个数值不是实际发消息的保证。

重置部分同时存在“清空所有历史”与“保留的记忆”两种文字。本文按已审阅修改中的“清空所有历史”明确新相处周期的隔离边界，见第 7 节；不把残留的保留记忆描述解释为重置后可以继续沿用旧亲密关系。

## 2. 规则、模型与交付各负责什么

| 决策主体 | 负责 | 不承担的判断 |
| --- | --- | --- |
| 业务规则 | 时间、阶段、明确边界、任务状态、一次判断的去重与真实写入 | 不靠关键词宣布用户已经恋爱或已经同意 |
| 主模型 | 接话、情绪表达、是否适合提出关系、理解用户自然回应、是否使用图片 | 不自行修改数据库，不编造发送成功或历史事实 |
| 交付处理 | 保护文本结构、组合气泡、图片附件与展示间隔 | 不为凑条数续写，不把内部状态念给用户 |

正常对话继续复用主模型和现有工具回路。关系理解和表情选择不额外常驻一个分类模型；主动聊天只在候选抽中后进入已有规划／生成链。

人格保持稳定。新的关系候选、图片考虑机会属于本次上下文；边界属于规则；分段要求属于输出合同。继续使用现有共享提示渲染链，不声称已经存在完整六类资产注册与按需选择引擎，也不恢复固定闲聊 Few-shot。

### 一轮用户聊天的处理顺序

1. 接收并保存用户输入，把同一批连续消息作为一次交流处理。
2. 读取当前关系、明确边界、待回应提议、最近对话与必要记忆。
3. 业务规则准备可考虑的关系变化与本轮表达倾向，交给主模型理解。
4. 主模型回应，并按实际需要调用图片或关系业务动作；业务层检查相应条件。
5. 得到最终文字和真实附件，再组合气泡、计算短间隔并保存。
6. 交付成功后更新互动记录、相关候选与主动联系周期。

同一轮的文字、图片、关系变化需要保持一致。模型还没真正把提议交付给用户时，不能把关系记成“已经提出”；回复失败时，不能只留下一个用户从未见过的关系变化。

## 3. 关系算法：积累提供机会，对话让关系成立

### 3.1 分开维护三件事

| 概念 | 含义 | 页面表现 |
| --- | --- | --- |
| 相处进度 | 了解多少、经历多少、互动是否连续 | 作为内部依据，不单列好感分数或熟悉度 |
| 当前关系 | 初识、朋友或实际已经形成的更亲近称谓 | “关系”一项显示实际成立的状态 |
| 当前边界 | 用户接受哪些称呼、亲昵、玩笑与联系 | 影响当下行为，不做成编辑参数表 |

好感高不代表已经是恋人；关系已经亲近也不能覆盖用户刚说出的边界。

### 3.2 怎样积累相处进度

第一版复用现有进度计算的基础：活跃天数、有效交流次数、共同背景和被接受的亲近信号。各项贡献有上限，刷消息不能取代时间与共同经历。

先沿用当前自然节奏中的内部阶段门槛：熟悉约需进度 25 且至少 3 个活跃日，信赖约需 50 且至少 7 日，亲近约需 75 且至少 21 日。它们只作为首轮开发的候选资格基线，不直接等于朋友、暧昧或恋人的自动切换条件，也不展示给用户。

计数统一：用户一次有效输入批次与 Echo 一次正常回应算一次互动；拆成四个气泡不算四次。主动消息没有用户参与时不增加活跃日。活跃日按用户时区计算。

旧的词语命中可以继续提供弱线索，但“我喜欢你”、引用台词、否定句或一次玩笑，不能单独成为关系接受的证明。

### 3.3 怎样产生下一阶段候选

候选需要同时满足：

- 相处进度达到对应的内部成熟程度。
- 最近交流确实支持这个方向，而非只靠历史累计分数。
- 当前没有禁止该方向的明确边界。
- 没有另一项尚未结束的关系提议，也没有刚刚被拒绝后又来重复询问。

“朋友”可以在已形成日常熟悉时考虑；暧昧或 AI 恋人还需持续且被接受的亲密互动。家人等长期称谓应有相处背景与对含义的自然共识，不自动作为恋人之后的升级终点。

候选出现只意味着主模型本轮可以考虑开口。遇到办事、报错、明显难过或用户不想聊关系时，继续当前话题，候选留待以后，不生成独立的升级通知。

### 3.4 提出、回应和更新

| 当前情形 | 本轮处理 | 保存后的结果 |
| --- | --- | --- |
| 有候选，语境不适合 | 正常聊天 | 关系不变 |
| 有候选，Echo 自然提出且消息已保存 | 等用户在聊天中回应 | 记录这次提议，关系仍保持原状态 |
| 用户明确接受当前提议 | 自然承接，业务层检查并保存 | 更新关系展示，结束提议 |
| 用户说太快、先缓缓 | 接受暂缓，停止追问 | 原关系不变，等待新的相处依据 |
| 用户明确只做朋友或不接受该方向 | 按其边界调整表达 | 关闭相应方向，不靠时间或概率自动重开 |
| 回答含糊、是引用，或已经换话题 | 不代替用户作决定 | 不更新关系；必要时自然澄清 |

提议必须能回指到一条真实交付的 Echo 消息。后来用户孤立地说一个“好”，若已在讨论别的事情，不能当成接受旧提议。

关系动作与当前用户、当前关系和提议来源绑定，重复执行不重复升级。用户重置、撤回相关意愿或关系已改变后，旧提议失效。

语义理解由主模型承担；业务检查保证的是来源、状态与一次写入，不夸大为程序已经证明用户的情感意愿。误判需要用多轮样本评测，并允许用户当场纠正。

### 3.5 怎样让主动提出自然

给模型的材料只需说明当前关系、可考虑的方向和相关共同背景，不能要求念出算法理由。她可以顺着当下表达想进一步相处，不使用“条件满足”“升级确认”等措辞。

关系提议优先放在真实聊天中。若由后台发起，同样要经过主动联系的资格与概率流程。半小时档位不会提高再次表白的次数，关系推进没有单独的催促计时器。

## 4. 主动聊天算法：半小时档位与一次机会

### 4.1 一个周期从哪里开始

最近一轮真实交流完成，或一次自然主动消息成功保存后，进入新的等待周期。用户又发来有效消息时，旧候选让位，按新的交流状态重新计时。

只累计允许联系的时间。安静时段、明确暂停、正在收集／处理用户输入和已有待交付消息时暂停累计，不推断用户在线或已经读过消息。

例如 22:10 完成交流，22:30 进入安静时段，此时累计 20 分钟；次日 08:00 恢复允许联系后，再经过 10 分钟才到第一档，不在 08:00 直接按整晚时长提高概率。

### 4.2 档位如何增长

| 累计允许联系时间 | 本档基础概率 |
| --- | --- |
| 30 分钟 | 10% |
| 60 分钟 | 15% |
| 90 分钟 | 20% |
| 120 分钟 | 30% |
| 150 分钟 | 40% |
| 180 分钟 | 50% |
| 此后每半小时 | 增加 5 个百分点 |
| 420 分钟及以后 | 达到并保持 90% 上限 |

每档最多判断一次。进入一个新的档位时，生成一次随机结果；未抽中就等待下一档，抽中才让模型判断是否有自然内容可说。

这张表是普通、可联系、没有未回复积压时的基础曲线。不会升到 100%，也不会因抽中就强行拼出一句话。

### 4.3 未回复怎样折减

| 连续未回复的自然主动联系 | 处理 |
| --- | --- |
| 0 次 | 使用本档基础概率 |
| 1 次 | 降低本档机会；首轮试运行采用基础概率的四分之一，作为内部可校准值 |
| 2 次 | 暂停自然主动联系，直到用户回来或主动恢复 |

有效用户输入表示重新参与交流，可以结束未回复周期；如果这条输入本身要求暂停联系，新的暂停边界优先生效。

用户明确建立的提醒不随机丢失，也不因为没回复提醒就增加自然闲聊的未回复计数。近期有其他 Echo 联系交付时，自然闲聊应让路，避免不同来源的消息扎堆。

### 4.4 抽中后做什么

按顺序处理：检查最新边界与任务状态；读取相关真实背景；进入现有主动规划／生成链；有自然内容则保存并交付，没有则结束本档机会。

生成前和保存前都检查用户是否已回来、是否刚暂停联系、是否已重置关系。状态变化时取消过时的候选，不抢在用户新消息前另发问候。

模型略过一次机会不会立即重新生成；搜索失败或发送失败不创建新的抽签机会。技术重试沿用原任务身份，仍须检查最新状态。

### 4.5 怎样避免后台频率改变实际概率

保存本周期的有效等待时间、当前已评估档位、评估结果和关联候选任务。多个 Worker 只能有一个消费某一档位。

后台每分钟检查和每五分钟检查，都不允许在同一半小时档反复抽签。服务重启沿用已保存结果。停机期间错过多个档位，不补抽全部历史机会，恢复后最多判断当前有效档位一次。

“扫描频率不改变概率”针对正常半小时以内的任务扫描；长时间停机本来就可能错过机会，不伪装成可以同时做到完整补偿和零补发。

### 4.6 什么才算成功联系

以真实消息已经保存、可被客户端读取为业务成功，不以模型生成过文字或推送接口返回为准。推送失败时重试通知，不重复生成第二条聊天消息；不把成功保存等同于用户已读。

一次主动回复拆成多个气泡或附带图片，仍只算一次联系。联系记录、计数变化和任务完成必须保持一致，避免重试多发或漏计。

## 5. 分段算法：确定内容，选择边界，保存组合

### 5.1 输入和输出

输入是主模型已经完成的自然文字与真实附件。输出是内容顺序相同的一组文字气泡和图片，以及对应展示间隔。

切分器不续写、不总结、不截掉必要答案。普通闲聊的内容量先由主模型根据当前话题控制；复杂求助仍完整回答。

### 5.2 五步处理

1. **保护完整结构。** 标出代码、列表、表格、引用、链接、数字和颜文字，避免把它们的内部标点当成聊天边界。
2. **保留模型段落。** 模型自然换行是最直接的语气与语义信号，优先采用。
3. **补充完整句子边界。** 普通多句聊天即使不到 180 字也参与判断；句号、问号、感叹号等提供候选，逗号不默认拆分。
4. **组合句子。** 对可切边界选择本轮偏连贯或偏轻快的组合倾向，允许两句合在一起，也允许一个独立反应自成气泡。
5. **检查与保存。** 保留原内容与顺序，避免重复或空气泡；超过现有交付保护上限时合并相关部分，不删除尾部答案。

程序兜底主要依据标点、连接关系和受保护布局，是结构近似；真正的语义分段主要来自主模型给出的自然段落，不声称纯标点规则能完整理解句意。

### 5.3 随机性放在边界组合

同一轮使用一个共同的组句倾向，不为每个标点各自高概率抽签。独立完整回应点更容易分开，紧密因果或条件解释更容易合并，受保护结构内部不能随机切开。

最近多次有合适的多句内容却一直是单气泡，可以小幅提高本轮偏轻快的倾向；已经连续多条短气泡时则适度合并。参考的是消息组，不把图片或单条气泡误当成一轮。

已有内容确实有三四个完整意思时，可以形成三四条；只有“好呀”就只发这一句。六条保留为当前交付保护上限，不变成生成目标。

只在第一次确定该回复组时选择组合，并保存结果。服务重试、另一台手机加载和历史重连都读取同一结果，不能各自重抽后出现不同气泡。

### 5.4 展示间隔

首条准备好的内容及时显示。之后复用按内容长度计算的短间隔，允许小幅浮动，并统一压缩到整组额外等待不超过三秒。

随机浮动只影响展示节奏，不改变内容或消息时间事实。旧历史加载与重连补偿不重演打字过程。本期仍先完成生成再交付消息组，不扩展未经完整检查就提前上屏的流式首气泡。

## 6. 表情算法：考虑机会、表达意图、真实选图

### 6.1 什么增加图片考虑机会

利用最近对话和现有轻松互动线索，保守识别适合考虑图片的回合。普通“哈哈”只是线索，不是对真实情绪的证明；不能判断时不额外加提示，工具仍然可用。

只计算有机会却未使用图片的轻松回合。严肃、明确悲伤、用户纠正或设定边界时不累积补发压力；没有聊天的几天也不转成图片欠账。

第一版采用“基础倾向 + 连续合适但未使用时的小幅提升 + 温和上限”。初值在实现评测时统一选取，不把这里扩展成面向用户的第二套频率档位。成功使用图片后回到基础倾向，搜索过但未发送不算使用。

### 6.2 抽中之后与没抽中之后

| 判断结果 | 对主模型与工具的影响 |
| --- | --- |
| 本轮抽中考虑机会 | 只附加一句条件提示，提醒可以自然用图片表达；主模型仍可不用 |
| 本轮没有抽中 | 不附加提示，表情工具照常存在，主模型仍可自主使用 |
| 用户明确索要表情 | 正常理解并执行请求，不走这层机会抽样 |
| 当前内容不适合装饰 | 不加考虑提示，优先让模型认真回应 |

因此，考虑概率不等于发图概率。不能据此许诺每几轮必有一张图，也不通过随机隐藏工具限制模型。

### 6.3 怎样选到贴切的图片

主模型先确定 Echo 想表达的态度与对象，例如“陪用户吐槽的无奈”“被夸后的害羞”“一起庆祝成功”，再向现有表情工具提供自然语言意图。

工具在当前用户可见的图库中，复用描述、标签与语义检索取得匹配图片；无合适候选则返回无结果，不从无关图片里随机补一张。描述与标签可能不准确，贴切程度仍需要真实图库样本检查。

成功结果才成为真实图片附件，写入消息并计为已使用。图片丢失或发送失败不能写成已经发送。保留归属、超时、工具预算与执行去重，不新增发图冷却或近期图片降权。

### 6.4 颜文字与图片怎样协调

颜文字由主模型直接写进自然文字，不额外做一个颜文字分类器或随机后缀器。切分与表达检查保护其整体，问号或括号不误当成多次追问或动作剧本。

同一个情绪优先使用一种明显表达：文字已经有小得意，或一个颜文字已经足够时，可以不配图。已有贴切图片时，文字可以更简短。这个倾向是软约束，不禁止自然庆祝或斗图中的组合表达。

第一版继续使用现有图片前置／后置能力；不额外扩展任意气泡之间插图的协议。图片数量由语境与现有整轮工具预算控制，不恢复固定单轮一张限制。

## 7. 关于她、重置与旧数据

### 展示由结果驱动

“关于她”读取真实的当前关系、互动和活跃日，不再显示单独的熟悉度、关系选择器或可编辑人格表单。关系更新后刷新，提议尚未成立时继续显示旧关系。

取消频率设置页时，保留提醒管理的可达入口。聊天中“暂停主动联系”“恢复联系”等指令要真正写入业务状态，不能只存一句可能检索不到的记忆。

### 重置按新的相处周期处理

按审阅稿“清空所有历史”的目标，重置后不继续使用旧聊天、摘要、从旧相处形成的陪伴记忆、亲密阶段或待回应提议。账号、登录、设备绑定及用户单独建立的提醒不属于关系历史，不顺带删除；明确拒绝、称呼边界和联系权限仍由相应业务状态保留。

执行前的现有二次确认必须列清实际清理范围，不能继续显示旧的“保留所有历史与记忆”文案。数据清理应符合现有保存与删除机制，不能仅隐藏页面却让旧记忆继续参与新聊天。

同时结束旧关系的主动候选与后台生成。清理期间旧结果不得重新写回；已在生成中的回复、关系提议与记忆任务都需要检查自己仍属于当前相处周期。

### 页面调整不等于重置

普通版本迁移保留用户已有关系、明确边界、历史与主动联系开关，不因去掉设置页面而清零或重新开启联系。原手选关系作为已有背景保留，不强迫用户重新确认。

旧频率与手选关系的读写消费者需要随正式迁移整理，不能只隐藏控件，后台仍按失效选项执行。

## 8. 一致性与异常处理

| 场景 | 算法要求 |
| --- | --- |
| 两个后台进程同时看到同一半小时档 | 只认领一次候选机会 |
| 概率抽中后用户刚好发来消息 | 过时主动候选让位，进入正常对话 |
| Echo 提出关系但消息保存失败 | 不留下“已提出”或已经升级的状态 |
| 用户接受关系动作被重试 | 同一次回应只产生一次关系变化 |
| 后台生成完成前用户重置 | 拒绝旧周期结果回写 |
| 消息已保存但推送失败 | 重试通知，不重生成聊天正文 |
| 图片工具无结果 | 保留自然文字，不虚构图片附件 |
| 客户端重连或另一个客户端加载 | 使用已保存的气泡顺序，不重新随机切分 |

关键状态与消息写入需有明确事务和幂等语义。应用层负责业务过程，基础设施实现原子保存，不在路由中拼 SQL。

## 9. 开发归属与接入顺序

| 现有模块 | 本次承担的工作 |
| --- | --- |
| relationship | 内部进度、关系候选、真实提议与回应后的状态流转、重置语义 |
| chat / agent | 当前轮材料、自然回应、实际关系动作与图片工具回路、气泡交付与统计 |
| proactive_chat | 半小时周期、一次判断、未回复收敛、暂停恢复与任务处理 |
| stickers | 可见图库搜索、真实附件与执行结果 |
| shared/prompting | 消费业务准备的材料，按真实链路渲染，不反向读取业务模块 |
| Flutter / Harmony | 关于她、入口精简、状态刷新、版本显示与 USB 覆盖安装验证 |

关系提议与自然回应写入尚不是现有完整能力，需要在本次实际消费链中实现。新增的业务动作、状态与端口必须与真实调用方一同接入，不先建空接口、备用 feature 或未加载提示资产。

实施时先统一业务状态和消费者，再接入关系流转与半小时调度；随后落地分段和图片机会；最后完成页面与发布验证。每一批交付都保留可执行检查，不把全套重构作为本次的前置工程。

当前规范中“手动选择关系”的规则需要随实际实现同步为新流程。已有跨 feature 内部依赖与依赖环不扩散，触及的协作通过真实业务端口和装配整理，不新增兼容门面掩盖问题。

## 10. APP 版本与安装验收

首页优先读取已安装包的版本，避免维护一份独立固定文字。发布时核对目标版本、构建配置、包内版本、首页显示和设备实际安装版本；各平台构建号按各自规则递增，不要求数值相同。

此前检查发现鸿蒙首页固定为 v1.1.7，而包配置与版本配置已为 1.1.8，这项应在客户端实现批次修复；不能只改首页字符串就当作版本问题解决。

默认走 USB 同签名覆盖安装，鸿蒙使用现有安装脚本，Android 使用对应 adb 覆盖流程。安装后实际打开首页核对版本，不自动卸载、清数据或改签名。
