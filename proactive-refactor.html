以前：两条路各写各的正文——念头那条直接投草稿或让一个几乎没人设的 agent 写，定时那条才有完整 11 层人设。 改后：两条路共用同一套正文提示与风格守卫；念头本身也补上同源人格摘要，保证"念头怎么说、消息就怎么接"。

三、打算怎么改 四层，正文只留一份

触发层保持两套（语义不同，不合并）；②③④ 收成一条。

① TRIGGER 两套触发，保留 presence tick 产出念头；schedule 由 planner 批准。预算、安静时段、去重不动。
保留：各自语义
② INTENT 统一成参数 intent（念头或提醒目标）、plan、action_intent、force_send。不新建跨 feature DTO。
新增：brief / plan 参数
③ GENERATE 同一套提示与守卫 无动作：走 prepare（A 路 skip_planner）。有动作：共用同一套提示层 + 简报，保留 agent 直调以拿到工具结果。
新增：include_user_profile=False / guard_dialogue_reply
④ DELIVER 已共用 persist_delivery → 微信 → 事件流 → 通知 Outbox。
不变
人格 一份源，两种渲染 default_persona 仍是唯一内容源；writer 用完整层，念头用 render_persona_digest（≤240 token）。planner 不加。
念头 念头也带人格 念头生成器 system = 固定职责 + 人格摘要；念头继续写入 presence_thoughts，App 展示不变。
一致 简报携带念头 "你刚才的内心想法：{念头}；表达同一件事，不要原样复述。" 保证语义一致、措辞自由。
退役 draft_text 下线 念头不再产出 draft；goal 不再存 draft；失败改静默 suppress + 内部记录，不再发"本来想…没做成"。

六、代价与验收

代价

  • A 路每次"想说句话"多一次模型调用（后台 worker，不影响用户交互延迟）。
  • 按生产数据 32 念头 / 11 可分享，日均十余次。
  • 风格兜底可能改写念头语气：语义一致、措辞允许不同。
  • 失败改为静默后，用户不会收到"没做成"的提示。

验收

  • 单测：A 路不调 planner；简报含念头；proactive 提示不含 USER_PROFILE。
  • 单测：失败/空交付不产生投递。
  • 链路：本地库跑一条 presence goal，消息与念头语义一致。
  • 回归：定时入口行为不变，仍走 planner。
  • 门禁：架构检查 + 全量后端测试 + ruff。
