# Echo 桌面机器人硬件与嵌入式入门手册

## 1. 这台机器人到底是什么

第一阶段的 Echo 桌面机器人不是一台独立运行大模型的电脑，而是一台低成本的联网语音终端。

```text
机器人负责：听、传输、播放、按键、灯光和屏幕
Echo 服务器负责：识别、思考、记忆、生成回复和合成声音
Echo APP 负责：账户、文字聊天、设备绑定和设置
```

完整链路如下：

```text
用户说话
  -> 麦克风将声音变成数字音频
  -> ESP32-S3 压缩音频并通过 Wi-Fi 上传
  -> Echo 服务器调用 ASR 得到文字
  -> Echo 使用人格、关系和长期记忆生成回复
  -> Echo 服务器调用 TTS 得到回复音频
  -> ESP32-S3 接收并播放音频
  -> 用户从扬声器听到 Echo 的回复
```

因此，机器人本体不需要 GPU，不需要在板子里安装大模型，也不需要额外购买一台高性能电脑。当前服务器调用第三方 ASR、LLM 和 TTS API 即可。

## 2. 你手上的硬件

### 2.1 Bread Compact Wi-Fi 是什么

`Bread Compact Wi-Fi` 不是一个芯片型号，而是 `xiaozhi-esp32` 项目为一套面包板接线方案定义的开发板类型。它通常以 ESP32-S3 为核心，连接麦克风、功放、扬声器、按键、LED 和可选 OLED。

本地小智源码已经包含这一板型：

```text
F:\project_work\xiaozhi-esp32\main\boards\bread-compact-wifi\
```

这里的代码规定了每个硬件连接到 ESP32-S3 的哪个引脚，以及按键、麦克风、功放、屏幕和灯光如何初始化。

### 2.2 ESP32-S3 是什么

ESP32-S3 是机器人中的微控制器，可以理解成一台体积很小、功耗很低的专用计算机。它擅长：

- 连接 Wi-Fi 和蓝牙。
- 读取麦克风数据。
- 对音频进行 Opus 编码和解码。
- 接收按键输入。
- 控制 LED、OLED 和功放。
- 与服务器保持 WebSocket 连接。
- 运行轻量的本地唤醒词和音频前处理。

它不适合运行 Echo 的完整大模型、长期记忆数据库或高质量自由语音 ASR/TTS。

### 2.3 麦克风、功放和扬声器

```text
麦克风：把空气振动转换成数字音频
功放：把 ESP32 输出的微弱数字音频转换成足以驱动扬声器的信号
扬声器：把电信号重新转换成声音
```

常见面包板方案可能使用 I2S 麦克风和 I2S 功放。I2S 是芯片之间传输数字音频的总线，不是网络协议，也不是音频文件格式。

### 2.4 OLED、按键和 LED

- OLED 用于显示配网、空闲、聆听、思考、说话、断网和错误状态，不参与 AI 推理。
- 按键可用于开始对话、停止播放、进入配网或恢复设置。
- LED 用颜色或闪烁方式表示当前状态。
- 物理静音开关用于真正关闭麦克风采集，是后续隐私设计的重要部分。

### 2.5 面包板和杜邦线

面包板是一种无需焊接的临时接线板，适合原型验证。杜邦线连接开发板和各种模块。

它们适合调试，不适合最终产品：线可能松动、接触不良，电源线接错还可能损坏模块。第一阶段不要频繁拔线；先拍清晰接线照片并记录每根线连接的引脚。

## 3. 固件是什么

固件是烧录在 ESP32-S3 Flash 中的程序，相当于机器人的嵌入式操作软件。它决定：

- 使用哪块开发板和哪些引脚。
- 如何配网。
- 麦克风如何采样。
- 音频如何编码和发送。
- 连接哪个服务器。
- 如何播放返回音频。
- 按键、LED 和屏幕分别做什么。
- 如何升级下一版固件。

你当前烧录的文件是：

```text
F:\tmp\bat\merged-binary.bin
```

`merged-binary.bin` 是把引导程序、分区表、应用程序和资源合并后的整包固件。它适合一次性烧录，但不适合直接阅读或修改。真正可维护的源代码位于：

```text
F:\project_work\xiaozhi-esp32
```

当前二进制内置的是小智官方 OTA 和 WebSocket 地址，所以设备现在属于小智官方服务链路。后续需要从源码编译 Echo 专用固件，而不是直接编辑这个 `.bin` 文件。

## 4. 烧录、编译和 OTA 的区别

### 4.1 编译

编译是把 C/C++ 源代码转换成 ESP32 能运行的二进制固件。编译时必须选对：

- 芯片类型，例如 ESP32-S3。
- Flash/PSRAM 规格，例如 N16R8。
- 板型，例如 `bread-compact-wifi`。
- 引脚配置。
- 分区表和资源大小。

选错板型可能导致麦克风无声、扬声器无声、屏幕不亮或设备无法启动。

### 4.2 烧录

烧录是通过 USB Type-C 数据线把固件写入 ESP32。烧录完整合并固件可能同时清除：

- Wi-Fi 配置。
- 设备 UUID。
- 服务器配置。
- 用户绑定状态。

烧录前必须保存当前可用固件、接线照片、设备 MAC 和串口日志。

### 4.3 OTA

OTA 是设备联网后自行下载并安装新固件。正式 Echo 固件最终应连接 Echo 自己的 OTA 地址，避免小智官方升级覆盖我们的服务器配置或协议修改。

第一轮开发不急着做 OTA，先保留 USB 烧录作为可恢复路径。

## 5. 音频是怎样流动的

### 5.1 PCM 与 Opus

麦克风产生的是原始采样数据，可以理解为 PCM。PCM 数据简单但体积较大。小智固件会把它编码成 Opus，以减少网络传输量。

```text
麦克风 PCM
-> ESP32 Opus 编码
-> WebSocket 二进制帧
-> 服务器 Opus 解码
-> ASR 接口需要的音频格式
```

服务器返回时方向相反：

```text
TTS 返回音频
-> 服务器转换为设备约定的采样率和 Opus 帧
-> WebSocket
-> ESP32 Opus 解码
-> 功放
-> 扬声器
```

### 5.2 ASR、LLM 和 TTS

| 名称 | 输入 | 输出 | 当前放置位置 |
| --- | --- | --- | --- |
| ASR | 用户音频 | 用户文字 | 第三方 API |
| Echo Chat/LLM | 用户文字和记忆上下文 | Echo 回复文字 | Echo 后端编排，模型可调用第三方 API |
| TTS | Echo 回复文字 | 回复音频 | 第三方 API |

你的服务器不是亲自计算大型模型，而是负责调用供应商、维护 Echo 人格和记忆，并编排整条链路。个人单设备使用时，普通服务器足以承担连接、转码和数据库工作。

### 5.3 半双工与全双工

第一版推荐半双工：

```text
用户说话时机器人不播放
机器人播放时默认不收取新一句语音
用户可按键打断播放
```

全双工意味着 Echo 播放时仍能听到用户插话。这需要稳定的回声消除，否则麦克风会把机器人自己的声音当成用户输入。全双工体验主要受声学结构和 AEC 能力影响，不只是改几行软件。

## 6. 网络和协议

### 6.1 Wi-Fi 配网

ESP32-S3 自带 Wi-Fi，不需要额外 Wi-Fi 模块。首次使用时，设备需要获得家庭 Wi-Fi 名称和密码。小智固件已有热点或 BluFi 配网能力，第一版可以继续复用。

配网只解决“设备如何上网”，不等于“设备属于哪个 Echo 用户”。

### 6.2 WebSocket

WebSocket 是设备和服务器之间的长连接。它可以交替发送：

- JSON 控制消息，例如开始聆听、停止聆听、ASR 文本和 TTS 状态。
- 二进制 Opus 音频帧。

它比每一小段音频都重新发 HTTP 请求更适合实时语音。

### 6.3 当前小智协议与 Echo 协议

小智固件已经实现一套完整协议，包括：

- `hello` 握手。
- `Device-Id` 和 `Client-Id` 请求头。
- Opus 音频帧。
- `listen`、`stt`、`tts` 等状态消息。
- WebSocket 或 MQTT/UDP 传输。

Echo 当前 APP 语音接口主要面向用户 Token 和 PCM 音频，不能只修改服务器 URL 就直接兼容。

推荐保留设备端成熟的小智音频协议，在 Echo 后端增加兼容入口：

```text
Bread Compact
-> Echo Device WebSocket（兼容小智协议）
-> ASR Provider
-> Echo Chat / Persona / Memory
-> TTS Provider
-> Bread Compact
```

## 7. APP 与机器人是什么关系

机器人不是“连接 APP 才能说话”，而是 APP 和机器人都连接 Echo 后端：

```text
Echo APP ---------> Echo 后端 <--------- Bread Compact
用户身份与设置       人格/记忆/聊天          语音终端
```

这样即使 APP 被关闭，机器人仍能工作。APP 主要承担：

- 登录账户。
- 绑定或解绑机器人。
- 查看机器人在线状态。
- 设置设备名称、音量和安静时段。
- 查看机器人产生的聊天记录。
- 后续切换云端服务器或家庭 Echo Hub。

设备不应保存 APP 的用户 access token。正确做法是 APP 使用一次性绑定码把 `device_id` 绑定到用户，服务器再给机器人签发权限受限的设备凭证。

## 8. Echo 接入需要开发什么

### 8.1 固件侧

第一版尽量少改：

1. 保留 Bread Compact 的麦克风、扬声器、Opus、按键、屏幕和配网代码。
2. 将 OTA 检查地址改为 Echo 控制的地址或暂时关闭自动升级。
3. 让服务器配置指向 Echo Device WebSocket。
4. 保存 Echo 签发的设备凭证。
5. 根据需要调整状态文字和品牌资源。

### 8.2 Echo 后端侧

需要新增：

1. 兼容小智握手和音频帧的设备 WebSocket。
2. Opus 解码、采样率转换和 TTS 音频重新编码。
3. 设备注册、绑定、凭证、撤销和心跳。
4. 将 ASR 文本交给现有 Echo Chat。
5. 将用户文字和 Echo 回复写入同一聊天历史。
6. 调用现有或可替换的 ASR/TTS Provider。
7. 超时、断网、API 失败和取消播放的状态处理。

### 8.3 APP 侧

第一轮语音闭环不必先改 APP。服务器原型跑通后，再增加：

- 输入绑定码或扫码。
- 设备列表和在线状态。
- 音量、静音状态和解绑。
- 固件版本和更新状态。

## 9. 现在不需要购买什么

在当前目标下，不需要额外购买：

- GPU 或 AI 加速卡。
- Raspberry Pi 或其他 Linux 开发板。
- 独立 Wi-Fi 模块。
- 本地 ASR/TTS 主机。
- 摄像头。
- 舵机、电机、底盘和导航传感器。
- 定制 PCB。

只有实际测试暴露问题后再升级：麦克风听不清才考虑麦克风阵列；无法自然打断才考虑带硬件 AEC 的音频板；要做视觉才增加摄像头和更强主控。

## 10. 推荐的安全操作顺序

### 阶段 A：只验证硬件

继续使用当前小智固件，确认：

- 能正常配网和连接官方服务器。
- 唤醒词和按键有效。
- 麦克风识别清楚。
- 扬声器无明显爆音或持续噪声。
- OLED/LED 状态正常。
- USB 数据线可以读取串口日志并重新烧录。

### 阶段 B：记录硬件基线

保存以下信息：

- 开发板、麦克风、功放、扬声器和屏幕正反面照片。
- 每根杜邦线的两端引脚。
- 芯片规格是否为 ESP32-S3 N16R8。
- 设备 MAC、Client-Id、固件版本和板型。
- 当前可恢复的 `merged-binary.bin`。
- 一份从上电到成功对话的串口日志。

### 阶段 C：电脑模拟设备协议

在修改固件前，先让电脑程序模拟小智设备连接 Echo 后端，验证：

```text
测试音频 -> Echo WebSocket -> ASR -> Echo Chat -> TTS -> 返回音频
```

这样服务器问题不会与焊接、引脚、USB 驱动和固件问题混在一起。

### 阶段 D：再编译 Echo 固件

服务器闭环稳定后，从当前 `xiaozhi-esp32` 源码为 `bread-compact-wifi` 编译 Echo 固件，并保留回刷旧固件的方法。

## 11. 常见误区

### “AI 加速”是否表示本地运行完整 AI

通常不是。ESP32-S3 的 AI/向量能力主要用于唤醒词、VAD、音频前处理和轻量命令识别。自由中文 ASR、自然 TTS 和 Echo 大模型仍放在服务器。

### 小智控制台是不是 Echo 后台

不是。当前 `xiaozhi.me` 控制台管理的是小智官方智能体。Echo 接管后，设备身份、人格、记忆和聊天记录应归 Echo 后端管理。

### 修改 WebSocket 地址是否就能接入 Echo

不能。服务器还必须理解小智握手、JSON 状态和 Opus 帧，并完成设备认证、ASR、Echo 对话和 TTS 返回。

### 调用第三方 ASR/TTS 是否需要服务器 GPU

不需要。GPU 计算在第三方服务商侧。Echo 服务器承担网络连接、音频转码、API 编排和业务数据。

### `.bin` 能否直接改成人格或服务器程序

不应直接修改。人格和记忆在 Echo 后端；服务器地址和板级行为应在固件源码中配置后重新编译。

## 12. 第一阶段完成的定义

第一阶段不是“所有硬件都弄懂”，而是达到以下结果：

```text
Bread Compact 能稳定收音
-> 连接自己的 Echo 服务器
-> 第三方 ASR 得到文字
-> Echo 使用同一人格和记忆回复
-> 第三方 TTS 生成声音
-> Bread Compact 稳定播放
-> APP 能看到这次对话
```

达到这一闭环以后，再讨论唤醒体验、语音打断、OLED 表情、外壳以及视觉模块。

## 13. 后续提问时最有用的信息

遇到问题时，优先提供：

1. 硬件或接线的清晰照片。
2. 商品链接及准确模块型号。
3. 当前现象，例如“能唤醒但无声音”。
4. 上电后的完整串口日志。
5. 使用的固件文件和烧录方式。
6. 问题发生前最后一次改动。

不要凭现象反复更换引脚或烧录不同固件。先定位问题属于供电、接线、驱动、固件、网络、协议还是服务器，再动对应层。
