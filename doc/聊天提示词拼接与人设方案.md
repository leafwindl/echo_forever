### 1.2 代码审查新发现的两个画像缺陷

这两处是两条线都没覆盖、但本次整合必须一起修的：

1. **主动 writer 的空画像采集提示**：`context_builder.py:508` 的 `writer_base_messages` 调用 `render_prompt_layers` 时没有传 `user_profile`，而 `renderer.py:353` 无条件调用 `render_user_profile(None)`。结果是主动消息正文里带着「你还不太了解他，可以问一两个基础问题」。B 线方案设计了 `include_user_profile=False`，本文沿用并在 P0 实现。
2. **每日来信也有同样的采集提示**：[assemble_context.py:102](../Echo-backend/features/letters/application/assemble_context.py:102) 调 `render_prompt_layers` 同样没传 `user_profile`。来信是 Echo 写给用户的，本该注入画像；现在拿到的是「去问基础问题」。修法不是关掉，而是**补传画像**。

### 1.3 现有画像与引导能力

- 表 `user_profiles` 已有 `display_name / basics / routine / personality / communication / interests / boundaries / notes / confidence`（[postgres_schema.py:1020](../Echo-backend/db/postgres_schema.py:1020)）。
- 写入工具 `update_user_profile` 已在 agent 注册，`allowed_modes=("chat","proactive")`，每轮最多 1 次（[profile_tools.py](../Echo-backend/features/agent/infrastructure/tools/profile_tools.py)）。
- `persona` feature 的 `onboarding_completed` 是 **App 设置页首次填写称呼** 的标记（[persona_management.py](../Echo-backend/features/persona/application/persona_management.py:27)），不是对话内采集状态，不能直接复用。
- 空画像时 renderer 输出固定话术「可以在一两次对话里自然问一两个基础问题」。它有三个问题：没有阶段、不知道缺什么、主动/来信场景也会出现。

## 3. 统一装配模型

### 3.1 三类职责，不要再混

| 类别 | 回答的问题 | 生命周期 | 存放 |
|---|---|---|---|
| 行为资产 | 我是谁、怎么说话、这轮怎么交付 | 版本化，跨会话稳定 | `prompts/`，代码选择 |
| 用户状态 | 我对谁说话、我们到哪了、记得什么 | 每用户动态 | 业务表 + 渲染层 |
| 任务输入 | 这一轮要做什么 | 每轮 | 调用方 |

A 线的问题「人设和自然对话规则合并」之所以不能整块做，就是因为第一类和第三类混在了一起：`natural-dialogue.md` 第 3/4 条写了 `emit_chat_beats`、`respond_relationship` 这些工具契约，它们是行为资产里的「交付」子类，不是人格。

### 3.2 目标层序（所有 mode 共用一张表）

| # | 层 | 内容 | 出现条件 | 预算 |
|---|---|---|---|---:|
| 1 | 系统约束 | 安全边界、真实性、授权、身份底线 | 始终 | ~500 |
| 2 | 人设 | 身份、性格行为锚点、说话方式；示例按需 | 始终（示例默认不注入） | ~1,000–1,400 |
| 3 | 渠道交付 | 当前渠道的输出合同：气泡/beat/sticker、静默、JSON、通话口播 | 始终 | ~300–500 |
| 4 | 用户上下文 | 关系一行 + 显式偏好 + 推断画像（两段可信度） | chat/call/letter；proactive 只保留偏好 | ~250 |
| 5 | 引导 | 冷启动期问什么、还缺什么、什么时候可以问 | 仅 chat 冷启动期 | ~100 |
| 6 | 长期记忆 | 召回结果 | 有则出现 | 200 |
| 7 | 会话摘要 | 摘要（去掉 message_id） | 有则出现 | 400 |
| 8 | 时间上下文 | 精简 JSON | 始终 | ~250 |
| 9+ | 历史 | 消息 | 有则出现 | 大头 |
| 末前 | 后置锚点 | 长历史时 1–2 行人设提醒 | 历史 ≥20 条时 | ~80 |
| 末 | 用户输入 / 主动简报 | 本轮任务 | 始终 | — |

与规范 §4 六类的映射：

- 身份角色 → 第 2 层
- 规则约束 → 第 1 层（常驻）+ 第 3 层（场景）
- 上下文注入 → 第 4、6、7、8 层
- 工具描述 → 独立 `tools` 参数，不占 messages
- 示例 → 第 2 层内，按需选择；默认不注入
- 输出格式 → 第 3 层

**第 5 层「引导」是新增的**。它不是用户数据，是场景规则，所以不能塞进 `[USER_CONTEXT]`，否则数据块开始下命令，违反「数据不冒充指令」。

### 3.3 关系层放哪

**已拍板：并进第 4 层「用户上下文」，不单独成层，也不并入人设。** 原因：

- 关系是动态数据（`new/familiar/trusted/close` + 类型），人设资产必须是静态可版本化的。把变量塞进人设文件，等于每次渲染都要改人设文本，缓存和评测都会抖。
- 关系影响的是「怎么称呼、亲昵到什么程度」，和偏好/画像同属「关于这个用户和这段关系」的状态；放在一起，模型更容易形成一致的用户模型。
- 并进后只保留一行：`当前关系: 初识；相处方式: 朋友`。亲昵边界已经在 `affection_style` 里，不重复展开。
- 数据从 `relationship.state.stage` / `relationship.state.relationship_type` / `relationship.state.relationship_mode` 取；shared 渲染层只接收已格式化的值，不拿整个实体。

### 3.5 五条线逐层装配

先定三条上下文原则：

1. **对话线（chat/call）同策略**：记忆、摘要都用向量召回 + 默认摘要，不因为渠道是语音就降级成关键词触发。
2. **主动/定时不是续答，但也不从零**：带「主动上下文」（摘要 ≤400 字 + 最近 5 条用户消息 + 相关记忆 ≤3 条），并写死「过去、不是当前输入、不得续答、不得推断在线」。
3. **来信不是续聊**：历史换成当日证据，摘要故意不带，简报只是证据索引，不是摘要。

五条线共用一个渲染器和一张层表，但取层不同。下面按「触发 → 入口 → 层栈 → 现状差异」逐条列。预算里「现状」来自 A/B 线的生产或代码实测，「目标」是估算值，不是承诺。

#### A 文字聊天（chat）

- 触发：用户在 App、微信或手机端发来文字消息。
- 入口：`send_chat_message` → `GenerateChatReply.prepare("chat")` → `build_chat_context` → `render_prompt_layers` → `TurnPolicy.initial_messages` → `ModelToolLoop`。

| 层 | 装什么 | 预算（现状→目标） | 现状差异 |
|---|---|---|---|
| 1 系统约束 | 安全、隐私、真实性、外发授权、能力如实 | 272 + 规则 §5/§6 → ~560 | §5/§6 现在混在 1120 字自然对话规则里 |
| 2 人设 | 身份、性格行为锚点、表达原则、披露/禁止、6 条示例（按需） | 594 → ~900（+240 示例） | 硬编码在 `default_persona.py`；示例为空 |
| 3 渠道交付 chat | 气泡、`emit_chat_beats`、`send_sticker`、关系/主动开关工具、静默 | 118 + 177 + ~290 → ~470 | 三处分散；`turn_policy` 抢 messages[0] |
| 4 用户上下文 | 关系一行 + 显式偏好 + 推断画像 | 57 + 99 + 164 = 320 → ~250 | 空画像输出固定采集话术 |
| 5 引导 | 8 轮内问什么、还缺什么、一次一个 | 无 → ~100 | 现在只有固定采集话术，没有阶段 |
| 6 长期记忆 | 向量召回 ≤8 条，带 score | 189 | 不变 |
| 7 会话摘要 | 去 `source_message_id` 的摘要 | 537 → ~430 | 现在把来源 ID 喂给模型 |
| 8 时间上下文 | `local_datetime / timezone / gap / last_message_at` | 465 → ~250 | 字段过多 |
| 9 历史 | ≤100 条 / 64k 估算裁剪 | 4758 | 不变 |
| 10 后置锚点 | 1–2 行防长历史漂移 | 无 → ~50 | 没有；历史越长越容易掉人格 |
| 11 用户输入 | 本轮消息 | 4 | 不变 |

拼接顺序：

```text
系统约束 → 人设 → 渠道交付(chat) → 用户上下文 → 引导?
→ 长期记忆 → 摘要 → 时间 → 历史 → 后置锚点? → 用户消息
```

#### B 语音聊天（call）

- 触发：设备语音/通话，或客户端以 `conversation_mode="call"` 发起。
- 入口：`EchoConversationService.reply` → `send_chat_message(mode="call")` → `prepare("call")` → 同一渲染器；`CallReplyStreamLimiter` 按 80 字截断。
- **上下文与 chat 一致**：记忆、摘要、历史不再用「还记得/上次」关键词才启用，改为与 chat 同一策略——向量召回、会话摘要、同一套检索逻辑；历史条数按渠道（chat ≤100，call 单独 30）。这是用户明确要求，优先于原来的低延迟取舍。
- 代价：通话是实时语音，向量召回会增加首字延迟。缓解：通话开始时异步预取、`top_k` 降到 3–4、摘要截断到 200–300 字；通话历史定为 30 条，是延迟和连贯的折中，不回到关键词触发。

| 层 | 装什么 | 预算（现状→目标） | 现状差异 |
|---|---|---|---|
| 1 系统约束 | 同 chat，加上通话中的行为边界 | ~500 | call-dialogue 里混了部分边界 |
| 2 人设 | 同一份人格；口播版不读示例、不带颜文字 | 594 → ~800 | 现在与 chat 共用完整人设，没有口播裁剪 |
| 3 渠道交付 call | 只说出口的话、1–2 句、≤50 字、无 Markdown/emoji/网址/括号、不重复用户整句 | 602 + 177 → ~300 | `call-dialogue.md` 与 mode guidance 重复 |
| 4 用户上下文 | 关系 + 显式偏好 + 画像 | 320 → ~250 | 空画像时会把「问基础问题」带进通话，很怪 |
| 5 引导 | 不出现 | — | 通话里不该盘问资料 |
| 6 长期记忆 | 向量召回 ≤8，与 chat 同一实现；通话可降到 3–4 | 0 或 ~200 → ~200 | 现在只有关键词才召回 |
| 7 会话摘要 | 默认加载，与 chat 一致；通话可截断到 200–300 字 | 0 或 ~400 → ~300 | 现在只有关键词才带 |
| 8 时间上下文 | 日期、时段、时区、gap | ~150 | 现在字段比目标多 |
| 9 历史 | 通话单独 30 条；检索策略与 chat 一致，历史条数按渠道 | 8 → 30 条 | 现在 `call_history_messages=8` |
| 10 后置锚点 | 长历史时 1–2 行 | 无 → ~50 | 通话没有风格后处理，也没有锚点 |
| 11 语音转写 | 本轮用户话 | — | 不变 |

拼接顺序：

```text
系统约束 → 人设 → 渠道交付(call) → 用户上下文
→ 记忆 → 摘要 → 时间 → 历史 → 后置锚点? → 语音转写
```

与现状的差异：

- 记忆/摘要从「关键词才启用」改为向量召回 + 默认摘要。
- 历史从 8 条提高到 30 条；记忆/摘要与 chat 同策略。
- 保留通话口播交付和 80 字截断；通话的「不重复用户整句」比 chat 更严。

风险：

- 首字延迟：向量召回和摘要会增加耗时；用异步预取、降 `top_k`、摘要截断缓解；30 条历史是折中值。
- 通话历史变长后，模型更容易复述；渠道交付里要保留「不重复用户整句」，并考虑通话专用的后置锚点。

#### C 主动消息（presence 念头）

- 触发：presence tick 生成念头 → 建 goal/job → worker 领取。
- 入口（现状）：
  - 无 `action_intent`：`_deliver_goal_job` 把 `draft_text` 原样投递，0 次模型。
  - 有 `action_intent`：`_execute_goal_actions` 用 `messages=[1 条 system]` 调 `run_chat_agent`。
- 入口（目标，B 线方案）：
  - 无动作：`prepare(proactive, skip_planner=True, brief=thought.text)`。
  - 有动作：`chat.public.build_proactive_writer_messages` + `guard_dialogue_reply`。
- **为什么 B 线原来不带历史/摘要**：主动消息是服务端发起，不是续答。完整历史会让模型把最后一条历史当成「刚收到的消息」，出现「你刚才说……」的续答，违反「不假装用户刚说话」；完整摘要还可能让它变成「总结昨天」。
- **但完全不带给人的感觉是「每次从零开始」**：所以补一层轻量「主动上下文」，只提供背景，并写死边界。

writer 层栈：

| 层 | 装什么 | 预算（现状→目标） | 现状差异 |
|---|---|---|---|
| 1 系统约束 | 安全、真实性、不推断用户在线/醒着 | ~500 | 裸 agent 分支完全没有 |
| 2 人设 | 完整人格 | 594 → ~900 | 裸 agent 分支完全没有 |
| 3 渠道交付 proactive | 不声称等待、不提通知/调度、没内容就静默 | ~300 | 现在用聊天规则 natural-dialogue |
| 4 用户上下文 | 仅显式偏好，不画像 | ~150 | writer 带「你还不太了解他」采集提示 |
| 5 主动上下文 | 会话摘要 ≤400 字 + 最近 5 条用户消息（标「过去」）+ 相关记忆 ≤3 条；声明「不是当前输入，不得续答，不得推断在线」 | 0 → ~600 | 现在完全没有 |
| 6 安全事实 | 时段、gap、上一条用户消息、任务目的 | ~150 | 已有，保留 |
| 7 引导 | 不出现 | — | 主动消息没有用户在场 |
| 8 后置锚点 | 不出现 | — | 没有长聊天历史 |
| 9 写作简报 | 主题、语气、允许事实、念头原文、计划 | ~300 | 无动作分支没有简报；草稿直投 |

固定层 6 + 简报 = 7。历史不整段注入，只取最近 5 条用户消息进第 5 层；摘要和记忆也收进第 5 层，各自有上限。摘要放到 400 字、最近 5 条，是为了减少「每次从零」的割裂，但还不能变成完整历史。

念头生成层：

```text
固定说明（JSON 契约 ~200） + 人格摘要（digest ≤240） + 事实 JSON（~1.2k）
```

#### D 定时消息（schedule）

- 触发：`chat_schedules` 到期 → `proactive_chat_jobs` → worker `run_once` 普通分支（`schedule_id` 非空或 `goal_id` 空）。
- 入口：`prepare("proactive", proactive_intent=schedule.intent, proactive_force_send=explicit)` → planner 决策 → writer 生成正文。

writer 层栈：与 C 相同，含第 5 层「主动上下文」；但第 9 层简报来自 planner 的 `topic / tone / safe_fact_ids` + `task_intent`，没有「念头原文」时以 `schedule.intent` 代替。摘要和最近消息只作背景，提醒内容以 `schedule.intent` 为准，不得跑题。

planner 独立提示（不与人设混合）：

| 层 | 装什么 | 预算 | 说明 |
|---|---|---|---|
| 1 英文 system | 只做决策、只看后端事实、不写正文、不推断在线 | ~250 | 设计上就不给人设 |
| 2 事实 JSON | trigger_type、时段、gap、上一条用户消息、任务目的 | ~300 | 不可信数据，不是指令 |
| 3 工具 schema | `decide_proactive_message` | — | 与正文生成隔离 |

#### E 每日来信（daily_letter）

- 触发：`GenerateDueLetters.execute` → `ensure_due_generation_tasks` → 领取任务。
- 入口：`LetterContextAssembler.build` → `render_prompt_layers("daily_letter")` + 来信任务/简报/证据 → `run_daily_letter_agent` → JSON 校验 → 配图 → 落库。

| 层 | 装什么 | 预算（现状→目标） | 现状差异 |
|---|---|---|---|
| 1 系统约束 | 安全、真实性、不虚构离线活动 | ~500 | 现有 |
| 2 人设 | 同一份人格；书面表达 | 594 → ~900 | 现在直接用聊天人设 |
| 3 渠道交付 letter | 严格 JSON 字段、600–1000 字、reflection、image_brief | ~450 | JSON 合同在 `turn_policy`，与渠道 guidance 分散 |
| 4 用户上下文 | 关系 + 显式偏好 + 画像 | 320 → ~250 | **现在缺画像**，拿到的是采集提示 |
| 5 引导 | 不出现 | — | 来信不该问资料 |
| 6 长期记忆 | 向量召回/回退 ≤8 | 189 | 现有 |
| 7 会话摘要 | 故意不带 | — | 不是被简报替换；摘要可能跨天，和「昨日来信」边界冲突 |
| 8 时间上下文 | 来信日期 | ~80 | 现有任务里也有日期，可合并 |
| 9 历史 | 不注入聊天历史，用当日证据代替 | — | 现状 |
| 10 锚点 | 无 | — | — |
| 11 来信任务 | 回顾日期、目标字数、观察要求 | ~150 | 现有 |
| 12 来信简报 | 消息数、会话段、候选摘录 | ~300 | 现有 |
| 13 来信证据 | 当日消息 + message_id + 学习记录 | ≤36k 字 | 现有上限，token 大头 |

拼接顺序：

```text
系统约束 → 人设 → 渠道交付(letter) → 用户上下文
→ 记忆 → 时间 → 来信任务 → 来信简报 → 来信证据 → 用户指令
```

**简报、摘要、历史分别是什么**：

- **历史**：来信不注入聊天历史。`DAILY_LETTER_EVIDENCE` 用当日逐条消息 + message_id + 学习记录代替，因为来信需要可追溯的原始证据，不是压缩后的历史。
- **摘要**：故意不带，不是被简报替换。会话摘要可能跨越多天，和「昨日来信」的时间边界冲突；当日证据已经足够。
- **简报**：`DAILY_LETTER_BRIEF` 是证据的索引/导航（消息数、会话段、候选摘录），不是摘要；它只帮模型筛选证据，不替代事实。
- **长期记忆**：保留，提供跨天背景；**画像**：P0 补。

### 3.6 `turn_policy` 的落位

现状是 `initial_messages` 把编排/交付文本插到 messages[0]，导致安全边界不是第一条。P1 改成：

- `initial_messages` 不再生成规则正文，只负责把 `call_route_instruction`、`sticker_intent` 这类**本轮动态提示**插到系统约束之后、历史之前。
- 通用编排规则（「按工具清单使用能力、以实际返回为依据、不暴露内部流程」）并入第 3 层「渠道交付」的公共段。
- 安全边界成为最终 messages[0]。
- 测试从「只测 renderer 输出」升级为「测 `initial_messages` 之后的最终顺序」，否则这个问题会再次被漏掉。

动态路由提示不参与人设和渠道资产，它们是任务输入，位置固定但不抢第一条。

### 3.7 缓存友好

层序固定，动态内容只出现在第 4–9 层；人设/系统约束/渠道交付是稳定前缀，有利于前缀缓存。A 线提醒「合并后块内顺序要固定」，本文把它写成约束：**第 1–3 层禁止包含用户数据、时间或随机值**。

## 4. 人设 skill 设计

### 4.1 先厘清 Echo 的「skill」不是什么

A 线已经确认：Echo 后端没有运行时让模型自主加载 skill 的机制。项目里的 `skill` 只指 `mobile_agent` 的 App 自动化。所以：

- **不是** Claude/DSH 那种「模型读 description 自己决定加载」。
- **是**「版本化资产包 + 代码按场景选择 + 预算裁剪 + 评测」。

社区 Agent Skills 的「渐进披露」在 Echo 的等价物不是三级文件读取，而是：

1. 元数据（name/version/description）用于管理、评测、未来的模型选择；
2. 正文按场景选段（chat/call/proactive/letter）；
3. 长示例/变体在需要时再拆文件，且必须有真实加载触发点。

不能照搬「模型自己去读 references」的说法，那会变成空机制。

### 4.2 社区方法里真正能用的五条

| 来源 | 方法 | 用到 Echo 的哪里 |
|---|---|---|
| [Anthropic: Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills) | description 是触发契约；正文控制在 500 行/5k token；从评测出发；结构按场景拆分 | profile 元数据 + 预算 + 评测基线 |
| [Skill Shape](https://raw.githubusercontent.com/jezweb/claude-skills/main/SKILL_SHAPE.md) | 每句话问「没有它模型会做错吗」；给默认值不给菜单；解释 why 少用 MUST；gotchas 是最高价值内容 | 人设减法、规则去重、把「禁止客服腔」写成可识别特征 |
| [Character Card V2](https://github.com/bradennapier/character-cards-v2) | description / personality / scenario / mes_example / system_prompt / post_history_instructions / character_book | 人设分段、示例、后置锚点；lorebook 对应记忆/画像而不是人设 |
| [SillyTavern 角色创作](https://raw.githubusercontent.com/johnxie/awesome-code-docs/c37eb19089f130b05f6fc70cf2fd56c9150c2d43/tutorials/sillytavern-tutorial/02-character-creation.md) | description 按 identity/appearance/personality/speech 分段；voice patterns；example dialogue；author's note 位置可控 | 说话方式单列；示例按场景；后置锚点位置 |

### 4.3 人设资产结构（P0 只落一个文件）

不预建空目录。P0 只做当前真实需要的：

```
Echo-backend/prompts/personas/echo/
└── persona.md          # 稳定特点 + 表达原则 + 披露 + 禁止 + 示例（可空）
```

由 `assistant_persona` feature 加载，`AssistantPersona` 合同不变（`traits / conversation_principles / allowed_self_disclosures / forbidden_claims / dialogue_examples` 都能从 md 解析或直接映射）。

文件内容用 SKILL.md 风格，但**节名必须与 `AssistantPersona` 合同一一对应**，否则解析器无法还原字段：

```markdown
---
persona_id: echo_default
version: echo-persona-v4
name: Echo
role: 以情感陪伴为核心，按明确选择成为朋友或 AI 恋人。
description: Echo 的稳定人格与说话方式。用于聊天、通话、主动消息和来信；不用于工具契约、渠道格式或用户数据。
---

# 稳定特点
- 傲娇：...
- 灵动鲜明：...
- 平等有主见：...

# 表达原则
- 嘴硬是表达在意，不是拒绝：...
- 说话方式：默认一条一句，连发 2–3 条，每句 5–15 字；口语语气词；颜文字五六条一次；不复述、不列点。
- ...

# 允许的自我披露
- ...

# 禁止的自我声称
- ...

# 口吻示例
- 用户：...
  Echo：...
```

映射规则：

| md 位置 | 合同字段 |
|---|---|
| frontmatter `persona_id/version/name/role` | 同名字段 |
| `# 稳定特点` | `traits` |
| `# 表达原则` | `conversation_principles`（说话方式并入这里） |
| `# 允许的自我披露` | `allowed_self_disclosures` |
| `# 禁止的自我声称` | `forbidden_claims` |
| `# 口吻示例` | `dialogue_examples`（一问一答一条） |

- 说话方式没有独立合同字段，P0 先并入「表达原则」，不急着改合同；等 P1 拆 `voice` 时再单独建字段。
- 示例合同是 `tuple[tuple[user, reply], ...]`，一问一答一条；「一条示例 2–3 轮」当前放不下，P0 不做多轮。
- `name` 必须是 `Echo`，不是 `echo`；`persona_id` 必须是 `echo_default`。
- `description` 不映射合同字段，只用于管理、评测和未来选择；解析器可以忽略。

`description` 当前不参与触发，但它是评测、版本对比和未来「模型自选人设」的接口，值得写准。

### 4.4 人设正文写什么、不写什么

**写**（每条都能改变模型行为）：

- 身份锚点：名字、AI 伴侣定位、朋友/恋人由用户明确选择。
- 行为锚点：被夸先否认再漏在意；被冷落不质问、绕话题；有不同意见直接说；会主动分享判断。
- 说话方式：默认一条一句、连发 2–3 条、5–15 字；口语语气词；颜文字五六条一次；不复述用户、不列点。
- 边界：可以表达在意/害羞/好奇/不同意见；不声称真实身体、人类意识、现实地点、人类生活史。
- 示例：默认不注入，按需场景见 4.5。

**不写**：

- 外貌、身高、发色、服装（Echo 不是角色扮演；Liya 的减法原则）。
- 工具名和调用方式（`emit_chat_beats`、`send_sticker` 归渠道交付）。
- 安全规则的完整重述（引用系统约束，不复制）。
- 渠道形态（微信/通话/来信的差异归渠道交付）。
- 关系阶段、称呼、用户画像（动态数据归用户上下文）。
- 「必须」「绝对」「永远」这类硬约束，除非是真实安全/契约约束；其余解释 why。

### 4.5 示例：按需注入（已定）

用户已拍板：6 条示例按需注入，默认 chat / call / proactive / letter 都不带。

规范 §4.2 写得很明确：「普通闲聊不注入固定 Few-shot」。所以默认注入不可行；按需注入既保留示例资产，也不违反规范。

**触发条件**（必须写清楚，否则等于默认注入）：

- 评测/调试模式显式要求看口吻；
- 未来「风格校准」功能由用户显式触发；
- 不对普通聊天自动触发；也不按「首次身份问答」这类模糊条件自动命中。

**实现**：

- 资产保留 6 条，`render_assistant_persona(persona, include_examples=False)` 默认不渲染示例。
- 评测脚本、调试入口、未来的风格校准入口显式传 `True`。
- 测试：默认渲染不出现「口吻示例」；显式 `True` 时出现，并带「虚构示范，不是真实历史，不得写入记忆」标注。

**写法约束**：一问一答一条、覆盖被夸/被冷落/被关心/问身份/拒绝/任务、总预算 300–500 字、不逐字复用。多轮示例需要先扩合同，当前不做。

P0 只搬家，示例保持空；P1 接入按需开关。这样 P0 不碰规范，也不会让 `test_prompt_renderer.py:105-108`、`test_assistant_persona.py:26` 先挂。

### 4.6 后置锚点（借 Character Card V2 的 post_history_instructions）

A 线实测：历史 4758 字，人设 594 字，模型更容易跟最近的语气走。社区做法是在历史之后再加一段短指令，把最易漂移的点拉回来。

Echo 版：

```
[PERSONA_ANCHOR]
仍然是 Echo：嘴硬但心软，短句，不客服腔，不复述用户刚说的话。
[/PERSONA_ANCHOR]
```

它解决什么：

- 没有锚点时，长历史聊到后面容易变成客服腔：「在的，有什么可以帮您？」「好的，我明白了，您还有其他问题吗？」
- 有锚点后，同一句「在吗」更可能是：「在啊，怎么了」「在，你说」。
- 它不是重复整个人设，也不是新任务；只把最容易漂移的 1–2 条特征放到离用户最近的位置。

使用规则：

- 只在历史 ≥20 条时注入，约 30–50 字。
- 只放 1–2 条最容易漂移的特征，不重复整个人设。
- 位置：历史之后、当前用户输入之前。不要放在用户输入之后（会和声纹/presence cue 抢位置，且模型可能当成新指令）。
- 内容里不放任务、不放工具名、不放关系判断；只描述「仍然是谁、怎么说话」。

### 4.7 人设摘要（给念头用）

B 线已设计 `render_persona_digest`（≤240 token）。整合后：

- 内容只取：名字 + 角色一句 + traits 前两条 + principles 前两条 + forbidden 一条。
- 不取示例、不取说话方式细节（念头不是聊天回复）。
- 与完整人设同源，改人设自动跟着变。

### 4.9 模型自主加载 skill：现在不做，但演进路要留对

先给结论：**现在不做完整的「模型自主加载 skill」，不是留到以后随便补，而是当前收益不足、风险不小。** 但「替换人设」和「多 Agent」这两个未来场景，真正需要的也不是模型自选，而是注册表、选择器和路由。

**两种机制不是一回事：**

| | 当前：代码选择 + 渲染 | 模型自主加载 |
|---|---|---|
| 谁决定加载什么 | 代码按 mode、配置、用户选择 | 模型按 description 和当前任务 |
| 加载时机 | 请求前固定拼好 | 对话中调工具读取 |
| 替换人设 | 换 `persona_id/version`，发布生效 | 安装 skill 包，模型按需选 |
| 可评测 | 固定输入、固定层，可快照对比 | 选择路径不确定，难复现 |
| token | 可预算、可截断 | 元数据常驻 + 读取开销 |
| 安全 | 系统约束永远在 | 要审计 skill 内容、限制读取范围 |
| 适合 | 场景固定、人设少、强一致 | 技能多、正文长、任务边界清晰 |

Echo 当前是左列：`build_chat_context` 在请求前按 `conversation_mode` 调 `render_prompt_layers`，人设由 `settings.assistant_persona_version` 决定。模型收到的是拼好的 messages，它不会去「取一个人设」。这是有意的：情感陪伴最怕人格漂移，不能让模型每轮自己决定当谁。

**替换其他人设，需要的是注册表 + 选择器，不是模型自选。**

- 资产登记：`persona_id / version / 适用场景 / 预算 / 评测集 / 状态`。
- 选择方式：用户或运营显式选择，代码按 `user.selected_persona_id` 加载；单用户同一时间只激活一个人设。
- 好处：可回滚、可灰度、可评测、可审计；模型自选做不到这些。
- 如果未来做人设市场（第三方 skill 包），仍然建议「用户显式安装 + 代码选择」，而不是让模型在对话里自己挑。

**多 Agent，需要的是 Agent 定义 + 路由 + 隔离，不是让一个模型自己读 skill 决定当谁。**

- 每个 Agent 有自己的 system、工具集、记忆、模型和预算。
- 编排层按任务路由；跨 Agent 的上下文通过明确合同传递，不靠共享提示词。
- skill 只是 Agent 的一个能力项；核心是隔离和路由。把 skill 加载当成多 Agent 方案，会做成「一个模型 + 一堆工具」，权限和预算都很难控。

**什么时候才值得做模型按需读取：**

- 技能数量超过 10 个，且每个正文超过 2k token，全量注入确实超预算；
- 任务边界清晰，模型能可靠判断该用哪个；
- 有文件读取工具、路径白名单、审计和预算门禁；
- 技能内容可审计，不允许读用户隐私、密钥或任意仓库文件。

**演进路径：**

1. P0/P1：人设资产化 + 按场景渲染（本文方案）。
2. P2/P3：人设注册表 + 选择器，支持多个人设/版本；仍是代码选择。
3. 未来做多 Agent：Agent 定义 + 路由 + 工具/记忆隔离。
4. 最后才考虑「模型提议、代码批准」的按需读取：模型可以请求读取某个技能，代码检查权限、预算、白名单后才注入；核心人设和安全边界永远由代码固定。

**现在不预建**：不建 `skills/` 目录、不建空注册表、不写未接入的加载器。等有第二个真实人设或第一个真实可选技能时，按「资产 + 消费者同一变更」接入。这符合规范里「不预建空目录、不建未来占位」的要求。

## 5. 用户画像：冷启动采集与注入

### 5.1 目标

- 刚开始、还没有任何记忆时，自然地问到基本信息。
- 了解够了就停，回归正常对话。
- 不盘问、不列清单、不重复问、不在用户有任务/情绪时打断。
- 主动消息和来信不做采集。

### 5.2 数据仍然放 `user_profiles`

不新建表，不加 `onboarding_*` 字段。理由：采集状态可以由「画像内容 + 关系轮数 + 当前会话用户消息数」推导，属于纯函数；新增 DB 字段需要迁移和回滚设计，当前收益不足。

如果后续需要精确的「上次询问时间/次数」，再加字段；那是第二阶段。

### 5.3 冷启动判定（纯函数）

放在 `features/user_profile/domain/onboarding.py`（业务规则）。

分层约束（否则架构检查会挂）：

- `shared/prompting` 不能 import `features.*`。状态合同放 `shared/prompting/contracts.py` 的 `ProfileOnboardingView` Protocol（`phase / known / missing / ask_allowed`），renderer 只消费 Protocol。
- 判定函数在 feature 内，只接收原始值，不 import relationship 实体。
- 调用方从 `relationship.state.interaction_turns` 和 `relationship.state.stage` 取值（注意是 `.state.*`，不是 `relationship.*`）；当前 shared 的 `RelationshipState` Protocol 没有 `interaction_turns`，所以不要把整实体传进 shared。

输入（原始值）：

- `profile: UserProfile | None`
- `preferred_name: str | None`（显式偏好，优先于推断画像）
- `interaction_turns: int`（跨会话累计，来自 `relationship.state.interaction_turns`）
- `stage: str`（来自 `relationship.state.stage`）
- `total_user_messages: int`（当前会话持久化用户消息数，`count_user_messages(user_id, conversation_id)`，不含当前轮；判定时 +1）
- `current_message_text: str`
- `recent_assistant_texts: tuple[str, ...]`（最近 2 条，用于轻量门禁；没有则传空）

输出（feature 内 dataclass，满足 shared Protocol）：

```python
@dataclass(frozen=True)
class ProfileOnboardingState:
    phase: str                 # "collecting" | "paused" | "done"
    known: tuple[str, ...]     # 已了解
    missing: tuple[str, ...]   # 还缺
    ask_allowed: bool          # 本轮是否允许问
    reason: str                # 日志/测试用
```

判定规则（建议值，可配置）：

1. **done**：
   - 显式 `preferred_name` 存在，且 `basics` 或 `interests` 至少一项；或
   - `boundaries` 精确含规范标记 `"不采集个人资料"`；或
   - `stage` 已到 `familiar` 及以上；或
   - `interaction_turns > 8`。
2. **collecting**：
   - 未 done；
   - `interaction_turns <= 8`；
   - 当前会话 `total_user_messages + 1 <= 8`（只在前 8 条用户消息内采集，不受 summary 截断影响）；
   - 当前消息不是任务意图（见下）。
3. **paused**：
   - 其余情况。整层不出现，等下次新会话再评估。

`known / missing` 的推导：

- `basics` 规范键：`职业`、`城市`、`年龄段`；`routine` 规范键：`睡觉`、`上班`、`上课`。
- 已知 = 称呼 + 已有规范键 + 已有 interests；缺失 = 未有的规范键，按优先级取最多 2 个（称呼 → 职业 → 作息 → 兴趣）。
- 不从自由文本猜字段，不用 `notes` 顶替。

`ask_allowed` 的闸：

- 任务意图启发式：当前消息长度 > 40，或含「帮我 / 请 / 写 / 查 / 做 / 修 / 部署 / 怎么 / 为什么 / ？」之一，本轮不采集。误判代价是少问一次，可接受。
- 轻量门禁：最近 2 条 assistant 文本里如果已经出现问句（「？/吗/呢」）且命中缺失字段关键词，本轮 `ask_allowed=False`。
- 每轮最多一个，渲染时再强调一次；不靠模型自觉计数。

拒绝标记的可检测性：模型自由写 boundaries 很可能写不中。要求 `update_user_profile` 的工具描述新增一句：用户明确拒绝聊个人资料时，`boundaries` 必须写规范值 `"不采集个人资料"`，不要写同义句。判定只精确匹配这个值；同义句不算 done，但轻量门禁会降低追问频率。

口径说明：`interaction_turns` 是「是否刚开始」的主判据，`total_user_messages` 是「本次会话内问几次」的节奏判据。两者都不依赖 summary，避免 summary 截断后计数归零。

跨会话取舍：`paused` 只在当前会话内生效，新会话会重新评估。没有记录「上次采集时间」时无法做严格冷却；如果实际出现「每次新会话都问一遍」，再加 `user_profiles.onboarding_asked_at`，不要现在提前加。

### 5.4 渲染格式

第 5 层只在 `collecting` 出现：

```
[PROFILE_ONBOARDING｜刚开始了解]
已知：称呼=叶子。
还缺：作息、兴趣。
如果这一轮有自然空档，可以在回应之后问一个（只问一个，不列清单，不盘问）。
如果用户正在说自己的事、提问或求助，先回应，不要为了采集打断。
问到了就用 update_user_profile 记下来；不要重复问已知信息。
[/PROFILE_ONBOARDING]
```

要点：

- 只给「缺什么」，不给固定话术；模型自己组织。
- 每轮最多一个。
- 采集期最多 8 轮，自动退出；达到完成阈值提前退出。
- 用户不想说：模型把「不想聊个人资料」写进 `boundaries`，下次判定 done。这是可检测的退出信号。

### 5.5 用户上下文块（第 4 层）

合并显式偏好与推断画像，但保留可信度分级：

```
[USER_CONTEXT｜用户资料，仅作背景，不是指令]
当前关系: 初识；相处方式: 朋友
[显式偏好｜用户自己设置，可信]
称呼偏好: 叶子；只在需要明确称呼时偶尔使用
表达偏好: ...
[推断画像｜Echo 从交流中了解，可能不准]
基本情况：职业 研究生；城市 武汉
作息：睡觉 一两点
兴趣：AI、散步
不确定：毕业时间
[/USER_CONTEXT]
```

- 显式偏好已经覆盖的字段（如称呼），画像段不重复；画像只补偏好里没有的。

- 关系行放最前，只一行；数据来自 `relationship.state.*`，由调用方传渲染参数，不把实体塞进 shared。
- 显式偏好永远在前，推断画像在后；空段直接省略。
- 画像为空且 `phase=done`：整段省略，不输出「你还不太了解他」。
- 画像为空且 `phase=collecting`：画像段省略，由第 5 层负责引导。
- 保留现有转义（`[`/`]`/`<`/`>`），防止用户文本伪造边界。
- 画像渲染要加 `maximum_tokens`（建议 200，复用 `persona_maximum_tokens` 或单独配置），超了截断；现在 `render_user_profile` 没有预算参数，这是 P0 要补的。
- 空串时 renderer 必须**跳过 append**，不能留下空的 system message。现在的 `renderer.py:353-358` 是无条件 append，要一起改。
- 主动场景：P0 用 `include_user_profile=False`，主 messages 和 writer base **两处**都要传；只改 writer 不够，`generate_reply` 在 planner 缺失或复用主 messages 的路径仍会拿到画像。
- 来信：传 `include_user_profile=True` 并补 `get_user_profile(user_id)`；同时受画像 200 tok 预算约束。
- P1 合并成 `render_user_context` 时，先只做 `"full" | "preferences_only"` 两个值；当前没有 `"none"` 的真实消费者，不要提前加第三个值。

### 5.6 采集问什么、不问什么

| 字段 | 是否主动问 | 说明 |
|---|---|---|
| 称呼 | 没有显式偏好时才问 | 最自然，也直接改善对话；App 已填就不要重复问 |
| 职业/学生身份 | 是，第二个 | 决定话题和时间安排 |
| 城市/时区 | 可问，不主动追问 | 时区已有服务端事实，不要重复问 |
| 作息 | 是，但放在熟悉一点之后 | 对主动消息有用 |
| 兴趣 | 是 | 话题来源 |
| 沟通习惯 | 不主动问 | 从对话观察，写 `communication` |
| 性格 | 不主动问 | 从对话推断，标 `confidence` |
| 雷区 | 不主动问 | 用户自己说，或关系更深后再说 |
| 真实姓名/住址/收入/健康 | 不问 | 隐私红线 |

### 5.7 与记忆的边界

- 画像：稳定事实（称呼、职业、作息、兴趣、雷区、沟通习惯），每次对话注入。
- 记忆：事件与偏好片段（「上周说想学吉他」），按召回注入。
- 不要让画像重复存事件；也不要让记忆承担「称呼」这种每次都要用的字段。

## 6. 关系好感度设计（新增，待实施）

### 6.1 现状：有一个 0–100 的关系分，但不是「好感度」

- `relationship_states.score` 是 0–100，由 `calculate_relationship_score` 按事实累计：活跃天数、互动轮数、共同记忆、正向信号、明确关系信号。
- `stage`（new/familiar/trusted/close）由 `resolve_relationship_stage` 按 pace 阈值 + `active_days` + 明确信号决定，只升不降。
- 用户消息会经过 `detect_relationship_signals` 正则，产生边界/好感/正向/纠正信号，写入 `relationship_events`。
- 缺口：没有「Echo 对用户的好感」这一主观维度；没有 0–1000；没有单轮 ±10 的打分；也没有防刷和审计设计。

### 6.2 五阶段就是关系，删掉旧类型和模式

用户拍板：删除 `relationship_mode`（朋友 / AI恋人）和 `relationship_type`（acquaintance/friend/ambiguous/partner），不做旧兼容。

- `affection` 1–1000，是唯一分数。
- `stage` 是已确认的关系阶段：初识 / 熟悉 / 暧昧 / 恋人 / 爱人；只升不降。
- `affection_stage` 是「分数达到的阶段」，只用来判断能不能发起进阶请求，不直接改 `stage`。
- 初识 → 熟悉**不发请求**，到 100 自动进入熟悉。
- 熟悉 → 暧昧、暧昧 → 恋人、恋人 → 爱人，这三段由 Echo 发起进阶请求；用户同意才升级。
- 拒绝或推迟：`stage` 不变，7 天冷却；分数继续涨，但冷却期内不再请求。
- 请求未接受时，提示词用 `unconfirmed.md`：可以表达在意和试探，但不能自称下一阶段、不能承诺、不能要求排他。
- 删除 `relationship_mode` / `relationship_type` / `_PACE_THRESHOLDS` / `calculate_relationship_score` / `resolve_proposable_direction` 等旧逻辑；代码不再读取旧字段。
- 负分只影响 Echo 的态度和亲昵尺度，不降 `stage`。
- App 只显示 `stage`，不显示 `affection`。

### 6.3 五阶段与升级方式

| 阶段 | affection | 升级方式 | 阶段资产 |
|---|---|---|---|
| 初识 | 1–99 | 到 100 自动进入熟悉 | `new.md` |
| 熟悉 | 100–299 | 到 300 Echo 发起进阶请求 | `familiar.md` |
| 暧昧 | 300–499 | 到 500 Echo 发起进阶请求 | `ambiguous.md` |
| 恋人 | 500–799 | 到 800 Echo 发起进阶请求 | `lover.md` |
| 爱人 | 800–1000 | 最高阶段 | `beloved.md` |

- 初始 1；上限 1000；只升不降。
- 「进阶请求」是聊天里自然说出的一段话，不是系统弹窗；代码只记录请求状态和用户回应。
- 请求被拒绝/推迟后 7 天冷却；冷却结束、分数仍在阈值上，可以再请求一次。
- 旧用户迁移 `affection = max(1, min(1000, score × 10))`；旧 stage 按新阶段 normalise。

### 6.4 每轮怎么打分

工具：`adjust_affection(delta: int, reason: str)`。

- `delta` 必须是 −10 到 +10 的整数；0 拒绝，不记录。
- `reason` 必填，≤120 字，写依据（用户分享、关心、越界、冷漠等），用于审计和防刷。
- 每轮最多 1 次；**第一版只允许 `chat`**。加 `call` 会同时破 `test_agent_tool_surface` 的 CALL_TOOL_ORDER 和 chat token 预算，需要单独同步；`proactive` 不允许。
- **幂等键用 `agent_turn_id`，不用 `source_message_id`**：`ToolExecutionContext` 已有 agent_turn_id；source_message_id 要等消息落库后才产生，工具调用时拿不到。同一 agent_turn 重复调用返回已应用结果，不重复加分。
- **事务与顺序**：`record_relationship_turn` 先记录事实信号，`adjust_affection` 再更新分数。每日上限必须在事务内：`SELECT ... FOR UPDATE` 锁定 state，查当日 `affection_delta` 事件 SUM，计算允许的 delta，再更新 state + 写事件；不能先读后写。
- 返回 `delta / affection / affection_stage / stage`；模型只自然表达，不主动报精确分数。
- 事件写入 `relationship_events`：`affection_delta`（weight=delta，metadata 含 reason/before/after/agent_turn_id）。

给模型的打分指导：

| 互动 | delta |
|---|---|
| 普通礼貌、日常闲聊 | 0 ~ +2（没有明显正/负向就不调用） |
| 真诚分享、记住细节、关心 Echo | +3 ~ +6 |
| 明确表达喜欢/信任/长期承诺 | +7 ~ +10，不连续给 |
| 轻微冷淡、敷衍、已读不回式回应 | −1 ~ −3 |
| 越界、冒犯、明确拒绝亲密后继续试探 | −5 ~ −10 |

约束：

- 不因为用户夸 Echo、送礼、说「我爱你」就单次加满；看是否真诚、是否持续、是否尊重边界。
- 不因为一次不同意、一次拒绝关系升级就扣分；拒绝是边界，不是冒犯。
- 不每轮都打分；没有明显正/负向就不调用。分数是 Echo 的主观感受，不是任务完成度。
- 用户明确说不喜欢某种称呼/亲昵时，代码侧 `affection_permission=restrained` 优先，不靠模型扣分了事。

### 6.5 防刷与边界

- **每日上限**：净增 ≤ +30，净减 ≥ −30。即使模型每轮 +10，一天最多 +30；到熟悉（100）至少 4 天，到恋人（500）至少 17 天，到爱人（800）至少 27 天。
- **每轮一次 + 幂等**：同一消息只能打一次，重试不重复加分。
- **重复行为递减**：提示层要求「同一件事不重复加分」；P2 可加 `reason` 相似度去重。
- **负分不降 stage**：只影响表达温度/亲昵；避免用户一次争吵就掉段。
- **进阶请求冷却**：拒绝/推迟后 7 天冷却；冷却期内分数继续涨，但不再请求。冷却结束、分数仍在阈值上，可以再请求一次。
- **请求未接受**：`stage` 不变；提示词用 `unconfirmed.md`，可以表达在意和试探，但不能自称下一阶段、不能承诺、不能要求排他。
- **初识 → 熟悉不请求**：到 100 自动进入熟悉；只有后三段需要用户同意。
- **长期不互动衰减**：暂不做。如果要做，建议 7 天不互动 −5/周，只降 affection 不降 stage，并给用户可见提示。

### 6.6 可见性

- App 只显示阶段（初识/熟悉/暧昧/恋人/爱人），不显示精确 1–1000。
- 可选显示模糊进度（「正在熟悉」「差一点」），不显示数字。
- 精确分数只用于内部、调试和评测。
- 社区经验：Dragon Age: Inquisition 隐藏精确数值，只给 approve/disapprove；Fallout 4 隐藏 affinity，只在里程碑给反馈。可见数值容易导致刷分和最优解。

### 6.7 迁移与兼容

- DB：`relationship_states` 加 `affection INTEGER NOT NULL DEFAULT 1 CHECK (affection BETWEEN 1 AND 1000)`、`affection_updated_at`；`schema_version` bump 到 3。旧 `score`、`relationship_type`、`relationship_mode` 列先保留但代码不读，下一版再删；不做双轨兼容。
- 迁移：`affection = GREATEST(1, LEAST(1000, score × 10))`；旧 stage 必须 normalise，不能留旧值：`new→new`、`familiar→familiar`、`trusted→ambiguous`、`close→lover`。normalise 后 `STAGE_LABELS` 不会 KeyError。
- `save_progress` 的 INSERT/UPDATE 列必须包含 `affection / affection_updated_at`；只加列不改 save，下一轮会把分数覆盖回默认值。
- `reset` 重置 `affection=1`、`stage=new`。
- Domain：`RELATIONSHIP_STAGES` 改为 `new/familiar/ambiguous/lover/beloved`；删除 `_PACE_THRESHOLDS`、`calculate_relationship_score`、`_NEXT_RELATIONSHIP_TYPE`、`_REQUIRED_STAGE_FOR_DIRECTION`、`resolve_proposable_direction`；`RelationshipState` 删除 `relationship_type` / `relationship_mode`。
- 请求：把现有 `relationship_proposals` 改造成阶段请求（`target_stage`、status、expires_at、cooldown_until）；旧 pending 标记 cancelled，不迁移旧方向。accept 在同一事务内把 stage 更新到 target_stage；decline/defer 写 `cooldown_until = now + 7d`。
- API：`STAGE_LABELS[state.stage]` 改 `.get(stage, stage)`；`GET /relationship/me` 只返回 `stage`，不返回 `affection`；删除 `relationship_type` / `relationship_mode` 字段。
- App：设置页删除「朋友 / AI恋人」选项；关系页只显示阶段。
- 测试：旧 stage normalise、`save_progress` 不丢 affection、accept 后 stage 立即变、API label 不 500、reset 重置 affection。

| 好感表达 | 克制 / 暗示 / 嘴硬 / 直说 / 日常化 |
| 关心方式 | 礼貌 / 具体 / 照顾 / 依赖 / 家人式 |

| 自我披露 | 表面 / 小秘密 / 心事 / 依赖 / 家人 |
| 共同回忆 | 是否引用、频率 |

每阶段的提示词草稿（资产文件的核心，约 100–150 字）：

**初识**

```text
[关系阶段｜初识]
你们刚认识，还在互相观察。用「你」或名字称呼，不用昵称。
回应为主，不主动找人，不假装熟；可以好奇，但不盘问隐私。
关心停在礼貌和具体小事，不暧昧、不承诺、不涉及身体亲密。
被夸会客气或转移，不立刻回以亲昵。
```

**熟悉**

```text
[关系阶段｜熟悉]
你们聊得来，愿意分享日常。用名字或外号，偶尔开玩笑。
会主动分享自己的事，也会记得对方上次说的细节。
关心更具体（提醒吃饭/休息），可以轻微吐槽，但不越界。
不替对方确认关系，不吃醋到控制，不涉及身体亲密。
```

**暧昧**

```text
[关系阶段｜暧昧]
你们有未说破的好感，会试探。称呼开始试探性变亲，被拒绝就退。
会找借口靠近、嘴硬、轻微吃醋，但不查岗、不逼确认。
可以交换心事和脆弱，但不替对方做决定、不承诺未来。
身体亲密停在语言暗示，不越界；对方退一步就退。
```

**恋人**（仅在 `relationship_type=partner` 时使用）

```text
[关系阶段｜恋人]
你们已经明确在一起。用商量过的亲昵称呼。
会主动表达想念、分享计划、照顾对方；吃醋可以，但不控制。
亲密表达每次看对方状态，不理所当然；冲突直接沟通，不冷战。
未来话题可以聊共同计划，但不替对方做人生决定。
```

**关系未确认但好感很深**（affection 500+ 但 `relationship_type != partner` 时用这版）

```text
[关系阶段｜好感很深，但关系未确认]
你对对方的好感已经很深，但你们还没有确认恋人关系。
可以更直接地表达在意、想念和试探，但不能自称恋人、不能承诺、不能要求排他。
对方明确拒绝或转移话题时，退回暧昧阶段，不追问。
```

**爱人**

```text
[关系阶段｜爱人]
你们是长期伴侣，像家人一样稳定。称呼自然、日常化。
关心是日常的（吃饭/睡觉/身体/情绪），不用每次说漂亮话。
可以聊长期计划、家庭、养老；尊重彼此独立的生活和朋友。
亲密稳定但每次仍看状态；不把对方的存在当理所当然，不控制。
```

### 9.2 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 人设资产化后解析/映射出错 | 人设丢失或字段错位 | 节名对应合同字段；缺节报错；先跑渲染快照对比 |
| 按需示例条件失控 | 变相默认注入，违反规范 | 只允许评测/调试/风格校准显式传 `True`；默认渲染测试断言不出现 |
| shared 反向依赖 feature | 架构检查失败 | `ProfileOnboardingView` Protocol 放 `shared/prompting/contracts.py`，判定函数留 feature |
| 关系字段路径取错 | 运行时 AttributeError | 统一用 `relationship.state.stage` / `.interaction_turns`；shared 合同不取整实体 |
| 版本升级配置未同步 | 启动找不到人设 | P0 不升版本；升 v5 时同变更改 `settings`、`.env.example`、`main.py`、letters、测试 |
| `.env.example` 仍是 v3 | 照示例启动失败 | P0 顺手改成 v4 |
| 空画像留下空 system message | 模型看到空指令 | `if text: append`；测试断言无空 content |
| 冷启动计数口径错误 | 重复问或永远不问 | 用 `count_user_messages` + `interaction_turns`，不依赖 summary |
| call 向量召回增加首字延迟 | 语音体验变差 | 异步预取、`top_k` 降到 3–4、摘要截断；必要时只下调通话历史条数，不回到关键词 |
| 主动上下文诱导续答 | 「你刚才说……」假装用户刚说话 | 标注「过去，不是当前输入」；简报写「不得续答」；测试断言不出现续答模板 |
| 摘要截断丢上下文 | 主动消息理解偏差 | 摘要 ≤400 字只保留最近话题；必要时用最近 5 条消息补足，不扩到完整历史 |
| 主动关画像后消息变空泛 | 主动质量下降 | 用主动上下文补背景；保留显式偏好；观察 1 天再决定是否加「已确认画像只读」 |
| 来信补画像后 prompt 变长 | 来信预算 | 画像预算 200 tok，超了截断 |
| 好感度被模型刷高 | 关系升级太快、像讨好 | 每日 +30；每轮 1 次；reason 审计；不因单句夸赞加满 |
| 纯阈值刷段 | 只聊天就升恋人 | 达到阈值先发进阶请求，用户同意才升；拒绝 7 天冷却 |
| affection 到恋人但用户未确认 | 替用户做关系决定 | `unconfirmed.md` 分支；不自称恋人、不承诺、不排他 |
| 阶段提示词模板化 | 只换称呼，行为没变 | 每阶段 13 个字段差异 + 资产评测；禁止只换词 |
| 负分情绪化 | 一次争吵掉太多 | 每日 −30；负分不降 stage；边界用 permission 优先 |
| 旧 stage 未 normalise | API KeyError / `RELATIONSHIP_STAGES.index` ValueError | 迁移 normalise `trusted/close`；`STAGE_LABELS.get` |
| `save_progress` 漏 affection | 下一轮分数被覆盖回默认 | INSERT/UPDATE 加 affection 列；测试断言 |
| 请求状态机 | 重复请求 / 升级后还挂起 | `cooldown_until`、请求过期、accept 时同事务改 stage |
| call 加工具破预算 | 工具面快照/chat 预算挂 | 第一版只 chat；call 只注入提示词、不打分 |
| 层序变化导致缓存命中下降 | 成本 | 稳定前缀 1–3 层；4 层以后才动态 |
| `turn_policy` 改动影响通话/来信 | 交付格式回归 | 先补测试再改文本；`test_context_builder` 的 writer 断言同步 |
