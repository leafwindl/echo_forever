# Echo v1.0.9 当前功能与扩展基线

> 文档用途：作为新增功能前的产品、业务和工程基线。本文只描述当前已经落地或明确关闭的能力，不把未来计划写成已上线功能。
>
> 当前 APK：Android `1.0.9+14`，用户可见版本为 `v1.0.9`
>
> 当前后端：生产分支 `master`，本轮对话/主动消息失败兜底修复部署提交 `62f3d0f`
>
> 更新时间：2026-08-10（Asia/Shanghai）

## 1. 产品定位

Echo 是一个有连续记忆、时间感知和主动联系能力的 AI 陪伴应用。它不是单轮问答页面，而是把聊天、记忆、人物、语音、表情包、每日来信和提醒组织成一条可持久化的陪伴链路。

当前版本的重点不是继续堆叠功能，而是把以下基础能力稳定下来：

- 用户可以随时发送消息，不必等待 Echo 回复完成。
- Echo 的回复可以拆成多条文字，并把表情包作为独立图片消息交付。
- Agent 统一决定是否调用时间、表情包、提醒和联网搜索工具。
- 聊天历史、摘要、长期记忆、关系状态和每日来信分别保存。
- 每日来信只基于真实证据生成，正文与发布时间保持独立。

## 3. 业务模式边界

Echo 当前有四种业务模式。它们共享人格、记忆和关系上下文，但不共享全部工具和交付规则。

| 模式 | 触发方式 | 允许的动作 | 交付方式 |
| --- | --- | --- | --- |
| `chat` | 用户发送文字或表情包 | 时间、搜索、表情包、提醒等 | 异步消息、SSE、多段文字和独立图片 |
| `proactive` | 后端主动任务到期 | 自然问候、有限主动表情包 | 保存聊天消息，再写通知 Outbox |
| `daily_letter` | 每日来信 Worker | 读取昨日证据并生成信件结构 | 来信页面独立展示，不写入聊天框 |
| `call` | 用户主动开始通话 | 对话回复，不使用表情包工具 | 同步返回 TTS 音频 |

通话模式明确禁止搜索、选择和发送聊天表情包，也不创建主动聊天任务或通知。

## 4. 对话业务逻辑

### 4.1 用户消息接收

```text
Flutter 生成 client_message_id
  -> 立即显示用户消息（sending）
  -> POST /chat/messages
  -> 服务端鉴权、校验、幂等检查
  -> chat_messages 写入用户消息
  -> 创建或追加 chat_turn_job
  -> 返回 202 和服务端 message_id
  -> APP 将消息置为 sent
```

用户不需要等待模型完成即可继续发送下一条文字或表情包。`client_message_id` 是重试幂等键，服务端消息 ID 是最终排序事实。

### 4.2 连续消息批次

当前默认窗口：

```text
静默窗口：2500 ms
最长等待：10000 ms
默认批次上限：8 条消息或 6000 个字符
```

同一窗口内的多条消息仍分别显示，但会作为一个 `Input Batch` 交给一次 Agent Turn：

```text
User Message × N
  -> Input Batch
  -> Agent Turn
  -> Reply Group
  -> Delivery Message × N
```

同一会话最多同时运行一个 Agent Turn。批次封口后新消息进入下一批，不追加到已经开始推理的批次。

当批次同时包含文字和用户表情包时，文字原文完整参与上下文；表情包只注入服务端确认的语义标签，不把文件名、描述词、URL 或图片二进制作为额外长文本输入。

### 4.3 时间感知

每轮 Agent 上下文固定注入：

- 当前本地日期和时间。
- 星期。
- 时段：凌晨、上午、中午、下午、晚上、深夜。
- 用户时区和 UTC 偏移。
- 当前消息与上一条用户消息之间的间隔状态。

历史消息会带本地时间标记，例如：

```text
[消息时间 2026-08-10T11:02:03+08:00 周一 上午]
```

两条消息间隔达到 30 分钟时插入会话时间边界，明确告诉 Agent 边界两侧不是连续即时聊天。对“刚刚、待会、等会、一会儿、上午、下午、晚上、昨天、今天、明天”等表达由服务端先解析为时间范围，再交给模型。

时间表达只代表范围，不代表事情已经完成：

```text
用户：下午准备干活
正确理解：用户计划在下午开始工作，事情未必已经完成
错误理解：下午工作已经顺利结束
```

```text
用户：我上午去了一趟医院，晚上再聊
正确理解：上午的事情已经发生；晚上是未来时间范围
```

Agent 不得只根据历史消息猜当前时段，必须使用本轮注入的当前时间。

### 4.4 Echo 回复交付

Agent 可以返回一至三段文字和最多一张表情包。交付层只使用服务端确定的延迟：

| 交付内容 | 默认延迟 |
| --- | ---: |
| 第一段文字 | 立即 |
| 第二段文字 | 1200 ms |
| 第三段文字及以后 | 2000 ms |
| 独立表情包 | 1000 ms |

这些延迟只营造“正在输入”的视觉节奏，不改变数据库中的真实创建时间，也不让 LLM 自由决定等待时间。

### 4.5 失败和重试

普通用户聊天失败时，用户可以看到失败提示并重新发送。

主动聊天没有等待中的用户消息，因此不能使用“再和我说一次”这类用户回合兜底：

```text
主动 Agent 空输出/截断/异常
  -> Agent run = failed
  -> proactive job = suppressed
  -> 不写聊天消息
  -> 不写通知 Outbox
  -> 不消耗主动消息额度
```

每日来信正文生成失败时不发布半成品；图片生成失败时可以按文字优先策略发布纯文字来信。

## 5. 表情包业务逻辑

### 5.1 资源归属

Echo 官方表情包和用户私人表情包使用不同归属：

```text
官方：owner_type = echo
私人：owner_type = user, owner_user_id = 当前用户
```

搜索候选只包含官方表情包和当前用户自己的私人表情包，不能把用户 A 的私人表情包返回给用户 B。

### 5.2 用户发送

输入框旁的表情包按钮打开底部面板。用户点击后立即发送一条独立的用户图片消息，不进入文字输入框。该消息仍会进入连续消息批次，Echo 必须按统一 Agent 流程回复文字，并可根据语境附带一张表情包。

### 5.3 Echo 发送

```text
当前语境
  -> Agent 决定是否需要表情包
  -> search_stickers 语义检索候选
  -> 相似度 + 标签 + priority + 来源加权排序
  -> 冷却门禁筛选
  -> send_sticker 成功
  -> 文字消息和图片消息分开持久化
```

当前排序规则：

- embedding 相似度优先保证语义接近。
- 官方表情包增加 `+10` 来源分。
- 数据库 `priority` 决定同语义候选的稳定顺序。
- 最近 5 次对话使用过，或距上次使用不足 5 分钟的候选进入冷却。
- 如果所有候选都冷却，退回最高语义优先级候选。
- 每轮最多一张成功表情包。
- `send_sticker` 失败不消耗成功发送额度。
- 搜索结果为空时不执行发送；明确索要但精确查询无结果时，允许有限回退到当前可用候选，不连续猜关键词。

### 5.4 语义检索

表情包的描述、标签和情绪语义会生成 embedding 写入 `sticker_embeddings`。搜索时先做向量相似度召回，再结合标签命中、优先级、来源和冷却排序。新增用户表情包在当前用户范围内生成向量，不改变其他用户的候选集合。

## 6. 每日来信业务逻辑

每日来信是独立内容，不是聊天消息的自动复制，也不向聊天框插入一条伪消息。

### 6.1 生成与发布时间

默认使用用户本地时区：

```text
07:45 生成前一个自然日的来信
08:00 发布 ready_to_publish 内容
```

当前 APP 不提供来信生成时间设置页，使用默认时间；服务端保留偏好接口，为后续开放用户设置做准备。生成时间和发布时间分开，生成失败可以在发布时间前有限重试。

### 6.2 内容证据

生成上下文包含：

- 前一个自然日的真实用户和 Echo 消息。
- 按时间间隔切分的连续会话段。
- 当前有效长期记忆的有限召回。
- Echo 人格、用户偏好和关系阶段。

没有用户互动时跳过当天来信，不生成空泛问候。来信输出必须包含：

```text
subject
content
mood
core_topics
reflection
closing_style
image_brief
source_message_ids
source_memory_ids
```

`reflection` 必须包含 Echo 基于证据形成的想法、观察或更深入的交流，不能只复述用户已经知道的事件。来源 ID 会经过服务端白名单校验，模型不能凭空引用不存在的消息。

### 6.3 图片状态

图片生成代码已经抽象出 MiniMax Provider、参考素材和 COS 存储，但生产开关为关闭：

```env
LETTER_IMAGE_GENERATION_ENABLED=false
```

因此当前来信以稳定文字为主。未来重新启用时，图片应作为增强内容；图片失败不能阻塞准时发布文字，发布后的来信不因迟到图片再次变化。

### 6.4 APP 展示

```text
来信 Worker
  -> daily_letters(status=ready)
  -> GET /letters
  -> 来信入口未读角标
  -> 打开详情
  -> POST /letters/{letter_id}/read
  -> status=read
```

来信不使用聊天 SSE，也不需要来信推送。通知和聊天历史不会因为来信失败而改变。

## 7. 其他稳定业务

### 7.1 长期记忆和关系

原始聊天消息、对话摘要、长期记忆和关系状态分开存储：

```text
消息事实 -> 摘要压缩 -> 记忆抽取/向量化 -> 关系事件累计
```

清空聊天只清理当前聊天消息、摘要和未完成回合，不删除长期记忆、人格偏好和关系数据。

### 7.2 语音通话

```text
PCM16LE 16 kHz 单声道
  -> WebSocket ASR
  -> 流式失败时整段 PCM 识别
  -> call Agent
  -> CosyVoice TTS
  -> APP 播放
```

通话不发送表情包、不触发每日来信、不创建主动聊天任务。音频文件按保留期由清理 Worker 删除。

### 7.3 主动聊天和通知

主动任务由服务器 Worker 创建和执行，手机 APP 不需要常驻进程才能生成主动内容。服务器先保存聊天消息，再写 `notification_outbox`，个推只是提醒入口。手机系统彻底清理 APP 后，厂商离线通道尚未全部配置，不能承诺通知必达；用户重新打开 APP 时仍应从服务端同步消息。

## 8. 端到端数据流

### 8.1 用户聊天

```text
Flutter ChatController
  -> POST /chat/messages
  -> chat_messages + chat_turn_jobs
  -> Chat Worker
  -> Context Builder（人格/关系/记忆/时间）
  -> Unified Agent
       -> LLM
       -> time / web / sticker / schedule tools
  -> Reply Group 持久化
  -> SSE chat.delivery.created
  -> APP 分段显示和历史合并
```

### 8.2 主动消息

```text
偏好 / 定时任务 / 自然主动策略
  -> proactive_chat_jobs
  -> Proactive Worker claim
  -> Unified Agent（conversation_mode=proactive）
  -> 成功：chat_messages -> notification_outbox -> 个推
  -> 失败或空结果：suppressed，不发送
```

### 8.3 每日来信

```text
用户本地日期和来信偏好
  -> letter generation task
  -> 读取昨日真实证据
  -> Daily Letter Agent
  -> 可选图片 Provider
  -> ready_to_publish
  -> publish_at 到期后 ready
  -> APP /letters 读取
```

### 8.4 版本更新

```text
本地构建 APK
  -> 包名/版本/签名/SHA-256 校验
  -> 上传 COS
  -> 写入 app_releases
  -> APP 检查版本
  -> 确认后下载、校验并交给 Android 安装器
```

## 9. 当前明确关闭或受限能力

- 每日来信图片生成：代码保留，生产关闭。
- 聊天中的图片生成：不作为当前功能入口。
- 通话中表情包：明确禁止。
- 华为、荣耀、小米、OPPO、vivo 厂商离线推送：尚未全部完成认证和配置。
- 正式短信验证码：体验环境仍使用固定验证码配置。
- 公开大规模运营：当前仍按封闭体验版管理，需另行完成备案、商店和推送资质准备。
- 多人群聊、多 Echo 角色、消息撤回/引用、插件市场和复杂多 Agent：未纳入当前版本。

## 10. 新功能接入规则

后续增加功能时，先回答六个问题：

1. 数据属于哪个用户、设备或 Echo 全局资源？
2. 是否需要数据库状态、后台任务、Outbox 或幂等键？
3. 用户前台操作和后台主动行为是否需要分开？
4. Agent 是需要理解后调用工具，还是确定性业务逻辑即可？
5. 失败时是重试、降级、静默跳过，还是必须提示用户？
6. 用户如何关闭、删除、回溯和恢复这项功能？

推荐目录边界：

```text
Echo-backend/features/<feature>/
  domain/          实体、规则、接口
  application/     用例、Worker、状态流转
  infrastructure/  PostgreSQL、外部 Provider、COS
  interface/       Router、Schema
  public.py        受控公共入口

app/lib/features/<feature>/
  domain/          Flutter 实体
  data/            API、Repository、DTO
  presentation/    Controller、Page、组件
```

如果功能具有外部副作用（发送通知、发图、扣额度、创建任务、写入用户资产），必须：

- 通过应用服务或 Agent Tool 执行，禁止 UI 直接写数据库。
- 使用状态机、幂等键和有限重试。
- 记录成功、失败、跳过和取消原因。
- 对用户资源执行 owner 权限过滤。
- 增加正常路径、失败路径、重复请求和权限隔离测试。

## 11. 开发和发布门禁

### 11.1 开发前

- 先更新本基线文档中的业务边界。
- 明确是否属于 v1.0.9 稳定范围，还是下一版本功能。
- 先定义 API、数据库状态和失败语义，再写 UI。

### 11.2 测试

```bash
python -B scripts/check_architecture.py
uv run pytest Echo-backend/tests -q
cd app
flutter analyze
flutter test
```

后端本轮修复后的完整测试为 `273 passed`；局部修改文件通过 Ruff 检查。全仓库仍有历史 Ruff 风格告警，不在本次版本基线中扩大清理范围。

### 11.3 发布

```text
本地提交并推送 GitHub
  -> 服务器 /opt/echo/app/ 拉取 master
  -> 服务器只构建并重启后端
  -> 本地构建 APK
  -> 上传 COS 并登记版本
  -> 真机验证健康、登录、聊天和回滚路径
```

服务器不构建 APK，不存放本地签名文件；APK 和后端按各自发布流程维护。

## 12. 后续功能的推荐拆分

后续功能建议按“一个用户可感知结果”为单位拆分，而不是一次引入一组互相耦合的页面：

1. 先写业务文档和状态机。
2. 再添加数据库迁移和后端用例。
3. 如果需要 Agent 决策，再注册最小权限 Tool。
4. 增加 APP 的加载、空状态、失败、重试和删除入口。
5. 完成端到端测试后再接入展示站和发布版本。

本文件是 v1.0.9 的稳定基线。后续新功能应新增版本章节或新版本文档，不直接修改已经发生过的历史决策。
