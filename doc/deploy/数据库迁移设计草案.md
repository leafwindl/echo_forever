# Echo 数据库迁移设计草案

> 历史设计记录：1.0 已完成 PostgreSQL 单实现收敛，不再保留 SQLite 迁移代码或旧版本增量 SQL。

## 1. 目标

本文用于记录 Echo 从 SQLite 迁移到 PostgreSQL + pgvector 的数据模型、代码边界、迁移步骤和风险。

当前代码已按本文方向落地：运行时默认数据库已切换到 PostgreSQL + pgvector，旧 SQLite 只作为一次性迁移输入保留。

完整迁移顺序是：

```text
先设计目标模型
  -> 收敛 Repository 接口
  -> 增加迁移脚本与双环境验证
  -> 小数据量演练
  -> 再切换生产数据库
```

## 2. 当前数据库现状

旧 SQLite 文件默认位于：

```text
data/echo_memory.db
```

旧库已有表：

- `users`
- `conversations`
- `chat_messages`
- `user_memories`
- `memory_embeddings`
- `background_jobs`
- `runtime_settings`

当前特点：

- 运行时默认使用 PostgreSQL + pgvector。
- 旧 SQLite 文件只用于迁移脚本读取。
- 通过 `user_id` 做数据隔离。
- Chat、Memory、Auth、Admin 的运行时 repository 已迁入各自 feature 的 infrastructure。
- 顶层旧 `repositories/` 源码目录已删除。
- PostgreSQL schema 由 `db/schema.py` 在启动时初始化，目标 DDL 由 `db/postgres_schema.py` 生成。

## 3. 目标数据库选择

### 3.1 MySQL

优点：

- 国内云厂商托管服务成熟。
- 运维资料多。
- 对常规业务表、索引、备份恢复支持足够。

适合：

- 以微信小程序、业务数据、聊天记录为主的常规应用。
- 需要低运维成本和成熟云数据库方案。

### 3.2 PostgreSQL

优点：

- JSON、全文检索、复杂查询能力更强。
- 后续如果使用 pgvector，可以把向量索引也收敛到 PostgreSQL。
- 数据约束和类型表达能力更强。

适合：

- 未来希望把结构化数据和部分向量能力放在同一个数据库中。
- 后续对数据分析、复杂查询、向量检索有更高要求。

### 3.3 当前决策倾向

当前项目更偏向选择：

```text
PostgreSQL + pgvector
```

原因：

- Echo 的核心竞争力会逐步落在长期记忆、语义召回、RAG 和 Agent 能力上。
- PostgreSQL 可以同时承载结构化业务数据、JSON 元数据和向量索引。
- pgvector 能让长期记忆 embedding 直接在数据库内做相似度检索，减少额外向量库的早期运维成本。
- 后续人物日记、会话总结、主动触发任务等能力会依赖更强的数据查询和索引能力。

MySQL 暂时不作为优先目标。后续除非部署成本、云服务约束或团队运维偏好发生变化，否则迁移设计以 PostgreSQL 为主。

当前部署策略：

```text
先在现有服务器自建 PostgreSQL + pgvector
```

原因：

- 当前已有服务器，先复用现有资源，避免过早增加云数据库成本。
- 自建 PostgreSQL 更方便验证 pgvector、迁移脚本和本地/服务器部署流程。
- 等用户规模和数据价值明确后，再评估是否迁移到云托管 PostgreSQL。

注意：

```text
pgvector 负责存储和检索向量，不负责生成 embedding。
```

文本转向量仍然需要 Embedding 模型或 API，例如第三方 Embedding API，或未来自部署 embedding 模型。

当前已确认参数：

| 项目 | 当前值 |
|---|---|
| 目标数据库 | PostgreSQL + pgvector |
| 部署方式 | 先在现有服务器自建 |
| 当前 Embedding 模型 | `Qwen/Qwen3-Embedding-0.6B` |
| 当前向量维度 | `1024` |
| 会话摘要触发 | 未摘要消息超过 `24` 条 |
| 短期上下文保留 | 最近 `12` 条消息 |

## 4. 目标表设计

### 4.1 `users`

业务归属：Auth 模块。

用途：

- 保存小程序用户身份。
- 维护微信 openid 与内部 `user_id` 的映射。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `user_id` | 内部用户 ID，唯一 |
| `openid` | 微信 openid，唯一，可为空 |
| `nickname` | 昵称，预留 |
| `avatar_url` | 头像，预留 |
| `status` | 用户状态，预留 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

建议索引：

- `uk_users_user_id`
- `uk_users_openid`

### 4.2 `conversations`

业务归属：Chat 模块。

用途：

- 保存用户会话。
- 记录会话摘要和摘要边界。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `conversation_id` | 业务会话 ID，唯一 |
| `user_id` | 用户 ID |
| `title` | 会话标题 |
| `summary` | 会话摘要 |
| `summary_message_id` | 摘要覆盖到的最后一条消息 ID |
| `status` | `active` / `archived` / `deleted` |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

建议索引：

- `uk_conversations_conversation_id`
- `idx_conversations_user_status_updated`
- `idx_conversations_user_id`

注意：

- 当前逻辑默认使用用户最近的 active conversation。
- 后续如果支持多会话列表，需要明确 active 的含义。

### 4.3 `chat_messages`

业务归属：Chat 模块。

用途：

- 保存用户消息和 Echo 回复。
- 支撑上下文构建、会话摘要、历史记录。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `message_id` | 业务消息 ID，预留 |
| `user_id` | 用户 ID |
| `conversation_id` | 会话 ID |
| `role` | `user` / `assistant` / `system` |
| `content` | 消息正文 |
| `message_type` | `text` / `voice_asr` / `voice_reply` |
| `source` | 来源，预留 |
| `created_at` | 创建时间 |

建议索引：

- `idx_chat_messages_user_conversation_id`
- `idx_chat_messages_conversation_id`
- `idx_chat_messages_user_created`

注意：

- 旧 SQLite 使用 `id` 作为消息顺序边界；迁移脚本会生成稳定的 `sqlite_msg_<旧ID>`。
- 迁移脚本会记录旧消息 ID 到 PostgreSQL 新 ID 的映射，并据此重写会话摘要边界和长期记忆来源引用。
- 日志中不应输出完整 `content`。

### 4.4 `user_memories`

业务归属：Memory 模块。

用途：

- 保存长期记忆。
- 支撑 Prompt 注入和用户记忆管理。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `memory_id` | 业务记忆 ID，唯一 |
| `user_id` | 用户 ID |
| `memory_type` | 记忆类型 |
| `content` | 记忆内容 |
| `source_message_id` | 来源消息 ID |
| `confidence` | 置信度 |
| `importance` | 重要度 |
| `status` | `active` / `inactive` / `deleted` |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `expires_at` | 过期时间，预留 |

建议索引：

- `uk_user_memories_memory_id`
- `idx_user_memories_user_status`
- `idx_user_memories_user_status_type`
- `idx_user_memories_source_message_id`

注意：

- `inactive` 用于系统或用户纠正后的停用历史。
- `deleted` 用于用户主动删除或清空。
- 删除或停用后，向量记录必须同步处理，避免旧记忆继续被召回。

### 4.5 `memory_embeddings`

业务归属：Memory 模块。

用途：

- 保存长期记忆对应的 embedding。
- 旧 SQLite 以 JSON 字符串保存向量；PostgreSQL 目标结构使用 pgvector。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `memory_id` | 记忆 ID，唯一 |
| `user_id` | 用户 ID |
| `embedding_model` | embedding 模型 |
| `embedding` | 向量数据 |
| `vector_store_id` | 外部向量库 ID，预留 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

建议索引：

- `uk_memory_embeddings_memory_id`
- `idx_memory_embeddings_user_id`
- `idx_memory_embeddings_user_model`

目标选择：

- PostgreSQL：使用 pgvector，把 `embedding` 改为 `vector(1024)` 类型。
- Embedding 生成仍由 Embedding Provider 负责，pgvector 只负责存储、索引和相似度查询。
- 暂不优先引入第三方向量数据库，除非后续数据规模或召回性能超过 PostgreSQL + pgvector 的承载范围。

### 4.6 `background_jobs`

业务归属：Shared / Infrastructure，当前主要服务 Memory，未来可服务 Voice、清理任务等。

用途：

- 记录可恢复的后台任务。
- 支撑服务重启后的任务恢复。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `job_id` | 业务任务 ID，唯一 |
| `job_type` | 任务类型 |
| `status` | `pending` / `running` / `retry` / `completed` / `failed` |
| `payload` | JSON 任务参数 |
| `attempts` | 已尝试次数 |
| `max_attempts` | 最大尝试次数 |
| `error` | 错误摘要 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `started_at` | 开始时间 |
| `finished_at` | 完成时间 |

建议索引：

- `uk_background_jobs_job_id`
- `idx_background_jobs_status_type`
- `idx_background_jobs_type_created`

注意：

- 当前任务执行仍偏轻量，后续队列化时可以继续复用该表记录任务状态。
- `payload` 不应放用户隐私原文，必要时只放 ID。

### 4.7 `runtime_settings`

业务归属：Admin / System 模块。

用途：

- 保存运行时配置，例如系统提示词。

建议字段：

| 字段 | 含义 |
|---|---|
| `key` | 配置键 |
| `value` | 配置值 |
| `scope` | 配置作用域，预留 |
| `updated_by` | 更新人，预留 |
| `updated_at` | 更新时间 |

建议索引：

- `pk_runtime_settings_key`

注意：

- 当前系统提示词是全局生效。
- 如果未来支持按用户、按角色、按环境配置，需要引入 `scope` 或新增 `prompt_profiles` 表。

### 4.8 `voice_files`

业务归属：Voice 模块。

当前尚未落库，建议迁移 COS 时新增。

用途：

- 记录语音文件存储位置、归属用户、过期时间和清理状态。
- 支撑本地 static 到 COS 的迁移。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `file_id` | 文件业务 ID，唯一 |
| `user_id` | 用户 ID |
| `conversation_id` | 会话 ID，可为空，当前可先不绑定 |
| `message_id` | 消息 ID，可为空，当前可先不绑定 |
| `file_type` | `upload` / `generated` |
| `storage_provider` | `local` / `cos` |
| `bucket` | COS bucket，预留 |
| `object_key` | COS object key 或本地相对路径 |
| `public_url` | 访问 URL 或签名 URL，可为空 |
| `content_type` | 文件类型 |
| `size_bytes` | 文件大小 |
| `status` | `active` / `expired` / `deleted` |
| `expires_at` | 过期时间 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

建议索引：

- `uk_voice_files_file_id`
- `idx_voice_files_user_created`
- `idx_voice_files_status_expires`

当前决策：

- ASR 上传文件原则上不长期保存。
- TTS 生成文件不作为历史消息附件长期复播。
- 生成音频当前不强制绑定 `chat_messages`。
- 音频更像一次性播放资源：生成、上传 COS、返回短期 URL、过期清理。
- COS 建议使用私有读，后端返回短期签名 URL。
- 如果后续确实需要历史回放，再补 `message_id` 绑定关系。
- 切到 COS 后，应优先依赖 COS 生命周期规则，同时保留数据库状态用于排查。

## 5. 数据关系

核心关系：

```text
users 1 -> N conversations
users 1 -> N chat_messages
conversations 1 -> N chat_messages
users 1 -> N user_memories
user_memories 1 -> 1 memory_embeddings
chat_messages 1 -> N user_memories(source_message_id)
chat_messages 1 -> N voice_files(message_id)
```

是否强制外键需要谨慎：

- 迁移设计中先保留逻辑外键关系。
- 初期可以不强制物理外键，降低历史数据迁移和修复成本。
- PostgreSQL 结构稳定后，再逐步给核心关系增加物理外键。
- 如果启用物理外键，需要先清理历史脏数据，并明确删除策略。

初步建议：

- `chat_messages.conversation_id -> conversations.conversation_id` 可作为候选外键。
- `user_memories.user_id -> users.user_id` 可作为候选外键。
- 不建议一开始启用大范围级联删除，避免误删用户数据。

## 6. 数据生命周期设计

### 6.1 聊天记录

聊天记录不只是历史展示，也会作为生成会话总结和中期记忆的原始材料。

当前会话摘要策略：

- 未摘要消息超过 `24` 条时触发摘要。
- 最近 `12` 条消息保留为短期上下文，不进入本轮摘要。
- 更早消息合并进 `conversations.summary`。
- `summary_message_id` 记录摘要覆盖到的最后一条消息 ID。

当前决策：

- 暂时不开放用户清空聊天记录。
- 用户侧优先开放长期记忆管理。
- 原始聊天记录在完成会话总结后，可以进入待删除阶段。
- 待删除阶段保留一周缓冲期。
- 缓冲期结束后，系统后台再物理清理原始明细。

建议状态：

```text
active -> summarized -> pending_delete -> deleted
```

说明：

- `active`：仍参与上下文、摘要或排查。
- `summarized`：已进入会话总结，可降低直接参与上下文的频率。
- `pending_delete`：等待一周缓冲期。
- `deleted`：已软删除或已物理清理。

PostgreSQL 目标表已经给 `chat_messages` 增加：

| 字段 | 含义 |
|---|---|
| `status` | 消息状态 |
| `summarized_at` | 被摘要覆盖的时间 |
| `delete_after` | 可物理删除时间 |

### 6.2 会话总结与人物日记

会话总结未来会演进成人物日记形式，并可能展示给用户。

当前阶段：

- 不开发人物日记前端功能。
- 数据库设计中预留扩展空间。
- `conversations.summary` 当前继续作为滚动摘要使用。

后续可考虑新增：

- `conversation_summaries`
- `character_diaries`

用于保存更稳定、可展示、可回溯的中期记忆或人物日记。

### 6.3 长期记忆

长期记忆继续由 `user_memories` 管理。

当前决策：

- 用户可以管理长期记忆。
- `inactive` 表示曾经有效但现在不应再召回。
- `deleted` 表示用户主动删除或清空后不再展示、不再召回。
- 删除或停用长期记忆时，必须同步处理 `memory_embeddings`。

### 6.4 语音文件

语音文件不进入长期历史复播逻辑。

当前决策：

- ASR 上传音频处理完立即删除。
- TTS 生成音频上传 COS 后返回短期签名 URL。
- 生成音频短期过期后由 COS 生命周期或后台任务清理。
- 暂不绑定 `chat_messages`。

## 7. 代码改造边界

迁移数据库前，建议先做代码边界收口。

### 7.1 Domain 层

Domain 层只定义 Repository 协议，不依赖 SQLite、MySQL、PostgreSQL。

示例方向：

```text
features/chat/domain/repositories.py
features/memory/domain/repositories.py
features/auth/domain/services.py
features/voice/domain/repositories.py
```

### 7.2 Application 层

Application 层只依赖 Domain 定义的接口。

不应该出现：

- `sqlite3`
- SQL 语句
- 具体数据库连接
- provider 细节

### 7.3 Infrastructure 层

Infrastructure 层提供具体实现：

```text
features/<module>/infrastructure/postgres_repositories.py
features/<module>/infrastructure/repository_provider.py
```

旧 SQLite repository、连接和 schema 兼容代码已删除；一次性迁移脚本直接只读打开旧数据库文件。

### 7.4 配置层

新增配置建议：

```dotenv
DB_PROVIDER=postgres
DATABASE_URL=postgresql://user:password@host:5432/echo
DB_POOL_SIZE=5
DB_POOL_TIMEOUT_SECONDS=30
```

Docker Compose 后端容器使用：

```dotenv
DB_PROVIDER=postgres
DATABASE_URL=postgresql://echo:echo_dev_password@echo-postgres:5432/echo
```

本地直连示例：

```dotenv
DB_PROVIDER=postgres
DATABASE_URL=postgresql://echo:echo_dev_password@127.0.0.1:5432/echo
```

迁移完成后，应删除或隔离：

- 运行时 SQLite repository 兼容实现。
- SQLite 初始化兼容代码。
- 本地 static 语音长期存储兼容逻辑。
- 仅服务迁移期的临时脚本和配置。

目标是完成迁移后不长期背负双数据库兼容成本。

## 8. 迁移步骤建议

### 当前落地状态

第一轮代码落地目标：

- 已增加 PostgreSQL + pgvector 目标 schema 生成能力。
- 已增加 `scripts/init_postgres_schema.py`，用于打印或初始化 PostgreSQL schema。
- Docker Compose 默认启动 PostgreSQL + pgvector 服务。
- 当前业务读写默认走 PostgreSQL。
- Chat 模块运行时仓储：`features/chat/infrastructure/postgres_repositories.py`。
- Memory 模块运行时仓储：`features/memory/infrastructure/postgres_repositories.py`。
- Auth/User 运行时仓储：`features/auth/infrastructure/postgres_repositories.py`。
- Admin runtime settings 已切换到 PostgreSQL。
- Feature 代码已不再直接依赖全局 `repositories/` 目录；全局旧目录源码已删除。

本地启动 PostgreSQL：

```bash
docker compose up -d echo-postgres
```

查看 PostgreSQL schema SQL：

```bash
python -B scripts/init_postgres_schema.py --print-sql
```

初始化 PostgreSQL schema：

```bash
python -B scripts/init_postgres_schema.py \
  --database-url postgresql://echo:echo_dev_password@127.0.0.1:5432/echo
```

SQLite 旧数据迁移：

```bash
python -B scripts/migrate_sqlite_to_postgres.py \
  --sqlite-path data/echo_memory.db \
  --database-url postgresql://echo:echo_dev_password@127.0.0.1:5432/echo
```

服务器 Docker Compose 迁移：

```bash
cp .env.compose.example .env
# 编辑根目录 .env，确保 POSTGRES_PASSWORD 与 DATABASE_URL_DOCKER 中的密码一致。
docker compose stop echo-backend
cp data/echo_memory.db data/echo_memory.pre-postgres.db
docker compose up -d echo-postgres
docker compose build echo-backend
docker compose run --rm echo-backend \
  python /app/scripts/migrate_sqlite_to_postgres.py \
  --sqlite-path /app/data/echo_memory.db
docker compose up -d echo-backend
```

`.env` 只负责选择数据库实现和提供连接地址，不承担数据复制。必须单独执行迁移脚本，并完成第 9 节的数据验证。

其中根目录 `.env` 由 Docker Compose 自动读取；`Echo-backend/.env` 继续保存 LLM、Embedding、微信登录等后端业务配置。

## 9. 迁移验证清单

必须验证：

- 用户登录后 user_id 不变化。
- 历史会话可以继续读取。
- 新消息能写入正确 conversation。
- 会话摘要边界不丢失。
- 长期记忆列表正确。
- 长期记忆向量召回可用。
- 删除记忆后向量同步删除。
- 背景任务可以继续执行或被安全重试。
- 系统提示词 runtime setting 不丢失。
- 语音回复仍能生成并返回 URL。
- COS 短期签名 URL 可以在小程序中播放。
- 过期音频不会继续可访问。

数据校验：

- 每张表总行数一致。
- 每个用户的聊天消息数量一致。
- 每个用户的 active memory 数量一致。
- `chat_messages.id` 顺序一致。
- `source_message_id` 能对应到原消息。
- 已摘要消息的生命周期字段正确。

## 10. 风险与待讨论问题

### 10.1 目标库选择

当前倾向已经明确为 PostgreSQL + pgvector。

仍需确认：

- 自建 PostgreSQL 的部署方式：直接宿主机安装，还是 Docker Compose。
- PostgreSQL 版本。
- pgvector 扩展安装方式。
- 未来是否迁移到云托管 PostgreSQL。

### 10.2 向量存储策略

需要确认：

- 使用 PostgreSQL pgvector？
- 向量维度固定为 `1024`，对应当前 `Qwen/Qwen3-Embedding-0.6B`。
- 使用哪种索引类型？
- 是否需要按 `user_id` 分区或联合过滤？
- 是否保留 `vector_store_id` 字段作为未来外部向量库预留？

### 10.3 是否强制外键

需要确认：

- 哪些关系第一阶段只保留逻辑外键？
- 哪些关系在 PostgreSQL 稳定后增加物理外键？
- 是否禁止级联删除？

### 10.4 消息内容归档

当前初步决策：

- 原始聊天记录在会话总结后进入待删除阶段。
- 待删除缓冲期为一周。
- 用户暂时不能清空聊天记录。
- 用户可以管理长期记忆。

仍需确认：

- 会话总结多久触发一次？
- 哪些消息可以被物理删除？
- 未来人物日记是否单独建表？

### 10.5 语音文件记录

当前初步决策：

- 使用腾讯云 COS。
- 生成音频暂不绑定 `chat_messages`。
- 生成音频不做长期历史复播。
- 使用短期签名 URL。

仍需确认：

- 签名 URL 有效期。
- COS 生命周期保留时间。
- 是否需要数据库记录每次生成音频，还是仅记录异常和清理状态。

## 11. 初步建议

我建议下一步先做三件事：

1. 按 PostgreSQL + pgvector 继续细化目标 schema。
2. 明确 embedding 模型和向量维度。
3. 继续完善 pgvector 检索性能和索引策略。
4. 先补 `voice_files` 表设计，不急着实现。
5. 设计聊天记录生命周期字段，为中期记忆和未来人物日记预留空间。

这样做的好处是：

- 不会立刻引入新数据库运维成本。
- 可以继续稳定本地开发和小范围内测。
- 后续真正迁移数据库时，业务层改动会更小。
