# Echo 后续优化待办与本地测试流程

## 1. 当前共识

Echo 当前已经具备本地开发和小范围内测基础。下一阶段不急于增加复杂的错误码、监控平台或合规文档，而是优先补齐后续扩展会依赖的底座。

当前阶段的取舍：

- 已有基础失败提示时，不提前建设复杂错误体系。
- 默认数据库已切到 PostgreSQL + pgvector；旧 SQLite 只作为迁移输入保留。
- 语音文件继续落本地 static 会限制扩展，应规划迁移到 COS。
- Redis、异步任务队列不一定马上落地，但要明确它们未来承接哪些职责。
- 日志监控、隐私协议、自动备份策略放到正式外测或上线收口阶段。

## 2. P0：扩展底座设计

### 2.1 数据库迁移设计

当前默认使用：

```text
PostgreSQL + pgvector + user_id 隔离 + Repository 抽象 + Docker 部署
```

SQLite 到 PostgreSQL 的迁移脚本已作为一次性工具保留。

建议优先梳理这些核心表：

- `users`：用户身份、微信 openid、基础资料。
- `conversations`：用户会话。
- `chat_messages`：用户消息与 Echo 回复。
- `user_memories`：长期记忆。
- `memory_embeddings`：记忆向量索引元数据。
- `runtime_settings`：系统提示词、运行时配置。
- `voice_files`：语音文件记录、存储位置、过期时间。
- `background_jobs`：异步任务记录。

设计目标：

- 明确每张表属于哪个业务模块。
- 明确哪些字段用于查询、索引和数据隔离。
- 明确 SQLite 到 PostgreSQL 的迁移步骤。
- 保持 Application 层不依赖具体数据库。
- Domain 层只定义 Repository 接口。
- Infrastructure 层只保留 PostgreSQL 运行适配；SQLite 仅由一次性迁移脚本读取。

暂不急于直接迁移数据库，先完成设计。

### 2.2 语音文件迁移到 COS

当前语音文件存在服务器本地 static 目录。

短期可用，但问题是：

- 文件会持续增长。
- 多实例部署时本地文件无法共享。
- 服务器磁盘满会影响主服务。
- 文件清理和访问控制都不够标准。

目标形态：

```text
后端生成语音
  -> 上传腾讯云 COS
  -> 数据库记录 voice_files
  -> 返回 HTTPS 音频 URL
  -> 前端播放
```

需要设计：

- COS bucket 和目录规则。
- 文件命名规则。
- 文件过期和生命周期策略。
- 本地 static 与 COS 的过渡方案。
- TTS 失败时仍返回文字回复。

### 2.3 Redis 引入评估

Redis 暂时不是必须，但未来会承接这些职责：

- 分布式聊天串行锁。
- 请求限流。
- 异步任务状态。
- 短期缓存。
- 多实例部署下的共享状态。

当前单容器部署可以继续使用内存锁。只有准备多实例或任务队列时，再正式引入 Redis。

### 2.4 异步任务队列边界设计

未来适合放入后台队列的任务：

- 长期记忆抽取。
- 会话摘要更新。
- 语音合成。
- 语音文件清理。
- 批量数据维护任务。

候选方案：

- Celery + Redis。
- RQ + Redis。
- 基于数据库表的轻量任务队列。

当前不急于实现，但要先明确：

- 哪些任务必须同步完成。
- 哪些任务可以异步完成。
- 异步失败后如何重试。
- 前端是否需要感知任务状态。

## 3. P1：上线收口阶段

这些事项重要，但不适合太早复杂化。建议在外测或正式上线前集中补齐。

### 3.1 回复失败与超时兜底

当前已有基础错误提示时，暂不建设复杂错误码体系。

上线前只保留必要原则：

- TTS 失败不能影响文字回复。
- LLM 失败时前端要有可理解的提示。
- 用户不应该看到技术错误细节。
- 必要时提供重试入口。

### 3.2 日志与基础监控

上线前需要补齐最小可用监控。

当前排查方式：

```bash
docker compose logs -f echo-backend
```

Nginx 日志通常在：

```text
/var/log/nginx/access.log
/var/log/nginx/error.log
```

后续建议监控：

- `/chat/send` 请求耗时。
- LLM、Embedding、TTS、ASR 成功率和耗时。
- 4xx/5xx 数量。
- 数据库写入失败。
- 磁盘占用。
- COS 上传失败。

日志必须避免记录：

- 聊天正文。
- ASR 原文。
- token。
- openid。
- secret。
- 微信临时 code。

### 3.3 自动备份策略

SQLite 备份脚本只服务旧库迁移前的兜底。

PostgreSQL 阶段需要正式设计：

- 自动备份频率。
- 保留周期。
- 恢复演练。
- 备份文件加密。
- 异地备份。

### 3.4 隐私协议与用户数据说明

这是面向用户和平台审核的说明，不是当前研发主链路。

外测或提交审核前需要补齐：

- 隐私政策。
- 用户协议。
- 录音用途说明。
- 长期记忆用途说明。
- 聊天记录保存说明。
- 用户如何删除记忆或清空数据。
- 数据是否用于训练的说明。

## 4. P2：规模化增强

当用户量、请求量或数据规模明显增长后，再推进：

- 多实例部署。
- Redis 分布式锁和限流。
- PostgreSQL 备份恢复与托管数据库迁移评估。
- 队列 worker 独立扩容。
- 语音文件全量迁移 COS。
- 监控告警平台。
- 成本监控和用量控制。

## 5. 本地测试流程

### 5.1 本地自动检查

每次准备提交前建议执行：

```bash
python -B scripts/check_architecture.py
python -B -m unittest discover -s Echo-backend/tests
```

前端执行：

```bash
cd Web
npx tsc --noEmit
```

### 5.2 本地启动后端

后端可以直接启动：

```bash
docker compose up -d echo-postgres
cd Echo-backend
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

也可以用 Docker 启动：

```bash
docker compose up -d --build
```

如果需要验证 PostgreSQL + pgvector 目标库，可以额外启动本地 PostgreSQL：

```bash
docker compose up -d echo-postgres
python -B scripts/init_postgres_schema.py --print-sql
python -B scripts/init_postgres_schema.py --database-url postgresql://echo:echo_dev_password@127.0.0.1:5432/echo
```

当前阶段业务读写默认走 PostgreSQL。

旧 SQLite 数据迁移：

```bash
python -B scripts/migrate_sqlite_to_postgres.py \
  --sqlite-path data/echo_memory.db \
  --database-url postgresql://echo:echo_dev_password@127.0.0.1:5432/echo
```

Docker Compose 环境执行：

```bash
cp .env.compose.example .env
# 编辑根目录 .env，确保 POSTGRES_PASSWORD 与 DATABASE_URL_DOCKER 中的密码一致。
docker compose stop echo-backend
cp data/echo_memory.db data/echo_memory.pre-postgres.db
docker compose up -d echo-postgres
docker compose build echo-backend
docker compose run --rm echo-backend \
  python /app/scripts/migrate_sqlite_to_postgres.py \
  --sqlite-path /app/data/echo_memory.db
docker compose up -d echo-backend
```

配置 `DB_PROVIDER=postgres` 和 `DATABASE_URL` 只会切换后续读写目标，不会自动迁移历史数据。

健康检查：

```bash
curl http://127.0.0.1:8000/
```

预期返回：

```json
{"status":"ok"}
```

### 5.3 小程序开发者工具联调

本地联调时，微信开发者工具需要勾选：

```text
不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书
```

开发者工具可以请求本地后端：

```text
http://127.0.0.1:8000
```

如果需要手机真机访问本地电脑，需要使用局域网 IP：

```text
http://本机局域网IP:8000
```

注意：

- 当前 `develop` 指向本地后端，`trial/release` 指向公网 HTTPS 域名。
- 不要把本地地址发布到体验版或正式版。
- 三个环境的客户端管理调试入口均默认关闭，管理 Token 不得打包进小程序。

### 5.4 真机测试

真机预览和体验版更接近真实微信环境，建议走正式 HTTPS 域名：

```text
https://api.echoaiforever.cn
```

真机测试重点：

- 登录。
- 文字聊天。
- 语音输入。
- 语音回复。
- 记忆列表。
- token 鉴权。
- TTS 失败降级。
- 网络异常提示。

## 6. 推荐发布流程

```text
本地开发
  -> 本地自动检查
  -> 本地后端联调
  -> 小程序开发者工具测试
  -> git push
  -> 服务器 git pull
  -> docker compose up -d --build
  -> 真机体验版测试
  -> 小范围灰度
```

未来建议增加预发布环境：

```text
test-api.echoaiforever.cn
```

这样可以先把代码部署到测试域名，确认无误后再发布正式域名。
