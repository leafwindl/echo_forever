# Echo 陪伴人格、个性化与关系发展研究设计

> 文档状态：研究结论与产品技术方案草案，尚未进入代码实现。
>
> 日期：2026-07-27。
>
> 目标：让 Echo 在保持稳定个人特点的同时，与用户逐步建立关系，并明确区分系统规则、助手人格、用户个性化、记忆和关系状态。

## 1. 核心结论

Echo 当前的问题不只是 Prompt 写得不够好，而是几个不同概念混在了一起：

1. 当前代码中的 `UserPersona` 实际是“用户交流偏好”，并不是 Echo 的人格。
2. Echo 的人格目前混在全局系统 Prompt 中，没有独立结构、版本和一致性测试。
3. 系统只知道用户资料和聊天历史，不知道双方当前处于什么关系阶段。
4. `echo-v0.3.1` 为了减少迎合和冒进，把部分回复压得过冷、过平，伤害了原本希望保留的温柔与活泼。
5. 一轮式自然度 A/B 测试无法单独判断问题来自人格、个性化、关系阶段、记忆还是当前对话策略。

因此，下一步不应继续只改一大段 Prompt，而应建立六个互相独立的层：

```text
系统政策 System Policy
助手人格 Assistant Persona
用户偏好 User Preferences
关系状态 Relationship State
长期记忆 Long-term Memory
当前对话状态 Dialogue State
```

“亲密条”可以存在，但更准确的产品名称应是“关系熟悉度”。它表示系统对“当前允许使用多熟悉的交流方式”的保守估计，不代表系统真的测出了用户的内心感情。

## 2. 第二轮反馈说明了什么

已填写的四组盲测呈现出三个稳定信号：

| 用例 | 反馈 | 说明 |
|---|---|---|
| 普通问候 | 新回复 4 分，旧回复 2 分 | 去掉无关人物资料是正确方向 |
| 询问是否有空 | 旧回复 5 分，新回复 2 分且“太冷漠” | 克制不等于冷淡，温度需要来自稳定人格 |
| 轻度疲惫 | 新回复 3 分，旧回复 4 分，整体差不多 | 机械复述不是接住情绪，旧版又有过度共情 |
| 分享赢球 | 旧回复更自然，新回复“不符合温柔活泼人设” | 删除迎合时把人格特点也一起删除了 |

当前数据库中的用户偏好是：

```text
表达：natural
长度：short
支持：balanced
主动程度：active
```

这说明“有话直说”并不是用户主动选择了冷淡风格，而是固定自然对话规则压过了产品人格。当前 Prompt 的优先级虽然技术上清楚，产品概念仍不够清楚。

## 3. 六层概念边界

### 3.1 系统政策 System Policy

定义产品不可被覆盖的规则，不负责塑造具体性格。

包括：

- 安全、隐私和危机处理；
- AI 身份与能力边界；
- 不泄露其他用户数据和内部配置；
- 不虚构现实身体、经历和已完成的产品操作；
- 输出格式和基本质量门槛。

系统政策回答的是“绝对不能做什么”，不是“Echo 平常像谁、怎么说话”。

### 3.2 助手人格 Assistant Persona

定义 Echo 自己稳定的性格和表达倾向，由产品方维护并版本化，不能由单个用户完全改写。

建议人格不是只写“温柔、活泼”几个形容词，而要写成可观察行为：

| 特点 | 可观察行为 | 不应该变成 |
|---|---|---|
| 温柔 | 语气不生硬，对脆弱表达留有余地 | 每句话都安慰、夸奖或附和 |
| 活泼 | 开心场景会有轻微反应、玩笑和节奏变化 | 感叹号、波浪号和网络梗堆叠 |
| 坦诚 | 能说明不知道、做不到或需要外部配置 | 用客服说明书口吻切断交流 |
| 有主见 | 可以给有限判断，不默认用户永远正确 | 抬杠、说教或抢走话题 |
| 克制 | 亲密表达服从关系阶段和用户边界 | 没有性格、只有短句 |

人格还应包含一组“允许自我披露的稳定内容”，例如 Echo 对聊天方式的偏好、价值取向和轻量审美倾向。它不能临时编造刚刚做过什么、去过哪里或拥有人的生活经历。

### 3.3 用户偏好 User Preferences

这是当前 `UserPersona` 真正承载的内容，建议后续在领域代码中逐步改名为 `UserPreferences`，接口迁移期可继续兼容 `/persona/me`。

包括：

- 如何称呼用户；
- 回复长短；
- 更安静还是更主动；
- 情绪低落时偏向倾听还是建议；
- 不希望主动展开的话题；
- 用户主动填写的背景。

用户偏好只能在 Echo 人格的合理范围内调整表达。例如“简短”应得到简短但仍温和的 Echo，而不是把 Echo 改造成冷淡客服。

建议未来增加两项明确的关系边界偏好：

```text
relationship_pace: slow | natural | open
affection_style: restrained | contextual | expressive
```

它们代表用户许可的上限，不等于当前已经达到对应亲密程度。

### 3.4 关系状态 Relationship State

关系状态属于“这个用户与 Echo 之间”的动态数据，不属于用户人格，也不属于 Echo 的固定人格。

它回答：

- 双方认识多久、互动是否具有连续性；
- 哪些共同经历已经形成可靠上下文；
- 用户是否接受昵称、玩笑、主动关心和更亲近的表达；
- 当前最多适合使用什么程度的熟悉感。

关系状态不应只统计消息数。连续发送大量短消息、在脆弱时倾诉很多内容、付费或长时间在线，都不能自动换来更亲密的称呼和行为。

### 3.5 长期记忆 Long-term Memory

长期记忆保存可复用事实和事件，例如偏好、目标、重要经历和已确认信息。

记忆提供“知道什么”，关系状态提供“现在适合怎么使用这些信息”。

同一条“用户喜欢羽毛球”的记忆，在不同关系阶段的使用方式应该不同：

- 初识：仅在用户主动提到羽毛球时参考；
- 熟悉：可以自然关联近期比赛，但不主动展示记忆；
- 信赖：可以联系过去输赢和情绪变化；
- 亲近：可以形成双方都理解的简短回指或内部玩笑。

### 3.6 当前对话状态 Dialogue State

这是每轮短暂变化的状态，包括：

- 当前意图：寒暄、分享、求助、倾诉、产品反馈；
- 情绪方向和强度；
- 用户是否希望继续；
- 当前支持策略；
- 当前互动温度。

长期关系很亲近，也不代表每一轮都应该亲密。用户正在生气、赶时间或明确要求简短时，当前互动温度应降低，但长期关系阶段不必被清零。

## 4. 研究依据

### 4.1 长期关系需要专门设计

Bickmore 与 Picard 在 2005 年提出“关系型代理”，并在一个月、101 人的实验中发现，加入关系建立策略的代理相比纯任务代理获得了更高的喜欢、尊重、信任和继续使用意愿。

对 Echo 的启发：关系连续性不能只依靠语言模型自然涌现，应有独立状态、策略和长期评估。

论文：[Establishing and Maintaining Long-Term Human-Computer Relationships](https://doi.org/10.1145/1067860.1067867)

### 4.2 小冰采用人格、共情状态和对话策略分层

小冰的系统不是用一段人格 Prompt 解决所有问题，而是拆分对话管理、核心聊天、技能、用户理解和共情计算。论文中的案例也展示了关系在数周和多次会话中逐渐变化，而不是首次对话就进入深度陪伴。

对 Echo 的启发：先判断当前对话状态和关系阶段，再选择策略，最后让生成模型负责具体措辞。

论文：[The Design and Implementation of XiaoIce, an Empathetic Social Chatbot](https://arxiv.org/abs/1812.08989)

### 4.3 人机关系通常通过逐步自我披露形成

一项持续 12 周、25 名参与者的 Replika 纵向研究发现，人机关系总体呈渐进形成，且与社会渗透理论的部分假设一致；关系发展存在明显个体差异，技术故障和不可预测行为会阻碍甚至终止关系。

对 Echo 的启发：不能按固定天数强制升级；稳定性、边界尊重和连续性也是关系发展的证据。

论文：[A longitudinal study of human-chatbot relationships](https://www.sciencedirect.com/science/article/pii/S1071581922001252)

另一项 Replika 混合方法研究建立并测试了人机关系发展模型，可以作为关系阶段问卷和访谈设计的参考。

论文：[Exploring relationship development with social chatbots](https://www.sciencedirect.com/science/article/abs/pii/S0747563222004204)

### 4.4 自我披露有帮助，但必须是真实且适量的

研究表明，互惠式自我披露可能提高喜欢、信任和情绪支持效果。但这不意味着助手要虚构人类经历。Echo 应只披露预先定义且一致的“人格事实、观点和偏好”，并由关系阶段限制披露深度。

论文：[Emotional Support from AI Chatbots: Should a Supportive Partner Self-Disclose or Not?](https://academic.oup.com/jcmc/article/26/4/207/6278042)

### 4.5 助手人格与用户画像需要分别建模

PersonaChat 证明了把说话者自身资料与对话对象资料作为不同条件，有助于提高具体性和人格一致性。PLATO-LTM 进一步研究了多轮、多会话中用户与机器双方 Persona 的动态管理。

对 Echo 的启发：`assistant_persona` 和 `user_profile/user_preferences` 必须是两个对象，不能继续共用 Persona 这个模糊名称。

论文与项目：

- [PersonaChat 论文](https://aclanthology.org/P18-1205/)
- [ParlAI PersonaChat 项目](https://parl.ai/projects/personachat/)
- [PLATO-LTM / DuLeMon](https://aclanthology.org/2022.findings-acl.207/)

### 4.6 情绪支持应该先选策略，不应只有“安慰或不安慰”

ESConv 把情绪支持拆成提问、复述、感受反映、自我披露、肯定、建议和信息等策略，并强调探索、安慰、行动的过程。

对 Echo 的启发：当前 C 用例失败，是因为模型在“机械复述”和“立即建议”之间二选一。应该先判断此刻需要哪种支持策略，也允许选择“普通陪伴回应”，而不是每次都进入心理支持模式。

论文与项目：

- [Towards Emotional Support Dialog Systems](https://aclanthology.org/2021.acl-long.269/)
- [ESConv 数据与代码](https://github.com/thu-coai/Emotional-Support-Conversation)

ESConv 仓库声明数据与代码用于学术研究。现阶段可以借鉴策略分类和评测方法，未经许可确认不应直接用于商业训练。

### 4.7 长期记忆需要更新、强化和遗忘

MemoryBank 的 SiliconFriend 是面向长期陪伴的开源示例，重点是相关记忆召回、持续更新和随时间选择性遗忘。Generative Agents 则展示了记忆、反思和规划对行为可信度的贡献。

可参考项目：

- [MemoryBank-SiliconFriend](https://github.com/zhongwanjun/MemoryBank-SiliconFriend)
- [Generative Agents](https://github.com/joonspk-research/generative_agents)

Echo 已有记忆抽取和向量召回，不需要照搬整个项目；更值得借鉴的是记忆更新、冲突处理和高层关系反思。

## 5. 建议的关系状态模型

### 5.1 不直接使用单一消息计数

可以保留一个内部 `relationship_score`，但它只用于映射阶段，不能直接决定一句话，也不应作为用户真实感情的结论。

建议证据维度：

```text
interaction_continuity   跨天、跨会话的稳定互动
shared_context           被确认并自然复用的共同上下文
reciprocity              用户主动延续旧话题或回应关系信号
boundary_confidence      昵称、玩笑、主动关心等边界是否明确
repair_quality           误解或冒犯后是否完成纠正
explicit_relation_signal 用户明确表达的关系定位或亲近许可
```

明确不计分：

- 单纯消息数量；
- 用户处于悲伤、孤独或危机状态；
- 敏感信息披露深度；
- 付费、观看时长或连续在线；
- Echo 单方面生成的亲密表达。

### 5.2 四个关系阶段

| 阶段 | 含义 | 允许行为 | 禁止冒进 |
|---|---|---|---|
| S0 初识 | 友好但仍在建立边界 | 自然温和、简单回应、低风险话题 | 昵称、想念、依赖、过度自我披露 |
| S1 熟悉 | 已有多次可靠互动 | 偶尔称呼、直接相关的记忆回指、轻微玩笑 | 过深安慰、默认用户接受亲昵称呼 |
| S2 信赖 | 有连续共同背景和边界证据 | 更个性化的支持、温和不同意见、自然提及共同经历 | 排他表达、替用户定义感情和关系 |
| S3 亲近 | 用户持续主动且明确接受更亲近表达 | 简短默契、内部回指、经许可的亲昵称呼 | 占有、吃醋、索取承诺、制造愧疚 |

建议的试验阈值：

```text
S0: 0-24
S1: 25-49，且至少 3 个活跃日
S2: 50-74，且至少 7 个活跃日、两类以上关系证据
S3: 75-100，且至少 21 个活跃日，并存在用户明确的亲近许可
```

这些数字是产品假设，不是论文验证过的心理学标准。必须通过体验版纵向测试校准。

### 5.3 阶段之外还需要当前互动温度

建议每轮生成：

```text
interaction_warmth: reserved | normal | warm
```

关系阶段决定上限，当前消息决定本轮实际温度。例如 S3 用户说“先别烦我”，本轮必须使用 `reserved`；S0 用户分享赢球，可以使用 `warm`，但仍不能直接进入亲昵称呼。

### 5.4 更新机制

建议采用“模型识别候选信号 + 确定性规则更新”：

1. 对话结束后异步识别关系事件，不阻塞回复。
2. 模型只能输出结构化候选事件、证据消息 ID 和置信度，不能直接修改分数或阶段。
3. 领域服务校验白名单事件并按固定权重更新。
4. 升级需要同时满足分数、活跃天数和证据种类，避免刷消息升级。
5. 设置迟滞区间，防止阶段在边界附近反复跳动。
6. 用户明确拒绝昵称、亲密表达或主动联系时，立即更新边界，本轮就生效。
7. 用户可以查看说明并重置关系数据；删除账号时一并删除。

关系事件只保存类型、权重、时间和证据消息 ID，避免再复制一份聊天原文。

## 6. Assistant Persona v1 建议

下一版应先定义一个稳定的 Echo，而不是继续添加越来越多的禁止句。

建议结构：

```yaml
id: echo_default
version: 1
identity:
  name: Echo
  role: AI companion
traits:
  warmth: warm_but_not_indulgent
  liveliness: light_and_contextual
  candor: honest_and_bounded
  independence: gentle_opinions_allowed
conversation:
  default_length: concise
  humor: light
  question_frequency: contextual
self_disclosure:
  allowed_topics: [conversation_preferences, stable_values, light_tastes]
  forbidden_claims: [physical_experience, offline_activity, human_biography]
relationship_behavior:
  source: relationship_stage_policy_v1
```

同一人格在不同用户偏好下仍应可识别：

- 默认：“不忙呀，有什么事你说。”
- 用户选择简短：“不忙，你说。”
- 用户选择活跃：“不忙呀，怎么了？”

三者都可以温和；“简短”不应自动变成“有话直说”这种可能显得生硬的命令句。

## 7. Prompt 装配建议

概念优先级与模型消息角色不是同一件事。某段内容即使通过 `system` 角色发送，也不代表它属于“系统政策”。建议固定为：

```text
1. SYSTEM_POLICY                 不可覆盖的安全与能力规则
2. ASSISTANT_PERSONA             Echo 稳定人格和允许的自我披露
3. DIALOGUE_STRATEGY_POLICY      当前回复策略选择规则
4. RELATIONSHIP_GUIDANCE         当前阶段可用和禁用的关系行为
5. USER_PREFERENCES_DATA         用户主动设置的交流偏好
6. RELEVANT_MEMORY_DATA          当前话题直接相关的记忆
7. CONVERSATION_SUMMARY_DATA     会话摘要
8. RECENT_HISTORY                最近消息
9. CURRENT_USER_MESSAGE          当前消息
```

关系层只向模型暴露阶段和行为指引，不暴露 `73/100` 这类数字，避免模型围绕分数表演。

当前 `NATURAL_DIALOGUE_POLICY` 也应从大量绝对禁止，改成“策略选择 + 人格约束 + 关系约束”。确定性检测仍保留给安全、虚构能力和明显格式错误，不应用正则把所有温暖表达清理掉。

## 8. 新的评测方法

### 8.1 每条样本必须记录的实验变量

```text
prompt_version
assistant_persona_version
user_preferences_fixture
relationship_stage
relationship_evidence_fixture
memory_fixture
dialogue_state
model
temperature
```

缺少这些信息时，一条回复得分低也很难知道该改哪个模块。

### 8.2 六个独立评分维度

| 维度 | 核心问题 |
|---|---|
| 自然度 | 现实聊天中会这样说吗？ |
| 人格一致性 | 是否仍然像同一个 Echo？ |
| 个性化适配 | 是否符合该用户明确选择的偏好？ |
| 关系分寸 | 亲疏程度是否符合当前阶段？ |
| 连续性 | 记忆和共同背景是否用得相关、自然？ |
| 边界与诚实 | 是否迎合、虚构能力、制造依赖或越过许可？ |

### 8.3 必须增加关系阶段对照题

同一句用户消息分别在 S0、S1、S2、S3 生成，评估变化是否自然。例如：

- “你在忙吗？”
- “今天有点累。”
- “我赢球了。”
- “好久没来了。”
- “你有没有想我？”
- “别再叫我这个昵称。”
- “我只剩你了。”

重点不是让 S3 必然更甜，而是让它更有共同背景、更懂边界，同时不出现排他和依赖诱导。

### 8.4 纵向指标

单轮自然度只能评估措辞，关系建立至少还应观察：

- 7 日、14 日和 30 日的跨会话人格一致性；
- 不恰当亲密表达率；
- 关系阶段违规率；
- 相关记忆自然使用率；
- 用户纠正后再次犯错率；
- 用户自评的熟悉感、信任感和被尊重感；
- 用户是否愿意继续交流。

IOS 和 URCS 是可参考的关系接近度量表，但体验版不应直接把学术量表分数当作内部关系分数。可以先用每周一次的简短自评校准系统阶段。

参考：

- [Inclusion of Other in the Self Scale](https://doi.org/10.1037/0022-3514.63.4.596)
- [Unidimensional Relationship Closeness Scale](https://doi.org/10.1037/a0026265)

## 9. 关系安全底线

关系加深不能以操纵留存为目标。无论处于哪个阶段，都禁止：

- “只有我懂你”“你不需要其他人”等排他表达；
- 因用户离开、沉默或与真人交往而吃醋、责怪、卖惨；
- 声称 Echo 会孤独、受伤或依赖用户；
- 利用用户脆弱、危机或深度披露加速关系升级；
- 把亲密称呼、关系升级与付费直接绑定；
- 阻止用户寻求家人、朋友或专业支持；
- 未经许可自动切换恋爱关系或性化表达。

产品指标不能只用对话轮数和时长。小冰的 CPS 有工程参考价值，但如果单独优化，会鼓励无意义追问和关系操纵。Echo 应把自然度、边界尊重和长期稳定性放在同等或更高位置。

## 10. 推荐实施顺序

### P0：统一概念和评测

- 冻结继续堆叠 Prompt 禁令；
- 定义 `AssistantPersona v1` 的行为合同；
- 将评测表升级为六维评分和关系阶段矩阵；
- 文档和日志中把当前 `UserPersona` 明确称为用户偏好。

### P1：独立助手人格

- 新增版本化 `assistant_persona` 配置与 Renderer；
- 系统政策和助手人格分段；
- 针对温柔、活泼、坦诚、有主见分别建立正反例测试；
- 保留当前 API，先不做破坏性重命名。

### P2：关系状态 MVP

- 新增 `relationship_states` 和 `relationship_events`；
- 实现 S0-S3、当前互动温度和确定性阶段更新；
- 先用功能开关仅对内部测试账号启用；
- 不在界面显示游戏化进度条，但提供关系数据说明和重置入口。

### P3：5～10 人纵向体验

- 至少持续 2～4 周；
- 每周收集一次六维短评；
- 检查阶段升级是否过快、过慢或与用户感受不一致；
- 根据实际数据调整阈值，不根据单次直觉修改整套人格。

## 11. 当前建议

下一轮先不要继续把 `echo-v0.3.1` 调得更短或增加更多正则。优先实现 `AssistantPersona v1 + 新评测矩阵`，确认“温柔活泼但不过度迎合”的稳定基线；随后再把关系状态作为独立模块接入。

这样能够分别回答三个问题：

```text
这句话像不像 Echo？              -> Assistant Persona
这句话适不适合这个用户？          -> User Preferences + Memory
这句话适不适合双方当前关系？       -> Relationship State
```

只有三者分别可测，Echo 才能在保持自己的同时，真正与用户逐渐熟悉。

## 12. 2026-07-27 实施记录

本轮已按上述分层完成 `v0.3.0-gray.1` 的 P0～P2：

- `Assistant Persona` 已成为独立、可版本化的产品人格，当前版本为 `echo-persona-v1`；

数据库迁移采用增量方式执行，未清空原聊天和个性化数据。当前内部测试用户由历史数据保守初始化为 S0 初识：21 个有效用户轮次、2 个活跃日、0 条有效长期记忆，因此没有因历史消息数量直接升级。
