# Echo 桌面机器人三阶段实施方案

## 1. 目标与边界

本方案为 Echo 增加一个桌面机器人终端。机器人不是一套新的 AI 产品，而是 Echo 的另一个身体：它与 Flutter APP 使用同一用户、人格、关系状态、聊天记录和长期记忆。

第一版限定为固定放置在桌面上的语音终端，不包含轮式移动、机械臂、导航或视觉识别。目标是先验证用户是否愿意把桌上的设备当作 APP 中同一个 Echo 来互动。

### 1.1 最终部署形态

后端只保留一套 Echo Core，根据部署位置提供两种运行方式：

```text
云端模式
机器人 / APP -> Echo Cloud -> 云端模型服务

局域网 Hub 模式
机器人 / APP -> Echo Hub -> 本地模型服务或云端模型服务
```

Echo Hub 是未来的配套服务器硬件。它使用与云端相同的 Echo Core、数据模型和设备协议；不同之处仅在服务地址、数据位置与 Provider 配置。不要为机器人复制另一套业务后端。

### 1.2 术语

| 术语 | 含义 |
| --- | --- |
| 本地音频 | 麦克风采集、扬声器播放、静音、唤醒和打断在机器人上运行。 |
| 本地 ASR | 机器人或 Echo Hub 在本地将语音转成文本。 |
| 本地 TTS | 机器人或 Echo Hub 在本地将回复文本合成为语音。 |
| 半离线 | 音频处理的一部分在本地，对话模型、记忆或某些语音能力仍可使用服务器。 |
| 完全离线 | ASR、TTS、对话模型、记忆和数据库均可在局域网或设备内运行，外网断开仍可工作。 |

## 2. 共同架构原则

### 2.1 一个 Echo Core，两个客户端入口

```text
                     +-----------------------------+
APP (用户凭证) ----> | APP 接入层                  |
                     |                             |
机器人 (设备凭证) --> | 设备接入层                  | --> Chat / Agent / Memory / Persona
                     |                             |     ASR / TTS Provider
                     +-----------------------------+
```

APP 继续负责账户、文字聊天、设备配置和设备管理。机器人只负责实体交互：收音、播放、状态灯、物理静音和未来的传感器/动作。机器人不得保存用户登录 Token。

### 2.2 设备身份与安全

每台机器人需要独立的 `device_id` 和设备凭证。初次绑定由 APP 发起，机器人完成一次性绑定后获得凭证；之后机器人仅能操作所属用户授权的对话与设备能力。

必须支持：

- 绑定、解绑和凭证撤销。
- 在线心跳、最后在线时间和固件版本上报。
- 物理静音状态上报；静音时不得发送原始音频。
- 用户 Token 与设备凭证分离。
- 机器人被转让或恢复出厂设置后的凭证清除。

### 2.3 统一设备会话协议

机器人始终面向同一份设备协议，不关心连接的是云端 Echo 还是局域网 Echo Hub。

```text
设备上行：device.ready、heartbeat、audio.start、audio.frame、audio.stop、speech.interrupted
服务端下行：session.ready、asr.partial、assistant.text、assistant.audio、device.state
```

第一阶段可复用现有 PCM16LE 音频格式和现有语音业务流程。随着实时体验优化，再收敛成设备专用 WebSocket 会话，不影响 APP 已有的语音通话接口。

### 2.4 交互状态机

机器人必须有明确状态，避免录音、播放和指示灯彼此冲突：

```text
idle -> listening -> thinking -> speaking -> idle
                     ^              |
                     |---- interrupt|
offline / muted 可从任意状态进入
```

- `idle`：待机，可显示低亮状态灯。
- `listening`：正在收音，禁止播放回复。
- `thinking`：已停止收音，等待识别或对话结果。
- `speaking`：正在播放 Echo 回复。
- `interrupt`：用户按键或检测到有效语音时立刻停止播放，回到 `listening`。
- `muted`：本地禁用麦克风，不能仅依赖软件 UI。

## 3. 阶段一：云端语音闭环桌面原型

### 3.1 目标

在不增加本地模型复杂度的前提下，验证硬件声音体验、设备绑定和“APP 与机器人是同一个 Echo”的体验。

```text
机器人本地收音 / 播放 / 按键唤醒 / 打断
-> Echo Cloud ASR
-> Echo Cloud Chat、人格、记忆
-> Echo Cloud TTS
-> 机器人播放
```

### 3.2 推荐硬件

| 类别 | 第一台原型建议 | 目的 |
| --- | --- | --- |
| 主控 | Raspberry Pi 5，8 GB | 运行 Linux、音频程序、网络与未来本地模型。 |
| 供电与散热 | 官方规格电源、主动散热、稳定外壳 | 避免长时间语音负载降频或重启。 |
| 存储 | 128 GB 或以上 microSD；稳定后切换 SSD | 保存系统、日志和后续离线模型。 |
| 音频前端 | USB 双麦克风阵列，例如 ReSpeaker Lite | 先降低驱动和接线复杂度。 |
| 输出 | 与音频板匹配的 3W 至 5W 扬声器 | 验证近距离桌面播放效果。 |
| 控制 | 一个物理静音开关、一个交互按键、一个状态灯 | 隐私、唤醒与状态反馈。 |

第一阶段不采购摄像头、AI 加速卡、ESP32、电机、电池或底盘。先把组件平放在桌面上调通，再设计外壳。

### 3.3 软件范围

机器人端新增独立运行时项目，建议暂定为 `echo-device/`：

```text
echo-device/
  audio/       # 录音、播放、音量、打断
  transport/   # 设备认证、WebSocket、重连
  state/       # 交互状态机
  hardware/    # 按键、LED、物理静音抽象
  config/      # 云端或 Hub 服务地址
  diagnostics/ # 音频与网络自检，不记录语音正文
```

后端新增 `devices` feature，而不是复制 chat 或 voice feature：

```text
features/devices/
  domain/          # 设备、绑定、授权范围、状态
  application/     # 绑定、撤销、心跳、会话授权
  infrastructure/  # PostgreSQL、设备凭证散列、连接管理
  interface/       # APP 管理 API、设备会话 API
```

APP 第一阶段只新增设备管理页，不参与录音或播放：绑定、设备名称、在线状态、音量、静音状态、解绑和固件版本。

### 3.4 实施顺序

1. 在 PC 或树莓派上做扬声器播放与麦克风录音自检。
2. 用按键按住说话完成一轮录音、上传、回复播放。
3. 接入设备绑定和设备凭证，不让硬件保存用户 Token。
4. 用设备凭证打通现有 Echo 语音、聊天和 TTS 业务。
5. 增加播放期间的按键打断。
6. 增加心跳、断网提示、断线重连和物理静音。
7. APP 显示设备状态并支持解绑。

### 3.5 验收标准

- 已绑定设备能在正常 Wi-Fi 下完成按键说话到播放回复的完整闭环。
- APP 与机器人产生的对话进入同一用户聊天历史，并可使用同一人格与记忆。
- 播放期间按键触发后，播放可在可感知的短时间内停止并开始下一次收音。
- 设备断网时显示明确状态；恢复网络后自动重连，不重复提交旧语音。
- 物理静音后不上传音频，APP 可见静音状态。
- APP 解绑后，设备凭证立即失效，不能继续访问用户对话。

### 3.6 阶段一暂不解决的问题

- 远场唤醒、多人说话和复杂噪声环境。
- 本地 ASR 与本地 TTS。
- 摄像头、人物识别、表情屏、舵机和移动。
- 云端不可用时的完整回复能力。

## 4. 阶段二：本地 ASR 与自然打断

### 4.1 目标

把听觉入口下沉到机器人或 Echo Hub。对话、人格和长期记忆仍可使用统一服务器，降低网络延迟和云端语音数据依赖。

```text
机器人本地唤醒 / VAD / 降噪 / ASR
-> 文本发送至 Echo Cloud 或 Echo Hub
-> Echo 对话与记忆
-> TTS 音频
-> 机器人播放
```

### 4.2 新增能力

- 本地唤醒词；保留按键作为可靠降级路径。
- VAD（语音活动检测），判断开始说话和说话结束。
- 回声消除与降噪，防止扬声器声音再次被识别成用户语音。
- 本地 ASR 模型；通过 Provider 接口支持切换本地、Hub 和云端识别。
- ASR 置信度、超时和失败原因上报，不上传原始音频作为普通日志。
- 播放时语音打断（barge-in），先确保不误把自身 TTS 当成用户说话。

### 4.3 部署选择

| 位置 | 优点 | 风险 |
| --- | --- | --- |
| 机器人本机 ASR | 数据不离设备，断网仍可得到文本。 | 树莓派算力与模型尺寸受限。 |
| Echo Hub ASR | 可用更大的本地模型，机器人更轻。 | Hub 离线或局域网异常时需要降级。 |
| 云端 ASR 兜底 | 识别效果和维护成本较稳定。 | 音频仍可能离开局域网。 |

推荐顺序是“机器人本机优先，Hub 其次，云端最后”。但只有在本地识别准确率和延迟满足验收标准后，才启用该优先级。

### 4.4 硬件调整

阶段二前先进行实测，避免提前采购：

- 若树莓派本机 ASR 满足延迟与温度要求，继续使用现有主控。
- 若本地 ASR 造成持续降频、回复等待过长或音频竞争，再引入 Echo Hub。
- 若麦克风远场效果不稳定，优先升级麦克风阵列位置、声学腔体与回声调校，不急于更换主控。

### 4.5 验收标准

- 常见桌面距离下，本地 ASR 对短句有稳定可用的识别效果。
- 网络断开时，设备至少能完成本地唤醒、收音、识别、状态提示；若对话依赖云端，要明确告知而非假装处理中。
- Echo 说话时，用户正常插话能够停止播放并进入新一轮聆听。
- 本地 ASR、Hub ASR 与云端 ASR 的切换不会改变用户身份、会话归属和聊天记录。
- 音频原始数据默认不持久化；诊断数据只保存状态、耗时和错误码。

## 5. 阶段三：本地 TTS、Echo Hub 与可选离线能力

### 5.1 目标

把回复发声能力下沉到机器人或 Echo Hub，并建立可部署在家庭局域网的 Echo Hub。此阶段完成从云端优先到局域网优先的迁移能力。

```text
机器人本地 ASR
-> Echo Hub Chat / Memory / Persona
-> Echo Hub 或机器人本地 TTS
-> 机器人播放
```

云端 Echo 仍是默认版和可选增强；Hub 版允许用户自行选择哪些数据留在局域网、哪些请求可使用云端模型。

### 5.2 Echo Hub 组成

```text
Echo Hub
  Echo Backend（与云端同一版本）
  PostgreSQL + 向量检索
  本地或可选云端 LLM Provider
  本地 ASR / TTS Provider
  设备会话与局域网发现
  管理界面、备份与升级服务
```

Hub 不应只是一个语音代理。它要保留 Echo 用户、会话、记忆、设备绑定和同步策略的完整所有权，才能在外网不可用时保持持续陪伴体验。

### 5.3 TTS 策略

| 方案 | 适用情况 | 取舍 |
| --- | --- | --- |
| 机器人本机 TTS | 短回复、断网优先、单设备。 | 音色、模型体积和算力受限。 |
| Echo Hub TTS | 多设备、希望更自然的本地音色。 | 依赖家庭局域网和 Hub。 |
| 云端 TTS | 追求当前最自然的声音或专属音色。 | 需要外网与服务成本。 |

TTS 输出格式和播放控制必须保持一致：无论音频来自本机、Hub 还是云端，机器人都要支持开始、暂停、取消、队列清空和故障恢复。

### 5.4 数据与同步策略

在 Hub 模式中，必须先明确数据主库归属，不能在云端与本地各自无规则写入。

建议提供三种明确模式：

- 云端主库：Hub 是本地缓存与模型网关。
- Hub 主库：云端只做用户显式开启的备份或模型增强。
- 单机私有：所有数据仅保留在 Hub；APP 仅经局域网访问。

每种模式都要覆盖：用户导出、删除、备份恢复、设备转让、聊天冲突、模型不可用与恢复后的重试。

### 5.5 验收标准

- Echo Hub 可使用与云端相同的机器人和 APP 协议，不需要安装另一份 APP。
- Hub 中断外网后，已配置的本地 ASR/TTS 可继续工作。
- 用户可清晰看见当前使用的是云端、Hub 还是本机 Provider。
- 各模式下用户的聊天、人格、关系和记忆数据归属可解释、可导出、可删除。
- Hub 故障或重启后，机器人能回退到明确的离线状态或指定云端模式，不产生重复消息。

## 6. 视觉、动作与导航的后续接入

视觉、动作和导航不进入前三阶段的验收范围，但协议应预留抽象事件：

```text
视觉上行：vision.person_detected、vision.user_present
动作下行：expression.set、led.set、motion.execute
导航下行：navigation.execute
```

模型只能产生高层意图，例如 `look_at_user` 或 `show_happy`。实时控制器负责把意图变成安全的灯光、舵机或电机指令。禁止让模型直接生成 PWM、速度或坐标控制命令。

## 7. 当前决策清单

开始阶段一前需要确认：

1. 首台原型采用 Raspberry Pi 5 还是先用现有 PC 验证音频。
2. 使用按键说话作为最初交互，还是同步研发唤醒词。
3. 初期 TTS 是否直接复用当前云端音色。
4. 设备是否只支持一个绑定用户，还是允许家庭共享模式。
5. APP 设备管理页第一版包含哪些控制项。
6. Echo Hub 的目标形态：迷你主机、NAS 容器，还是未来的专用硬件。

推荐默认决策：Raspberry Pi 5 桌面原型、按键说话、云端 TTS、单用户绑定、APP 仅做绑定/状态/音量/静音/解绑，Hub 暂不进入阶段一开发。
