# 主动机制设计与 P1 实现

更新日期：2026-11-11
适用范围：presence（念头）与 proactive_chat（投递）的主动链路。

## 1. 已确认的业务决策

| # | 决策 | 落地方式 |
| --- | --- | --- |
| 1 | 主动性三档 | quiet 1 / standard 6 / active 12 条/天，12 为上限 |
| 2 | 深夜禁闲聊 | 23:00–07:00 只允许日程类目标 |
| 3 | 只结果回传 | 执行前不说话；回传说明做了什么、结果如何 |
| 4 | 隐私类可自主 | 摄像头/屏幕可主动，但回传必须写明看过什么；偏好保留关闭 |
| 5 | 外发授权 | 发给用户自己可主动；他人需事先授权 |
| 6 | 失败也说 | 回传三选一：成功 / 部分成功 / 没做成 |
| 7 | 每日消息预算 | 上限 12 |
| 8 | 目标最多 5 步 | 主动 turn 的工具调用上限单独设为 5 |
| 9 | 信号汇聚 | 每 30 分钟 tick + 事件驱动（专注结束、设备上线、日程到点） |

## 2. 概念模型

| 概念 | 定义 | 例子 |
| --- | --- | --- |
| 触发信号 | 外部事实：时间 / 日程 / 专注 / 设备 / 记忆 | 用户说明天面试 + 现在 21:00 |
| 意图 | Echo 想做什么，一句话 | 想提醒他早点休息 |
| 目标 | 可跨轮、可执行的小计划 | 关心今晚睡眠，最多 2 步，23:00 前有效 |
| 执行 | 用工具完成目标（0–5 步） | 写便签 → 发消息 |
| 回传 | 把结果告诉用户并写进上下文 | 留了张便签在你电脑上 |

## 3. 流程

```text
信号汇聚（30 分钟 tick / 事件）
  → 打扰门禁（代码）：深夜闲聊 / 静默 / 预算 / 未回复 / 正在聊天 / 去重
  → 意图与目标（一次轻量模型调用）
  → 目标落库 pending
  → 统一投递：创建 job（goal_id）
  → 执行：Agent runtime + 完整工具面（排除破坏类）
  → 回传：成功 / 部分成功 / 没做成
  → 投递：写消息 + notification_outbox
  → 入账：goal=reported，等待用户反馈
```

## 4. P1 已实现：投递统一

### 4.1 数据

```text
proactive_goals（新表）
  goal_id / user_id / trigger_type / trigger_ref
  intent / draft_text
  status: pending / reported / failed / expired / cancelled
  created_at / reported_at

proactive_chat_jobs（加列）
  goal_id
```

`proactive_goals` 与 job 在同一事务写入；job 通过 `goal_id` 反查目标。

### 4.2 链路

```text
presence.tick
  → 生成念头 + 文案（沿用 thought_generator + message_composer）
  → goal_creator.create_goal(intent=念头, draft_text=文案)
  → proactive_repository.create_goal()（goal + job 原子写入）

ProcessProactiveChatJobs.run_once
  → claim_due_job 拿到 goal_id
  → _deliver_goal_job：偏好/暂停/静默门禁 → persist_delivery
  → 写 chat_messages + notification_outbox
  → mark_goal_reported
```

presence 不再直接调用 `deliver_external_assistant_message`。旧的 `ChatPresenceMessageDelivery` 已删除。

### 4.3 验收结果

| 项 | 结果 |
| --- | --- |
| 全量测试 | 552 passed / 9 skipped / 0 failed |
| 架构检查 | 通过 |
| 目标创建 → 投递 | goal=reported，job=succeeded，消息已写入 |
| 推送 | `notification_outbox.status=sent`，`body_policy=preview` |

测试用户没有注册推送设备时会 `discarded / no_active_target`，属于预期；手机账号已能收到通知。

主动模式实际注入（实测）：

| 场景 | 工具数 |
| --- | ---: |

## 5.2 P3 已实现：目标执行与回传

| 改动 | 说明 |
| --- | --- |
| goal 新增 `action_intent` / `result_status` / `result_summary` | 记录做了什么、结果如何、失败原因 |
| worker 执行目标 | 有 `action_intent` 时执行动作，否则沿用 P1 的文案直投 |
| 动作执行确定性 | 按 `music:` / `notepad:` 映射到桌面动作，不交给模型自由选择 |
| 回传三态 | 成功走模型润色；失败用「本来想…，这次没做成。」；`dsh:` 等未授权动作直接判失败 |
| 投递 | 统一走 job 通道，写消息 + 推送 |

**验收结果**

| 场景 | 结果 |
| --- | --- |
| `music: 夜的钢琴曲五 石进` | goal=reported/success；桌面日志「收到操作请求 → 总是允许 → 操作完成」；回传「给你放了…」 |
| `dsh: 整理一下桌面上的文件` | goal=reported/failed；原因「主动动作需授权或暂不支持：dsh」；回传「本来想…，这次没做成。」 |

**一个真实教训**：P3 第一版把动作交给模型自由选择，结果让它「放歌」，它却调用了摄像头。现在改为代码执行动作、模型只写回传，避免偏题。

**P3 尚未完成**：48 小时去重、三档预算、部分成功（partial）判定。

## 5.3 P4 已实现：触发信号与打扰规则

| 信号 / 规则 | 落地方式 |
| --- | --- |
| 时间（tick） | 默认间隔 900 → **1800 秒**（30 分钟） |
| 记忆 | presence 产 goal 时带 `trigger_type=memory`、`trigger_ref=memory_id` |
| 专注 | `study_focus` 结束不再直投，改为创建 `trigger_type=focus` 的 goal，走统一投递与推送 |
| 日程 | 用户显式提醒本来就走 job 通道，不再重复接 |
| 设备 | 只影响工具可用性（P2），不单独触发主动消息 |
| 深夜 | 23:00–07:00 由静默窗口拦截，专注/闲聊类目标 defer 到 07:00；显式日程提醒按偏好策略处理 |
| 去重 | 优先按 `trigger_type + trigger_ref`（同一 session 不重复）；无 trigger_ref 时按 intent 文本 48 小时去重 |

**验收结果**

| 场景 | 结果 |
| --- | --- |
| 23:12 专注完成 | job 被 defer 到 07:00，`error_code=quiet_hours`，符合深夜规则 |
| 临时推后静默窗口后 | goal=reported/success；消息「辛苦了，这一轮 15 分钟完成啦…」 |
| 不同专注 session | 去重键改为 trigger_ref 后各自独立提醒，不再被相同文案误伤 |

## 5.4 P5 已实现：念头合一

| 改动 | 说明 |
| --- | --- |
| 念头生成一次产出 | `thought` / `salience` / `shareable` / `action_intent` / `draft_text` 同一次调用返回 |
| 删除 composer | 不再有第二次"把念头写成消息"的模型调用；`PresenceMessageComposer`、实现、装配与配置一并删除 |
| 是否打扰由代码判断 | 预算、静默、间隔、`draft_text` 是否为空，统一在服务层决定 |
| 落库 | `presence_thoughts.draft_text` 保存草稿，便于复盘 |

**收益**：每次念头从 2 次模型调用降到 1 次，presence 的 token 成本约减半。

**验收**：一次 tick 只产生一次模型请求；`presence_thoughts` 最新记录带有 `draft_text`；`shareable` 与 `draft_text` 一致性由提示词约束（draft 非空则 shareable 必须为 true）。

## 5.5 主动触发收敛（按讨论调整）

| 调整 | 说明 |
| --- | --- |
| presence 只保留 `shareable` + `draft_text` 判定 | 删除消息预算（6/天）、消息间隔（60 分钟）、presence 层静默检查；念头生成后只要模型认为可说且有草稿，就创建目标 |
| 深夜与总预算交给 worker | 三档预算（quiet 1 / standard 6 / active 12）与 23:00–07:00 defer 仍在投递层统一执行 |
| `draft_text` 明确为执行失败兜底 | goal 有 `action_intent` 时走主动执行；执行失败用 `draft_text` 回传，草稿不再悬空 |
| 设备能力不再反复征求许可 | 自然对话规则第 9 条改为：直接使用电脑/手机能力，隐私读取后如实说明看到什么；只有外发给他人或修改文件才先说明 |

## 6. 已知边界

- presence 自己的计数（`presence_states.proactive_messages_used` 等）仍在用；P3 统一到 `proactive_chat_preferences`，过渡期以 proactive 为准。
- `study_focus` 的完成提醒仍走 `deliver_external_assistant_message`（无推送），P4 统一。
- 主动动作（`action_intent`）目前仍是 presence 旁路执行，P2 迁到 Agent 工具面。
- 测试用户与手机账号的推送目标不同，验收时以有 `push_targets` 记录的账号为准。
- 本地联调期间，桌面节点曾临时配对到本地服务；原生产配置备份在 `%APPDATA%\EchoDesktop\config.production.bak`，恢复后节点会回到生产。
- 主动动作目前只支持 `music:` / `notepad:`；`dsh:` 与多步手机任务按「需授权」处理。
- P4 只接入"专注结束"这一事件信号；日程到期、设备上线、记忆计划类触发仍靠 presence tick 的上下文推断，未做独立事件源。
- 静默窗口按用户时区判断；每日预算按 UTC 日期统计，跨时区用户可能在本地凌晨重置预算。
