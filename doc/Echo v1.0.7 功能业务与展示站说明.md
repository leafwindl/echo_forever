>
> 用途：给产品、设计、内容和展示站开发使用
>
> 当前版本：Android `1.0.7+12`，服务端分支 `master`
>
> 文档原则：只展示当前代码已经具备的能力；标记为“未启用”的能力不能在页面上写成已上线承诺。

## 1. 产品定位

Echo 是一个有连续记忆、会理解语境、能够主动联系用户的 AI 陪伴应用。它不是单轮问答页面，而是把一次聊天变成持续关系：用户可以随时说话，Echo 会结合当前对话、长期记忆、用户偏好和关系状态做出回应。

产品体验的四个关键词：

1. **有时间感**：知道用户刚刚说了什么，也知道用户隔了多久回来。
2. **有连续性**：聊天记录、摘要、长期记忆和关系状态分别保存，退出 APP 后仍可回溯。
3. **有行动能力**：Agent 可以按需调用时间、表情包、提醒和可选联网搜索工具。
4. **有陪伴感**：文字、独立表情包、人物状态、语音和每日来信共同构成 Echo 的表达。

## 3. 一条完整用户旅程

```text
打开 APP
  -> 手机号登录
  -> 首次引导设置称呼和偏好
  -> 进入 Echo 聊天首页
  -> 发送文字或表情包
  -> Echo Agent 读取上下文并按需调用工具
  -> 回复文字、独立表情包或语音
  -> 消息和记忆写入服务端
  -> 用户离开后，任务 Worker 可在合适时间主动联系
  -> 后台通过通知提醒，点击后回到同一段聊天
```

退出 APP 不会删除聊天内容。重新进入时先显示最近一页，继续向上滚动才请求更早历史。

## 4. 核心业务逻辑

### 4.1 登录、人物和关系

用户通过手机号验证码建立账号。首次完成 onboarding 后，服务端保存用户称呼、偏好和人格相关设置。每轮用户消息都可能产生关系事件，例如互动次数、积极信号、边界信号和最近互动时间。

人物显示只属于客户端展示层：聊天收起时显示 idle，输入或聊天展开时显示 sit。人物图片不参与模型推理，也不改变聊天数据。

### 4.2 异步聊天

用户发送文字或表情包时：

1. 客户端立即插入本地发送中的消息。
2. `POST /chat/messages` 通过 `client_message_id` 做幂等提交。
3. 服务端先写入 `chat_messages`，返回 `202 Accepted`。
4. 用户可以继续发送下一条消息，不需要等待 Echo 回复。
5. Chat Worker 为同一用户串行处理待完成回合，避免上下文竞态。
6. Agent 读取最近消息、摘要、记忆、人格和关系状态。
7. Agent 输出多段文字和可选内容部件。
8. 服务端先保存 Echo 消息，再通过 SSE `chat.delivery.created` 交付。
9. 客户端按服务端提供的段间延迟展示 typing、文字和表情包。

用户或网络失败时，客户端保留失败状态，支持重新发送；服务端使用 `client_message_id` 避免重试生成重复消息。

### 4.3 Agent 与工具

Agent 是统一的消息决策层，LLM 是 Agent 使用的语言模型。LLM 不直接操作数据库或发送网络请求，只能从 Tool Registry 选择工具。

当前工具：

- `get_current_time`：回答当前时间、日期或解析相对时间前必须使用。
- `search_web`：需要外部最新资料时使用，生产是否可用取决于联网 provider 配置。
- `search_stickers`：按语义返回 Echo 和用户可见的表情包候选，并返回优先级。
- `send_sticker`：只能发送本轮搜索返回且通过冷却门禁的一张表情包。
- `create_chat_schedule`：创建提醒或后续联系。
- `list_chat_schedules`、`cancel_chat_schedule`：管理用户可见任务。

工具成功和最终回复在同一轮 Agent 结果中生成，避免“功能已经执行但文字说不能执行”的冲突。

### 4.4 表情包

用户表情包上传时必须填写：

- 图片文件。
- 人类可读的描述。
- 一个或多个语义标签。

用户发送路径类似微信：输入框旁点击表情包按钮，底部展开可用表情包，点击后立即作为独立消息发送。

Echo 发送表情包路径：

```text
当前语境
  -> Agent 判断是否自然需要表情包
  -> search_stickers 返回相近语义候选
  -> 优先级排序 + 最近 5 轮/5 分钟冷却
  -> send_sticker 成功
  -> 回复文字与图片分开持久化和展示
```

官方表情包增加优先级，但私人表情包仍可参与候选。每轮最多成功发送一张；失败的发送不消耗额度，候选集合变化后允许重新选择同一个 ID。

### 4.5 长期记忆和摘要

聊天消息是原始事实，摘要是上下文压缩，长期记忆是经过抽取和状态管理的稳定信息，三者不能互相替代。

```text
最近聊天 + 历史摘要 + active memories + persona + relationship
  -> Prompt 上下文
  -> Agent/LLM 回复
  -> 消息落库
  -> 后台记忆抽取和摘要更新
```

“清除聊天上下文”只清理聊天消息、摘要和未完成回合，不清理长期记忆、人格偏好和关系状态。长期记忆页面提供单条删除和全部清空。

### 4.6 语音通话

语音通话是用户主动发起的独立流程：

```text
PCM 录音
  -> WebSocket 流式 ASR
  -> 失败时整段 PCM ASR
  -> /chat/send mode=call
  -> Agent 生成回复
  -> CosyVoice TTS
  -> 客户端播放
```

通话不发送表情包，不创建主动聊天任务，不产生后台通知。音频文件有保留期，过期由清理 Worker 删除。

### 4.7 主动聊天与提醒

主动行为有三种来源：

1. **用户明确提醒**：例如“晚上八点提醒我喝水”。
2. **Echo 后续联系**：用户允许后，Echo 可创建一次性“晚点再问问”的任务。
3. **自然主动聊天**：用户打开允许后，系统根据最近互动时间和频率策略创建候选任务。

推荐策略：

| 档位 | 最少未互动时间 | 限制 |
| --- | ---: | --- |
| 保守 | 24 小时 | 每周最多 4 次，最小间隔 24 小时 |
| 平衡 | 6 小时 | 每天最多 4 次，最小间隔 6 小时 |
| 主动 | 2 小时 | 每天最多 6 次，最小间隔 2 小时 |

所有主动任务受用户时区、安静时段、连续未回复次数和任务状态限制。默认安静时段为 `22:30-08:00`，默认通知隐藏正文。主动消息仍然是普通 Echo 聊天消息，通知只是提醒入口。

## 5. 端到端数据流

### 5.1 普通文字消息

```text
Flutter ChatController
  -> Dio POST /chat/messages
  -> chat_messages + chat_turn_jobs
  -> Chat Worker
  -> Agent Orchestrator
  -> LLM / Tools
  -> chat_messages + agent_runs + agent_tool_calls
  -> SSE /chat/events
  -> Flutter 合并消息、执行分段展示
```

### 5.2 主动消息

```text
preferences / schedule
  -> chat_schedules
  -> proactive_chat_jobs
  -> Proactive Worker claim due job
  -> 当前上下文 + Agent
  -> chat_messages
  -> notification_outbox
  -> Getui / 前台事件
  -> APP 聊天页
```

### 5.3 应用更新

```text
本机构建 APK
  -> 校验包名、versionName、versionCode、SHA-256
  -> 上传私有 COS
  -> 写入 app_releases
  -> APP GET /releases/latest
  -> 用户确认
  -> POST /releases/{id}/download
  -> 短期签名 URL
  -> 客户端下载、校验、请求 Android 安装器
```

## 6. 展示站的目标

展示站面向没有使用过 Echo 的访客，目标不是展示代码，而是让访客在一分钟内理解：

1. Echo 是一个会记得、会回应、也会主动联系的陪伴应用。
2. 聊天、语音、表情包和提醒不是四个孤立按钮，而是一条连续体验。
3. 用户拥有主动权，可以关闭主动联系、管理记忆、管理任务和控制通知正文。
4. 当前产品已经能用的能力和未来扩展能力边界清晰可信。

展示站不需要用户登录，不应读取真实用户聊天，不应暴露 API 密钥、服务器地址之外的内部配置、个推 CID 或数据库信息。演示数据应使用静态 fixture 或脱敏样例。

## 7. 推荐页面信息架构

建议做成一页可滚动的产品展示页，采用完整宽度的叙事分区，不把所有内容堆进互相嵌套的卡片。

### 7.1 首屏：Echo 本人和核心承诺

- 主标题：`Echo`
- 支持文案：`会记得，也会主动找你的 AI 陪伴`
- 补充文案：`从一句聊天，到一次提醒、一段语音和一张刚好合适的表情包。`
- 首屏视觉：使用 Echo 人物素材或 `assets/echo.jpg`，同时露出聊天内容的下一段预览。
- 主要动作：`查看功能`、`了解数据如何流动`、`下载最新测试版`。
- 版本角标：显示 `v1.0.7`，不要显示内部 `+12`。

### 7.2 体验分区：一条连续对话

用一段可交互的静态聊天演示展示：

```text
用户：我下午要去面试，有点紧张
Echo：先深呼吸，你已经准备了很久。结束后告诉我结果，好吗？
Echo：［加油表情包］
系统：已安排今晚的后续问候
```

演示重点：用户可以继续发下一句话，Echo 的回复可以分段，表情包与文字分开，时间和后续任务可见。

### 7.3 功能分区

用六个连续主题分区，而不是只用同色卡片：

1. **连续聊天**：异步发送、SSE 交付、历史分页和断线补偿。
2. **Agent 行动**：需要时间、提醒或表情包时，Agent 调用工具后再组织自然回复。
3. **记忆与关系**：消息、摘要、长期记忆和关系状态各自保存，用户能查看和管理。
4. **表情包表达**：用户点击即发；Echo 根据语境、标签、优先级和冷却选择。
5. **语音通话**：PCM ASR、CosyVoice 和人物陪伴，通话保持独立，不打扰聊天逻辑。
6. **主动联系**：用户设置频率、时区和安静时段，Echo 在允许范围内发起一次自然问候。

### 7.4 控制权与可靠性分区

展示以下可理解的产品控制：

- 主动聊天开关。
- 保守、平衡、主动三个频率档位。
- 安静时段。
- 通知正文显示/隐藏。
- 任务查看、暂停、修改和取消。
- 长期记忆单条删除和全部清空。
- 应用内更新校验。

文案应强调：通知失败不等于消息丢失，消息以服务端聊天历史为准。

### 7.5 结尾：适合谁使用

可以用三种访客场景收束页面：

- 想要有连续感的日常聊天。
- 想用提醒和主动问候保持生活节奏。
- 想通过语音、人物和表情包获得更自然的陪伴。

不要使用“治疗、诊断、保证永远在线、保证系统清理后必达”等医疗或可靠性承诺。

## 8. 展示站演示数据

推荐准备三条无账号演示：

### 场景 A：自然聊天与表情包

1. 用户发送“今天终于把事情做完了”。
2. Echo 分两段回复。
3. 第二段独立显示“开心”或“加油”表情包。

### 场景 B：提醒与通知

3. Echo 回复明确的本地时间和任务标签。

### 场景 C：语音通话

1. 展示 PCM 录音状态和实时识别字幕。
2. 展示 Echo 语音回复播放状态。
3. 明确标注通话不发送表情包，也不触发主动通知。

## 9. 素材清单

展示站可以复用仓库已有素材：

- `assets/echo.jpg`：Echo 品牌/头像素材。
- `app/assets/character/echo_idle.png`：聊天收起时的 idle 人物。
- `app/assets/character/idle_sit.png`：聊天输入时的 sit 人物。
- `assets/sticker/`：官方表情包样例，可按文件名作为演示语义。

图片应保留清晰主体，避免把人物裁切成无法辨认的背景装饰。展示站不应直接引用用户上传的私人表情包。

## 10. 展示站的交互与状态

前端页面至少需要表现这些状态：

- 初始加载和人物素材加载失败。
- 聊天中的 typing、分段到达和表情包单独到达。
- 定时任务创建成功、暂停、取消和错过。
- 通知正文隐藏/显示设置。
- 语音录音、识别中、播放中和失败降级。
- 当前版本、发现新版本、下载校验和安装提示。
- “已实现”“可配置”“暂未启用”能力标识。

演示页的动画应服务于理解：消息逐段出现、任务时间线推进、通知点击回到聊天。不要把动画做成无法阅读的连续闪烁。

## 11. 对外口径

推荐使用：

- “Echo 会根据你允许的范围主动联系你。”
- “你的聊天记录、长期记忆和提醒任务分开管理。”
- “Agent 会在需要时调用工具，再给出一条完整回复。”
- “消息先保存，通知只是提醒入口。”

避免使用：

- “Echo 可以永远记住一切。”
- “Echo 一定会在后台收到每条通知。”
- “所有图片都能立即生成。”
- “语音通话和文字聊天完全共用同一条实时链路。”

## 12. 展示站验收标准

另一个智能体完成页面后，应能回答以下问题：

1. Echo 与普通聊天机器人有什么不同？
2. 用户能否在 Echo 回复前继续发送消息？
3. Echo 为什么会发送一张表情包？
4. 主动聊天是否由用户控制？
5. 退出 APP 后聊天记录是否还在？
6. 语音通话与文字聊天有什么边界？
7. 通知失败时消息是否丢失？
8. 当前版本是什么，哪些能力仍需外部服务商配置？

页面只要能够用真实流程和清晰状态回答这八个问题，就达到了 v1.0.7 展示目标。
